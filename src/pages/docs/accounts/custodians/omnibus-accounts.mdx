# Hold customer funds in an omnibus account

Take deposits for every customer into one account, and still know who paid.

Exchanges and payments processors hold many customers' stablecoins in one account. Each customer's balance lives in your own ledger. On Tempo, you give each customer a [virtual address](/docs/accounts/virtual-addresses): a deposit address that pays straight into your account, with no per-customer wallet and no sweep job. Each deposit names the address it was sent to, so you know which customer to credit.

Virtual addresses and receive policies are live on mainnet and testnet. The code below runs on Moderato testnet.

:::::steps

<span id="choose-the-account" />

### Choose the account that receives deposits

Registering an account binds every deposit address you derive from it to that account permanently. Pick one whose keys you can change without changing its address.

- **Single-key account.** On mainnet and testnet, its deposit addresses work only while you keep that one key. If you expect to rotate keys, register a multisig or upgradeable contract instead.
- **Configurable account.** [Add](/docs/accounts/account-configuration/configuration-updates#add-a-signer) and [remove signers](/docs/accounts/account-configuration/configuration-updates#remove-a-signer) at the same address. Until T14, it runs only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet).

<span id="register-and-derive" />

### Register the account and derive deposit addresses

Register the account once: call `registerVirtualMaster` on the virtual-address registry from it, with a salt you mine offchain with `VirtualMaster.mineSaltAsync`. Registration returns a 4-byte master ID. Register more than once to get separate ranges of addresses, such as one per business line.

Then derive each customer's address offchain from the master ID and a 6-byte customer tag you choose. Deriving an address sends no transaction:

```ts [virtualAddress.ts]
import { VirtualAddress } from 'viem/tempo'

const masterId = process.env.TEMPO_MASTER_ID
if (!masterId || !/^0x[0-9a-fA-F]{8}$/.test(masterId)) {
  throw new Error('Set TEMPO_MASTER_ID to your registered 4-byte master ID')
}

const virtualAddress = VirtualAddress.from({ // [!code hl]
  masterId: masterId as `0x${string}`, // [!code hl]
  userTag: '0x000000000001', // [!code hl]
}) // [!code hl]
```

Keep the mapping from customer tag to customer in your own records. To try registration first, use the [live deposit address demo](/docs/guide/payments/virtual-addresses).

<span id="set-a-receive-policy" />

### Accept only the stablecoins you list

Set a [receive policy](/docs/accounts/policies/receive-policies) on the registered account. Tempo checks deposits to its virtual addresses against the account's policy, because a virtual address can't set its own. This policy accepts one stablecoin from any sender. It lets your account recover anything it holds back:

::::code-group

```ts [receive-policy.ts]
import { client } from './client'

// The stablecoins you list, by token contract address
const { policyId: tokenPolicyId } = await client.policy.createSync({
  account,
  type: 'whitelist', // [!code hl]
  addresses: [stablecoin], // [!code hl]
})

await client.receivePolicy.setSync({
  account,
  senderPolicyId: 'allow-all', // [!code hl]
  tokenPolicyId, // [!code hl]
  claimer: 'self', // [!code hl]
})
```

```ts [client.ts]
// [!include ~/snippets/viem.moderato.public.ts:setup]
```

::::

`account` is the registered account and `stablecoin` is the token contract address you accept. Only TIP-20 stablecoins are forwarded to your account. Other tokens sent to a virtual address can't be recovered, so tell customers to send only the stablecoins you list on Tempo.

<span id="credit-each-deposit" />

### Credit each deposit once

A deposit to a virtual address emits [two `Transfer` events](/docs/protocol/tip20/virtual-addresses) in one transaction: sender to virtual address, then virtual address to your account. Treat the pair as one deposit to your account, not two. Then:

- **Read the customer tag** from the virtual address: its last 6 bytes are the tag you chose. Look up the customer in your records.
- **Check the recipient.** A deposit your receive policy blocks still succeeds and still emits `Transfer`, but its recipient is `ReceivePolicyGuard`, not your account. Credit only when the confirmed event names your account.
- **Record it once.** Store the network, transaction hash, and log index as a unique key, and credit the customer in the same database transaction.

Read live deposits with [webhooks](/docs/api/webhooks) or [transfer events](/docs/guide/payments/accept-a-payment#detect-payments), and history with the [transfers API](/docs/api/transfers).

<span id="handle-held-payments" />

### Handle held payments

A deposit in a stablecoin you don't list stays in `ReceivePolicyGuard` until your account claims it. Index the guard's `TransferBlocked` events for your account to find held deposits. Decide whether to return or accept each one, then [claim it](/docs/accounts/policies/receive-policies#claim-blocked-receipts) with `client.receivePolicy.claimSync`. A claim releases the full amount.

To let senders recover their own held payments instead, set the recovery authority to the sender (`claimer: 'sender'`).

:::::

## Omnibus account limits

- A virtual address never holds a balance: `balanceOf` on it returns `0`. Show customers the balance from your ledger.
- Some protocols record ownership against the literal address they're given. Don't send LP shares, receipts, or rewards to a virtual address unless that protocol supports it.
- The customer tag tells you whose address received a deposit, not who sent it.
