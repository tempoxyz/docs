# Configuration updates

A configuration update changes a configurable account's signers, weights, or threshold, at the same address.

A signer is a key that approves a configurable account's transactions. To back up a key you could lose, let another person approve, end an approver's access, or rotate a key, the current signers approve one [configuration update](/docs/accounts/account-configuration#every-change-is-one-signer-update): a new signer list and threshold. The address, balance, token approvals, and access keys stay the same.

:::warning
**Configurable accounts aren't live yet.** Accounts with several signers and a threshold ([TIP-1107](https://tips.sh/1107)) work only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change. Every configuration update needs one.
:::

## How it works

A configuration update replaces the account's whole signer list. Build it from the address and configuration your app saved for the account ([keep the current configuration](/docs/development/configurable-accounts#keep-the-current-configuration)): rebuild the account with the approving signers' keys attached, as in [Signing thresholds](/docs/accounts/policies/signing-thresholds#collect-approvals), and pass the new list to `updateConfigSync`. Viem signs with the attached keys, highest weight first, until their weights reach the current threshold. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

Each update raises the configuration's version by one. Save the `config` it returns with the account record, and rebuild from the latest saved record before every payment or update: an account built from the old configuration no longer matches the hash Tempo stores, and its next transaction fails. Approvals collected under the old signer list stop counting.

## Add a signer

The weight you give the new signer decides what it can approve alone. Every signer has a weight of at least 1:

- Below the threshold, the new signer approves only together with others, so no single backup or recovery signer controls the account.
- At or above the threshold, it approves anything alone, including removing every other signer. Give this weight only to a key you'd trust with the whole account.

The threshold stays the same unless you change it, so each new signer adds a way to reach it. To keep requiring the same approvers, raise the threshold in the same update. For a recovery signer, give it enough weight that the account can [lose any one signer](/docs/accounts/account-configuration#plan-for-recovery) and still reach the threshold, and no more, because it can approve payments at that weight too. [Signing thresholds](/docs/accounts/policies/signing-thresholds#recommended-signer-setups) lists recommended setups. `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

::::code-group

```ts [add-signer.ts]
import { client } from './client'

const { config: updated } = await client.accounts.updateConfigSync({
  account,
  nextConfig: { // [!code hl]
    owners: [...config.owners, { owner: newSigner, weight: 1 }], // [!code hl]
    threshold: config.threshold, // [!code hl]
  }, // [!code hl]
})
```

```ts [client.ts]
// [!include ~/snippets/accounts-devnet.ts:client]
```

::::

`account` is the rebuilt account, and `config` is the saved configuration it came from. `newSigner` is the new key's address: a passkey, a device key, a key in a KMS or hardware wallet, or an address from a recovery provider. Viem sorts the signers by address, as Tempo requires. [`updateConfig`](https://viem.sh/tempo/actions/accounts.updateConfig) in Viem lists every option. Tempo can't tell whether a signer still holds its key, so have each new signer approve once before you rely on it.

## Remove a signer

Removing a signer ends its power to approve when an approver leaves or a key is lost. The signers that stay approve a list without it:

```ts [remove-signer.ts]
import { isAddressEqual } from 'viem'
import { client } from './client'

const { config: updated } = await client.accounts.updateConfigSync({
  account,
  nextConfig: { // [!code hl]
    owners: config.owners.filter(({ owner }) => !isAddressEqual(owner, departing)), // [!code hl]
    threshold: config.threshold, // [!code hl]
  }, // [!code hl]
})
```

If the remaining weights fall short of the threshold, lower `threshold` in the same update, or [replace the signer](#replace-a-signer-in-one-update) instead. Lowering the threshold to 1 lets any one remaining signer pay and change signers alone, so a 2-of-3 treasury that drops to two signers at threshold 1 no longer needs two approvals. [Replace an approver](/docs/accounts/custodians/company-treasury#replace-an-approver) covers a treasury.

[Access keys](/docs/accounts/access-keys) keep working after the update. A device key or agent key the removed signer authorized keeps paying within its limits, so [revoke every key](/docs/accounts/access-keys/revocation#revoke-after-a-signer-change) its holder could reach, including any an attacker added.

## Replace a signer

Rotate when the holder stays but the key changes: a new hardware wallet, a new device, or a new wallet provider. Put the new key at the old one's weight and keep the threshold, so every group of signers that could approve before still can:

```ts [rotate-signer.ts]
import { isAddressEqual } from 'viem'
import { client } from './client'

const rotation = await client.accounts.updateConfigSync({
  // on a scheduled rotation, the old key can be one of the approvers
  account,
  nextConfig: { // [!code hl]
    owners: config.owners.map((entry) => // [!code hl]
      isAddressEqual(entry.owner, oldSigner) ? { owner: newSigner, weight: entry.weight } : entry, // [!code hl]
    ), // [!code hl]
    threshold: config.threshold, // [!code hl]
  }, // [!code hl]
})
```

Because one update swaps the keys, the account never has both keys active, or neither.

### Lost or compromised signers

When a signer is lost or compromised, the other signers approve the update without it. Tempo has no recovery service or override, so this works only if their weights still reach the threshold. Check that when you create the account, using the rule in [Plan for recovery](/docs/accounts/account-configuration#plan-for-recovery). [Recover a user's account](/docs/accounts/apps/recover-an-account) walks through replacing a lost passkey.

Treat a compromised signer as an attacker and leave it out of the approvers. If its weight reaches the threshold alone, it can remove your other signers first, so give that much weight only to a key you'd trust with the whole account.

## Limits

- An account holds 1 to 48 signers, with total weight at most 255. A transaction carries at most 8 approvals, so the 8 largest weights must reach the threshold. Viem checks these limits before sending and throws `Invalid account config` with the reason. A signer already on the list fails with the reason `owners must be strictly ascending`.
- The approving signers must reach the current threshold, and the new signer list must reach the new one. Viem throws `Local owners do not meet the threshold.` when the attached keys fall short, and `Invalid account config: threshold exceeds total owner weight.` when the new list does.
- `multisig configuration commitment mismatch` means the account was built from a configuration that no longer matches the hash Tempo stores, for example because another configuration update landed first. Load the latest saved configuration and rebuild the update.
- Rebuild with `address: 'infer'` only while the configuration is version 0. After a configuration update, the current signers no longer derive the address, so pass the saved `address`, as [Signing thresholds](/docs/accounts/policies/signing-thresholds#collect-approvals) does.

Specifications: [configuration updates](https://tips.sh/1109), [configurable accounts](https://tips.sh/1107).
