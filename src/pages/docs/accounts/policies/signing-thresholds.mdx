# Signing thresholds

Choose signer weights so that no outside party can pay alone and losing any one signer doesn't lock the account.

A signing threshold is the [account policy](/docs/accounts/policies) that decides who controls a configurable Tempo account. Each signer, a key that approves the account's transactions, has a weight, and a transaction runs only when the signers who approve it reach the threshold in total weight.

:::warning
**Configurable accounts aren't live yet.** Accounts with several signers and a threshold ([TIP-1107](https://tips.sh/1107)) work only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change.
:::

## Signer weights and the threshold

Take a customer account at threshold 2, with a passkey at weight 2, and a backup key and a recovery provider's key at weight 1 each:

```ts [threshold.ts]
import { Account } from 'viem/tempo'

const account = Account.fromConfig({
  address: 'infer', // derive the address from these first signers
  owners: [ // [!code hl]
    { owner: passkey.address, weight: 2 }, // [!code hl]
    { owner: backup.address, weight: 1 }, // [!code hl]
    { owner: recovery.address, weight: 1 }, // [!code hl]
  ], // [!code hl]
  threshold: 2, // [!code hl]
})
```

The passkey approves alone, and the backup and recovery keys approve together. Either of those alone reaches 1 of 2 and can't pay.

Signers approve a whole transaction at once, including every call in a batch. The same threshold covers payments, signer changes, and new [access keys](/docs/accounts/access-keys). Access keys don't count toward it: each pays alone within its limits, and an [admin access key](/docs/accounts/access-keys/admin-access-keys) can also authorize other access keys.

To change signers or the threshold, send a [signer update](/docs/accounts/key-management/signer-updates#add-a-signer), approved at the current threshold.

<span id="what-a-threshold-protects" />

## What a threshold protects against

A signer can be stolen or lost: a key leaks, a phone breaks, an approver leaves. Choose weights that survive both:

- **Theft:** no single party reaches the threshold alone, unless that party is the customer.
- **Loss:** the other signers still reach the threshold without any one of them. [Plan for recovery](/docs/accounts/key-management#plan-for-recovery) gives the rule to check.

Count parties, not keys. Two keys in the same KMS, or a wallet provider's key and a recovery key it also runs, belong to one party, which can approve with their combined weight.

## Recommended signer setups

| Setup | Signers (weight) | Threshold | Who can approve |
| --- | --- | --- | --- |
| [Getting started](/docs/accounts/apps/self-custodial-wallets) | Passkey (1), backup key (1) | 1 | Either one |
| [Customer accounts](/docs/accounts/apps/self-custodial-wallets) | Passkey (2), backup key (1), recovery provider (1) | 2 | The passkey, or both keys |
| [Self-custodial wallets with a provider](/docs/accounts/apps/self-custodial-wallets) | Customer's passkey (1), your wallet provider's key (1), customer's backup key (1) | 2 | Any two: the passkey and the provider day to day, or the customer's two keys without you |
| [Company treasury](/docs/accounts/custodians/company-treasury) | Three approvers (1 each) | 2 | Any two |

<span id="recovery-provider" />

A recovery provider is any party other than the customer and your wallet provider that holds one key to help replace a lost signer, such as a key in your own KMS or a recovery service you contract. Tempo doesn't limit a signer to recovery: any signers that reach the threshold together can also pay and change signers.

Getting started survives a lost passkey, but either key can pay alone, so keep both with the customer and move to customer accounts before balances grow.

## Collect approvals

Each signer's key stays with its holder: the customer's passkey on their device, their backup key in a hardware wallet, and the recovery key with the [recovery provider](#recovery-provider), such as your KMS. No single place holds all three.

Tempo stores only a hash of the account's configuration (its signers, weights, threshold, and version), which it checks approvals against but can't read back. When your app creates the account, save `account.address` and `account.config` with the account record, `saved`, and rebuild the account from that copy whenever signers approve. The examples call that helper `openAccount`. It passes `saved` to `Account.fromConfig` with the approving keys on this device in place of their addresses, and with `address: 'infer'` until the first signer update, then the saved address. [Add a recovery signer](/docs/accounts/apps/self-custodial-wallets) shows it in full.

Rebuild the account from the latest record before each transaction. A signer update raises the configuration's version, and Tempo checks every transaction against the new configuration's hash, so save the `config` that `updateConfigSync` returns. An account built from the old configuration fails with `multisig configuration commitment mismatch`.

When the keys on one device reach the threshold, attach them and send the transaction as usual. Here the customer's passkey reaches the threshold alone, so the payment runs in the customer's browser. `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

::::code-group

```ts [pay.ts]
import { client } from './client'

await client.token.transferSync({ account: openAccount([passkey]), amount, to, token }) // [!code hl]
```


`passkey` is the customer's passkey account, such as `Account.fromWebAuthnP256(credential)`. Viem signs with the attached keys, highest weight first, until their weights reach the threshold. If they fall short, it throws `Local owners do not meet the threshold.` and sends nothing.

### Approvers on separate devices

When no single device holds enough weight, such as when the backup key and the recovery provider's key approve together, your app prepares the transaction once, each approver signs it on their own device, and your app submits it with their approvals:

```ts [approve.ts]
import { Actions } from 'viem/tempo'
import { client } from './client'

// 1. Your app: prepare the payment once, from the account with no keys attached.
const request = await client.prepareTransactionRequest({ // [!code hl]
  account: openAccount([]), // [!code hl]
  calls: [Actions.token.transfer.call({ amount, to, token })], // [!code hl]
}) // [!code hl]

// 2. Each approver signs the same request on their own device: the backup key, then the recovery provider.
const backupApproval = await client.signTransaction({ ...request, account: backup }) // [!code hl]
const recoveryApproval = await client.signTransaction({ ...request, account: recovery }) // [!code hl]

// 3. Your app: submit the same request with the approvals.
const receipt = await client.sendTransactionSync({ ...request, signatures: [backupApproval, recoveryApproval] }) // [!code hl]
```

For a configurable account, `signTransaction` returns the signer's approval rather than a signed transaction. An approval covers the exact transaction, the account, and the configuration version, so send every approver the same `request`, show them what they're approving, such as the recipient and amount, and submit it unchanged. The request contains bigints, so move it between devices in an encoding that keeps them.

Approvals can arrive in any order: Viem sorts them by signer address when it combines them. Submit only the approvals the threshold needs, with none to spare: the passkey's approval alone, or the backup and recovery approvals together. Tempo adds up approvals in order of signer address and rejects the transaction with `excess multisig owner signatures` when an approval comes after the total already reaches the threshold. Too few fail with `multisig signature weight below threshold`.

An approval also covers the transaction's nonce, its place in the account's sequence of transactions. If another transaction from the account lands first, submitting fails with `nonce too low`, so prepare again and collect new approvals. To keep slow approvals valid while the account keeps paying, pass `prepareTransactionRequest` its own `nonceKey`, a random `bigint` from `1n` to `2n ** 256n - 2n` that starts a [separate sequence](/docs/guide/tempo-transaction#concurrent-transactions) for this transaction. The maximum `uint256` selects an [expiring nonce](/docs/guide/tempo-transaction#expiring-nonces) instead.

A signer update works the same way: put `Actions.accounts.updateConfig.call({ currentConfig: saved.config, nextConfig })` in `calls`, collect approvals from the current signers, and once it lands, save `AccountConfig.update(saved.config, nextConfig)` as the account's configuration. That's the same configuration `updateConfigSync` returns. An update voids approvals collected under the old configuration, so collect those again.

## Verify approvals in a contract

A contract checks that an account's signers approved a message with `verifyMultisig` on the [signature verifier](/docs/protocol/tips/tip-1020), a contract built into Tempo at `0x5165300000000000000000000000000000000000`. `verifyMultisig` exists only on the Tempo Accounts devnet; on mainnet and testnet, the call reverts with `UnknownFunctionSelector`.

```solidity [ApprovalCheck.sol]
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface ISignatureVerifier {
    function verifyMultisig(address account, bytes32 hash, bytes calldata signature) external view returns (bool);
}

contract ApprovalCheck {
    ISignatureVerifier constant VERIFIER = ISignatureVerifier(0x5165300000000000000000000000000000000000);

    function isApproved(address account, bytes32 hash, bytes calldata signature) external view returns (bool) {
        return VERIFIER.verifyMultisig(account, hash, signature); // [!code hl]
    }
}
```

`verifyMultisig` checks the account's signers at call time, so approvals from removed signers fail, and an account that hasn't sent a transaction yet verifies against its first signers. It returns `false` when the signers don't match the account, and reverts with `InvalidSignature()` when approvals fall short. Include your chain ID, contract address, and the account in `hash`, so an approval can't be replayed elsewhere.

To check a single access key's signature instead, call `verifyKeychain`, which also works on mainnet and testnet. It accepts only access keys that sign with one key, so a configurable account signing as an access key, such as a team budget, reverts with `InvalidFormat()`.

## Signing threshold limits

| Limit | Value |
| --- | --- |
| Signers per account | 1 to 48 |
| Weight per signer | At least 1 |
| Total weight | Up to 255 |
| Approvals per transaction | Up to 8, so the eight largest weights must reach the threshold |
