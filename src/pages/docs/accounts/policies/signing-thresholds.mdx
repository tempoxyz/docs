# Signing thresholds

A signing threshold decides who controls a Tempo account. Each signer, a key that approves the account's transactions, has a weight, and a transaction runs only when the signers who approve it reach the threshold in total weight. Choose weights so that no outside party can pay alone and losing any one signer doesn't lock the account.

:::warning
**Not live yet.** Signing thresholds ([TIP-1107](https://tips.sh/1107)) run only on Tempo devnet, and behavior may change.
:::

<span id="how-approvals-add-up" />

## Signer weights and the threshold

Take a customer account at threshold 2, with a passkey at weight 2, and a backup key and a recovery provider's key at weight 1 each:

```ts [threshold.ts]
import { Account } from 'viem/tempo'

const account = Account.fromConfig({
  address: 'infer', // derive the address from these first signers
  owners: [
    { owner: passkey.address, weight: 2 },
    { owner: backup.address, weight: 1 },
    { owner: recovery.address, weight: 1 },
  ],
  threshold: 2,
})
```

The passkey approves alone, and the backup and recovery keys approve together. Either of those alone reaches 1 of 2 and can't pay.

Signers approve a whole transaction at once, including every call in a batch. The same threshold covers payments, signer changes, and new [access keys](/docs/accounts/access-keys). Access keys don't count toward it: each pays alone within its limits, and an [admin access key](/docs/accounts/access-keys/admin-access-keys) can also authorize other access keys.

To change signers or the threshold, send a [signer update](/docs/accounts/key-management/add-signers), approved at the current threshold.

<span id="what-a-threshold-protects" />

## What a threshold protects against

A signer can be stolen or lost: a key leaks, a phone breaks, an approver leaves. Choose weights that survive both:

- **Theft:** no single party reaches the threshold alone, unless that party is the customer.
- **Loss:** the other signers still reach the threshold without any one of them. [Plan for recovery](/docs/accounts/key-management#plan-for-recovery) gives the rule to check.

Count parties, not keys. Two keys in the same KMS, or a wallet provider's key and a recovery key it also runs, belong to one party, which can approve with their combined weight.

## Recommended signer setups

| Setup | Signers (weight) | Threshold | Who can approve |
| --- | --- | --- | --- |
| [Getting started](/docs/accounts/guides/users/add-a-recovery-signer) | Passkey (1), backup key (1) | 1 | Either one |
| [Customer accounts](/docs/accounts/guides/users/add-a-recovery-signer#multi-factor-approval) | Passkey (2), backup key (1), recovery provider (1) | 2 | The passkey, or both keys |
| [Embedded wallets](/docs/accounts/guides/users/embed-wallets) | Customer's passkey (2), your wallet provider's key (1), recovery provider (1) | 2 | The customer, or both providers |
| [Company treasury](/docs/accounts/guides/teams/company-treasury) | Three approvers (1 each) | 2 | Any two |

<span id="recovery-provider" />

A recovery provider is any party other than the customer and your wallet provider that holds one key only to help replace a lost signer, such as a key in your own KMS or a recovery service you contract.

Getting started survives a lost passkey, but either key can pay alone, so keep both with the customer and move to customer accounts before balances grow. In customer accounts, a new device, a signer change, or a payment beyond a device key's limits needs the passkey on the customer's device, or both other keys.

## Collect approvals

Each signer's key stays with its holder: the customer's passkey on their device, their backup key in a hardware wallet, and the recovery key with the [recovery provider](#recovery-provider), such as your KMS. No single place holds all three. Tempo stores only a hash of the account's configuration (its signers, weights, threshold, and version), a fingerprint it checks approvals against but can't read back. So when your app creates the account, it saves `account.address` and `account.config` with the account record, and rebuilds the account from that copy whenever signers approve:

```ts [account.ts]
import { type Address, http, isAddressEqual } from 'viem'
import { tempoDevnet } from 'viem/chains'
import { Account, type AccountConfig, createClient } from 'viem/tempo'

export const client = createClient({ chain: tempoDevnet, transport: http() })

/** Rebuilds the account from your app's saved record, with the approving keys on this device attached. */
export function openAccount(
  saved: { address: Address; config: AccountConfig.Config },
  approvers: readonly Account.RootAccount[] = [],
) {
  const { address, config } = saved
  const owners = config.owners.map(({ owner, weight }) => ({
    owner: approvers.find((key) => isAddressEqual(key.address, owner)) ?? owner,
    weight,
  }))
  // Never updated (version 0): the configuration derives the address.
  if (config.version === 0n)
    return Account.fromConfig({ address: 'infer', owners, salt: config.salt, threshold: config.threshold })
  return Account.fromConfig({ ...config, address, owners })
}
```

Rebuild the account from the latest record before each transaction. A signer update raises the configuration's version, and Tempo checks every transaction against the new configuration's hash, so save the `config` that `updateConfigSync` returns. An account built from the old configuration fails with `multisig configuration commitment mismatch`.

When the keys on one device reach the threshold, attach them and send the transaction as usual. The customer's passkey reaches it alone, so this payment runs in the customer's browser:

```ts [pay.ts]
import { client, openAccount } from './account'

await client.token.transferSync({ account: openAccount(saved, [passkey]), amount, to, token })
```

`passkey` is the customer's passkey account, such as `Account.fromWebAuthnP256(credential)`. viem signs with the attached keys, highest weight first, until their weights reach the threshold. If they fall short, it throws `Local owners do not meet the threshold.` and sends nothing.

### Approvers on separate devices

When no single device holds enough weight, such as when the backup key and the recovery provider's key approve together, your app prepares the transaction once, each approver signs it on their own device, and your app submits it with their approvals:

```ts [approve.ts]
import { Actions } from 'viem/tempo'
import { client, openAccount } from './account'

// 1. Your app: prepare the payment once, from the account with no keys attached.
const request = await client.prepareTransactionRequest({
  account: openAccount(saved),
  calls: [Actions.token.transfer.call({ amount, to, token })],
})

// 2. Each approver, on their own device: sign the same request.
const backupApproval = await client.signTransaction({ ...request, account: backup }) // backup key's device
const recoveryApproval = await client.signTransaction({ ...request, account: recovery }) // recovery provider

// 3. Your app: submit the same request with the approvals.
const receipt = await client.sendTransactionSync({ ...request, signatures: [backupApproval, recoveryApproval] })
```

For a configurable account, `signTransaction` returns the signer's approval rather than a signed transaction. An approval covers the exact transaction, the account, and the configuration version, so send every approver the same `request`, show them what they're approving, such as the recipient and amount, and submit it unchanged. The request contains bigints, so move it between devices in an encoding that keeps them.

Approvals can arrive in any order. Submit only the approvals the threshold needs, with none to spare: the passkey's approval alone, or the backup and recovery approvals together. Tempo adds up approvals in order of signer address and rejects the transaction with `excess multisig owner signatures` when an approval comes after the total already reaches the threshold. Too few fail with `multisig signature weight below threshold`.

An approval also covers the transaction's nonce, its place in the account's sequence of transactions. If another transaction from the account lands first, submitting fails with `nonce too low`, so prepare again and collect new approvals. To keep slow approvals valid while the account keeps paying, pass `prepareTransactionRequest` its own `nonceKey`, a random nonzero number that starts a separate sequence for this transaction.

A signer update works the same way: put `Actions.accounts.updateConfig.call({ currentConfig: saved.config, nextConfig })` in `calls`, collect approvals from the current signers, and once it lands, save `AccountConfig.update(saved.config, nextConfig)` as the account's configuration. An update voids approvals collected under the old configuration, so collect those again.

## Verify approvals in a contract

A contract checks that an account's signers approved a message with `verifyMultisig` on the [signature verifier](/docs/protocol/tips/tip-1020), a contract built into Tempo at `0x5165300000000000000000000000000000000000`:

```solidity [ApprovalCheck.sol]
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface ISignatureVerifier {
    function verifyMultisig(address account, bytes32 hash, bytes calldata signature) external view returns (bool);
}

contract ApprovalCheck {
    ISignatureVerifier constant VERIFIER = ISignatureVerifier(0x5165300000000000000000000000000000000000);

    function isApproved(address account, bytes32 hash, bytes calldata signature) external view returns (bool) {
        return VERIFIER.verifyMultisig(account, hash, signature);
    }
}
```

`verifyMultisig` checks the account's signers at call time, so approvals from removed signers fail, and an account that hasn't sent a transaction yet verifies against its first signers. It returns `false` when the signers don't match the account, and reverts with `InvalidSignature()` when approvals fall short. Include your chain ID, contract address, and the account in `hash`, so an approval can't be replayed elsewhere.

To check a single access key's signature instead, call `verifyKeychain`. It accepts only access keys that sign with one key, so a configurable account signing as an access key, such as a team budget, reverts with `InvalidFormat()`.

## Signing threshold limits

| Limit | Value |
| --- | --- |
| Signers per account | 1 to 48 |
| Weight per signer | At least 1 |
| Total weight | Up to 255 |
| Approvals per transaction | Up to 8, so the eight largest weights must reach the threshold |
