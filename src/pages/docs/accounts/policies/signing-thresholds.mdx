# Signing thresholds

A signing threshold decides who controls a Tempo account. Each signer, a key that approves the account's transactions, has a weight, and a transaction runs only when the signers who approve it reach the threshold in total weight. Choose weights so that no outside party can pay alone and losing any one signer doesn't lock the account.

:::warning
**Not live yet.** Signing thresholds ([TIP-1107](https://tips.sh/1107)) run only on Tempo devnet, and behavior may change.
:::

<span id="how-approvals-add-up" />

## Signer weights and the threshold

Take a customer account at threshold 2, with a passkey at weight 2, and a backup key and a recovery provider's key at weight 1 each:

```ts [threshold.ts]
import { Account } from 'viem/tempo'

const account = Account.fromConfig({
  address: 'infer', // derive the address from these first signers
  owners: [
    { owner: passkey.address, weight: 2 },
    { owner: backup.address, weight: 1 },
    { owner: recovery.address, weight: 1 },
  ],
  threshold: 2,
})
```

The passkey approves alone, and the backup and recovery keys approve together. Either of those alone reaches 1 of 2 and can't pay.

Signers approve a whole transaction at once, including every call in a batch. The same threshold covers payments, signer changes, and new [access keys](/docs/accounts/access-keys). Access keys don't count toward it: each pays alone within its limits, and an [admin access key](/docs/accounts/access-keys/admin-access-keys) can also authorize other access keys.

To change signers or the threshold, send a [signer update](/docs/accounts/key-management/add-signers), approved at the current threshold.

<span id="what-a-threshold-protects" />

## What a threshold protects against

A signer can be stolen or lost: a key leaks, a phone breaks, an approver leaves. Choose weights that survive both:

- **Theft:** no single party reaches the threshold alone, unless that party is the customer.
- **Loss:** the other signers still reach the threshold without any one of them. [Plan for recovery](/docs/accounts/key-management#plan-for-recovery) gives the rule to check.

Count parties, not keys. Two keys in the same KMS, or a wallet provider's key and a recovery key it also runs, belong to one party, which can approve with their combined weight.

## Recommended signer setups

| Setup | Signers (weight) | Threshold | Who can approve |
| --- | --- | --- | --- |
| [Getting started](/docs/accounts/guides/users/add-a-recovery-signer) | Passkey (1), backup key (1) | 1 | Either one |
| [Customer accounts](/docs/accounts/guides/users/add-a-recovery-signer#multi-factor-approval) | Passkey (2), backup key (1), recovery provider (1) | 2 | The passkey, or both keys |
| [Embedded wallets](/docs/accounts/guides/users/embed-wallets) | Customer's passkey (2), your wallet provider's key (1), recovery provider (1) | 2 | The customer, or both providers |
| [Company treasury](/docs/accounts/guides/teams/company-treasury) | Three approvers (1 each) | 2 | Any two |

<span id="recovery-provider" />

A recovery provider is any party other than the customer and your wallet provider that holds one key only to help replace a lost signer, such as a key in your own KMS or a recovery service you contract.

Getting started survives a lost passkey, but either key can pay alone, so keep both with the customer and move to customer accounts before balances grow. In customer accounts, a new device, a signer change, or a payment beyond a device key's limits needs the passkey on the customer's device, or both other keys.

## Collect approvals

Signers sign the same transaction hash, so they approve separately, on their own devices, in any order. Your app holds the approvals until their weights reach the threshold, then submits the transaction. In viem, the `Relay.accounts` plugin on a [`withRelay`](https://viem.sh/tempo/transports/withRelay) transport does both, and approving with `owner` requires it:

```ts [client.ts]
import { http } from 'viem'
import { tempoDevnet } from 'viem/chains'
import { createClient, Relay, Store, withRelay } from 'viem/tempo'

export const client = createClient({
  chain: tempoDevnet,
  transport: withRelay(http(), { plugins: [Relay.accounts({ store: Store.memory() })] }),
})
```

`Store.memory()` works in one process. For signers on different devices, give every signer's client the same persistent store, such as one in your backend. With the account above, the backup and recovery keys approve a payment together:

```ts [approve.ts]
// The backup key starts the payment. receipt.status is 'pending' until approvals reach the threshold.
const { receipt } = await client.token.transferSync({ account, amount, to, token, owner: backup })

// The recovery key approves its hash: 2 of 2, so the payment runs.
await client.sendTransactionSync({ account, hash: receipt.transactionHash, owner: recovery })
```

Tempo rejects signatures beyond the threshold. A signer update voids approvals collected under the old signers, so collect them again.

## Verify approvals in a contract

A contract checks that an account's signers approved a message with `verifyMultisig` on the [signature verifier](/docs/protocol/tips/tip-1020), a contract built into Tempo at `0x5165300000000000000000000000000000000000`:

```solidity [ApprovalCheck.sol]
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface ISignatureVerifier {
    function verifyMultisig(address account, bytes32 hash, bytes calldata signature) external view returns (bool);
}

contract ApprovalCheck {
    ISignatureVerifier constant VERIFIER = ISignatureVerifier(0x5165300000000000000000000000000000000000);

    function isApproved(address account, bytes32 hash, bytes calldata signature) external view returns (bool) {
        return VERIFIER.verifyMultisig(account, hash, signature);
    }
}
```

`verifyMultisig` checks the account's signers at call time, so approvals from removed signers fail, and an account that hasn't sent a transaction yet verifies against its first signers. It returns `false` when the signers don't match the account, and reverts with `InvalidSignature()` when approvals fall short. Include your chain ID, contract address, and the account in `hash`, so an approval can't be replayed elsewhere.

To check a single access key's signature instead, call `verifyKeychain`. It accepts only access keys that sign with one key, so a configurable account signing as an access key, such as a team budget, reverts with `InvalidFormat()`.

## Signing threshold limits

| Limit | Value |
| --- | --- |
| Signers per account | 1 to 48 |
| Weight per signer | At least 1 |
| Total weight | Up to 255 |
| Approvals per transaction | Up to 8, so the eight largest weights must reach the threshold |
