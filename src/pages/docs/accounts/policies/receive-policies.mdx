# Receive policies

A receive policy controls which stablecoins an address accepts and who can pay it. A regulated business can use one to accept payments only from verified senders, and an exchange to accept only the stablecoins it lists. A blocked payment doesn't fail: the transaction succeeds, and Tempo holds the funds in `ReceivePolicyGuard`, a system contract, until the recovery authority you choose claims them.

<span id="receive-policies" />
<span id="when-to-configure-a-receive-policy" />

## What a receive policy checks

Each address sets its policy in the [TIP-403](/docs/protocol/tip403/spec) registry, the same registry of allowlists and blocklists that tokens use to restrict transfers. The policy has three parts:

| Part | Decides | Set it to |
| --- | --- | --- |
| Token filter | Which stablecoins the address accepts | Built-in policy `1` (allow all) or `0` (reject all), or a `WHITELIST` or `BLACKLIST` policy of token contract addresses |
| Sender policy | Who can pay the address | The same options, with sender addresses as members |
| Recovery authority | Who can claim held payments | `address(0)` for the payment's sender or minter, the receiver's own address, or another address |

Neither the token filter nor the sender policy can be a `COMPOUND` policy. An address with no receive policy accepts every transfer and mint the token itself allows.

<span id="account-level-receive-policies" />
<span id="understand-receive-policy-behavior" />

## How Tempo enforces receive policies

Every transfer and mint to the address runs three checks, in order:

| Check | If it fails |
| --- | --- |
| The token's own TIP-403 policy | The call reverts and nothing moves. |
| The receiver's token filter | The call succeeds. `ReceivePolicyGuard` holds the funds, with blocked reason `TOKEN_FILTER`. |
| The receiver's sender policy | The call succeeds. `ReceivePolicyGuard` holds the funds, with blocked reason `RECEIVE_POLICY`. |

If all three pass, Tempo credits the receiver.

The sender checked is the `from` address, or the minter for a mint. For a delegated `transferFrom`, that's the token owner, not the spender, and a held payment still spends the spender's allowance.

The checks run on every TIP-20 transfer and mint, including the memo variants and `systemTransferFrom`. Fee deposits and refunds, TIP-20 rewards, and internal balances skip them.

<span id="virtual-address-behavior" />

A payment to a [virtual address](/docs/protocol/tip20/virtual-addresses) is checked against its master address's policy, so set the policy on the master; a virtual address can't set its own. A held payment's receipt belongs to the master and keeps the original `to` for attribution.

<span id="monitor-blocked-receipts" />

### Blocked receipts

A held payment looks like a success: the transaction succeeds and the token emits its usual `Transfer` event (and `Mint` for a mint), but the recipient is `ReceivePolicyGuard` at `0xB10C000000000000000000000000000000000000`, not the receiver. Check the event's recipient before you credit a payment.

The guard records one receipt per held payment. You can't list receipts onchain, so index the guard's events. `TransferBlocked` fires when a payment is held, and its `receipt` field is the encoded receipt you pass to claim or burn it. `ReceiptClaimed` and `ReceiptBurned` fire when a receipt is released or burned.

## Set a receive policy

The steps below set the demo's policy in code on Moderato testnet: accept only AlphaUSD, from any sender, and let the receiver recover held payments. `client` is a Viem client for the receiving account from the [payment client setup](/docs/guide/payments/send-a-payment/examples#payment-client-setup), `receiver` is its address, and `alphaUsd` is `0x20c0000000000000000000000000000000000001`. The CLI examples use the [CLI client](/docs/guide/payments/send-a-payment/examples#cli-client) variables, plus:

```bash [Terminal]
export TIP403_REGISTRY=0x403c000000000000000000000000000000000000
export RECEIVE_POLICY_GUARD=0xB10C000000000000000000000000000000000000
```

<span id="create-or-choose-a-token-filter" />

:::::steps

### Create a token allowlist

Create a `WHITELIST` policy whose only member is AlphaUSD's token contract address:

::::code-group

```ts [Viem]
const { policyId: tokenPolicyId } = await client.policy.createSync({
  type: 'whitelist',
  addresses: [alphaUsd],
})
```

```bash [CLI]
cast send "$TIP403_REGISTRY" \
  'createPolicyWithAccounts(address,uint8,address[])' \
  "$TEMPO_ACCOUNT_ADDRESS" 0 "[$ALPHA_USD]" \
  --tempo.fee-token "$ALPHA_USD" \
  --rpc-url "$TEMPO_RPC_URL" --private-key "$TEMPO_PRIVATE_KEY"
```

```tsx [Wagmi]
import { Hooks } from 'wagmi/tempo'
const { mutate: createFilter, data: filter, isPending, error } = Hooks.policy.useCreateSync()
const createTokenFilter = () => createFilter({
  type: 'whitelist', addresses: [alphaUsd],
})
const tokenPolicyId = filter?.policyId
```

::::

In the CLI, read the new policy ID from `topics[1]` of the `PolicyCreated` log and export it as `TOKEN_POLICY_ID`. The `0` argument is the policy type (whitelist), not built-in policy `0`.

<span id="create-or-choose-a-sender-policy" />
<span id="choose-a-recovery-authority" />

### Set the receive policy

Call `setReceivePolicy` from the receiving account with the sender policy, token filter, and recovery authority, in that order:

::::code-group

```ts [Viem]
await client.receivePolicy.setSync({
  senderPolicyId: 'allow-all',
  tokenPolicyId,
  claimer: 'self',
})
```

```bash [CLI]
cast send "$TIP403_REGISTRY" 'setReceivePolicy(uint64,uint64,address)' \
  1 "$TOKEN_POLICY_ID" "$TEMPO_ACCOUNT_ADDRESS" \
  --tempo.fee-token "$ALPHA_USD" \
  --rpc-url "$TEMPO_RPC_URL" --private-key "$TEMPO_PRIVATE_KEY"
```

```tsx [Wagmi]
import { useWriteContract } from 'wagmi'
import { Abis, Addresses } from 'viem/tempo'
const { writeContract, data: hash, isPending, error } = useWriteContract()
const setPolicy = () => tokenPolicyId !== undefined && writeContract({
  address: Addresses.tip403Registry, abi: Abis.tip403Registry,
  functionName: 'setReceivePolicy', args: [1n, tokenPolicyId, receiver],
})
```

::::

The sender policy here is built-in policy `1` (`'allow-all'` in Viem), so anyone can pay. To limit who can pay, create a sender allowlist the same way as the token allowlist, with sender addresses as members, and pass its ID instead. Viem calls the token filter `tokenPolicyId` and the recovery authority `claimer`: `'self'` is the signing account, `'sender'` is `address(0)`, or pass another address.

Changing the recovery authority affects only payments held afterward; existing receipts keep the authority they were held under. A recovery authority other than `address(0)` can't be `ReceivePolicyGuard`, a virtual address, or a system precompile that can't initiate calls.

:::::

## Check a payment before sending

Ask whether the receiver's policy accepts a token from a sender. `sender` is the paying address (`TEMPO_SENDER` in the CLI):

::::code-group

```ts [Viem]
const { authorized, blockedReason } = await client.receivePolicy.validate({
  token: alphaUsd, sender, receiver,
})
```

```bash [CLI]
cast call "$TIP403_REGISTRY" \
  'validateReceivePolicy(address,address,address)(bool,uint8)' \
  "$ALPHA_USD" "$TEMPO_SENDER" "$TEMPO_ACCOUNT_ADDRESS" \
  --rpc-url "$TEMPO_RPC_URL"
```

```tsx [Wagmi]
import { useReadContract } from 'wagmi'
import { Abis, Addresses } from 'viem/tempo'
const { data: validation } = useReadContract({
  address: Addresses.tip403Registry, abi: Abis.tip403Registry,
  functionName: 'validateReceivePolicy', args: [alphaUsd, sender, receiver],
})
```

::::

The answer covers only the receive policy, not the token's own policy, the sender's balance, or the rest of the transaction. The policy can also change before the payment executes, so still check where the confirmed payment landed.

<span id="claim-blocked-receipts" />

## Claim a held payment

The recovery authority claims a held payment by passing a destination and the `receipt` bytes from its `TransferBlocked` event (`blockedReceipt`, or `BLOCKED_RECEIPT` in the CLI). Here the receiver claims the payment to itself:

::::code-group

```ts [Viem]
await client.receivePolicy.claimSync({ to: receiver, receipt: blockedReceipt })
```

```bash [CLI]
cast send "$RECEIVE_POLICY_GUARD" \
  'claim(address,bytes)' "$TEMPO_ACCOUNT_ADDRESS" "$BLOCKED_RECEIPT" \
  --tempo.fee-token "$ALPHA_USD" \
  --rpc-url "$TEMPO_RPC_URL" --private-key "$TEMPO_PRIVATE_KEY"
```

```tsx [Wagmi]
import { useWriteContract } from 'wagmi'
import { Abis, Addresses } from 'viem/tempo'
const { writeContract, data: hash, isPending, error } = useWriteContract()
const claimPayment = () => writeContract({
  address: Addresses.receivePolicyGuard, abi: Abis.receivePolicyGuard,
  functionName: 'claim', args: [receiver, blockedReceipt],
})
```

::::

A claim releases the receipt's full amount; partial claims aren't supported. When a recovery authority other than `address(0)` claims back to the receiver, the payment completes under the token's own policy without rechecking the receive policy, so claim only payments your application has approved. Every other claim, including any claim under an `address(0)` recovery authority, is a reroute with extra checks; see the [claim rules](/docs/protocol/tip403/receive-policies#claims).

<span id="burn-blocked-receipts" />
<span id="receive-policy-limits" />

The token's issuer can instead burn a held payment by calling `burnBlockedReceipt` from an account with the token's `BURN_BLOCKED_ROLE`, but only while the token's own policy bars the receipt's subject from sending. The subject is the payment's sender or minter under an `address(0)` recovery authority, and the receiver otherwise.

<span id="learn-more-about-receive-policies" />

For every claim and burn rule, see [TIP-403 receive policies](/docs/protocol/tip403/receive-policies) and the [TIP-1028 specification](https://tips.sh/1028).
