# Add signers

Adding a signer, a key that approves the account's transactions, backs up a key you could lose or lets another person approve. The current signers approve the addition in one signer update, and the address, balance, token approvals, and access keys stay the same. Signer updates run only on the Tempo Accounts devnet.

<span id="what-adding-a-signer-does" />

## Choose the new signer's weight

The weight you give the new signer decides what it can approve alone. Every signer has a weight of at least 1, and the signers who approve a payment or a signer update need weights that reach the account's threshold:

- Below the threshold, the new signer approves only together with others, so no single backup or recovery signer controls the account.
- At or above the threshold, it approves anything alone, including removing every other signer. Give this weight only to a key you'd trust with the whole account.

The threshold stays the same unless you change it, so each new signer adds a way to reach it. To keep requiring the same approvers, raise the threshold in the same update. [Signing thresholds](/docs/accounts/policies/signing-thresholds#recommended-signer-setups) lists recommended setups.

## Add a recovery signer

A recovery signer lets the remaining signers replace a lost one. Give it enough weight that the account can [lose any one signer](/docs/accounts/key-management#plan-for-recovery) and still reach the threshold, and no more, because it can approve payments at that weight too. [Add a recovery signer](/docs/accounts/guides/users/add-a-recovery-signer) walks through it in a live demo.

## Send the signer update

A signer update replaces the account's whole signer list. Tempo stores only a hash of the configuration (signers, weights, threshold, salt, and version), a fingerprint it checks approvals against but can't read back. Your app saves the account's address and configuration with the account record and builds every approval from that copy.

Each signer's key stays with whoever holds it. To send the update, rebuild the account from the saved record with the approving signers' keys attached, and append the new signer. `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

```ts [client.ts]
// [!include ~/snippets/accounts-devnet.ts:client]
```

```ts [add-signer.ts]
import { isAddressEqual } from 'viem'
import { Account } from 'viem/tempo'
import { client } from './client'

const { address, config } = await loadAccount(customerId) // your app's storage

// Attach the approving signers' keys. The other signers stay addresses.
const owners = config.owners.map(({ owner, weight }) => ({
  owner: approvers.find((key) => isAddressEqual(key.address, owner)) ?? owner,
  weight,
}))
const account =
  config.version === 0n // never updated: the first signers derive the address
    ? Account.fromConfig({ address: 'infer', owners, salt: config.salt, threshold: config.threshold })
    : Account.fromConfig({ ...config, address, owners })

const { config: updated } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [...config.owners, { owner: newSigner, weight: 1 }],
    threshold: config.threshold,
  },
})
await saveAccount(customerId, { address, config: updated }) // the next action rebuilds from this
```

`approvers` holds the keys of current signers on the device running the code, such as the customer's passkey in their browser, which approves alone in the [recommended customer setups](/docs/accounts/policies/signing-thresholds#recommended-signer-setups). viem signs with them, highest weight first, until their weights reach the threshold. `newSigner` is the new key's address: a passkey, a device key, a key in a KMS or hardware wallet, or an address from a recovery provider. viem sorts the signers by address, as Tempo requires.

Before every payment or signer update, rebuild the account from the latest saved record instead of reusing an account object your code kept in memory. The update raises the version by one, so an account built from the old configuration no longer matches the hash Tempo stores, and its next transaction fails. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

## Limits on adding signers

- An account holds 1 to 48 signers, with total weight at most 255. A transaction carries at most 8 approvals, so the 8 largest weights must reach the threshold. viem checks these limits before sending and throws `Invalid account config` with the reason. A signer already on the list fails with the reason `owners must be strictly ascending`.
- The approving signers must reach the current threshold without the new signer. If the attached keys fall short, viem throws `Local owners do not meet the threshold.` and sends nothing.
- `multisig configuration commitment mismatch` means the account was built from a configuration that no longer matches the hash Tempo stores, for example because another signer update landed after you loaded it. Load the latest saved configuration and rebuild the update.
- `address: 'infer'` derives the address from the first configuration, so it works only before the first update. After a signer change, build the account from its saved address, as the code does.
- Tempo can't tell whether a signer still holds its key. Have each new signer approve once before you rely on it.

Specification: [configuration updates](https://tips.sh/1109).
