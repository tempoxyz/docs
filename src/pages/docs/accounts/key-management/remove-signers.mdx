# Remove signers

Removing a signer ends its power to approve when an approver leaves or a key is lost or compromised.

Removing a signer from a configurable account is a [signer update](/docs/accounts/key-management#every-change-is-one-signer-update): the signers that stay approve a new signer list without the removed one, and the account keeps its address, balance, and token approvals. To rotate a key, the same update puts the new key in the old one's place.

:::warning
**Configurable accounts aren't live yet.** Accounts with several signers and a threshold ([TIP-1107](https://tips.sh/1107)) work only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change. Removing, rotating, and replacing signers all need one.
:::

## What removing a signer stops

Once the update lands, the removed signer can't approve anything, and approvals collected under the old signer list stop counting.

<span id="revoke-what-the-old-signer-authorized" />

[Access keys](/docs/accounts/access-keys) keep working. A device key or agent key the removed signer authorized keeps paying within its limits, so after the update, [revoke every key](/docs/accounts/access-keys/revocation#revoke-after-a-signer-change) its holder could reach, including any an attacker added.

## Remove a signer

Each signer's key stays with whoever holds it, and Tempo stores only a hash of the account's configuration: its signers, weights, threshold, salt, and version. Your app rebuilds the account from the address and configuration it last saved, with the approving signers' keys attached, as in [Signing thresholds](/docs/accounts/policies/signing-thresholds#collect-approvals). Drop the departing signer's entry and send the update. `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

::::code-group

```ts [remove-signer.ts]
import { isAddressEqual } from 'viem'
import { client } from './client'

const { config: updated } = await client.accounts.updateConfigSync({
  account,
  nextConfig: { // [!code hl]
    owners: config.owners.filter(({ owner }) => !isAddressEqual(owner, departing)), // [!code hl]
    threshold: config.threshold, // [!code hl]
  }, // [!code hl]
})
```

```ts [client.ts]
// [!include ~/snippets/accounts-devnet.ts:client]
```

::::

`account` is the rebuilt account, and `config` is the saved configuration it came from. Attach the keys, on the device running the code, of signers that stay and approve the removal, such as the customer's passkey in their browser. viem signs with them, highest weight first, until their weights reach the current threshold. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

Save the configuration the update returns, and rebuild from it before the next action. The update raises the configuration's version by one, so an account built from the old copy no longer matches the hash Tempo stores, and its next payment or update fails.

If the remaining weights fall short of the threshold, lower `threshold` in the same update, or add a replacement signer in it instead. Lowering the threshold to 1 lets any one remaining signer pay and change signers alone, so a 2-of-3 treasury that drops to two signers at threshold 1 no longer needs two approvals. [Offboard an approver](/docs/accounts/guides/teams/offboard-an-approver) walks through removing one from a treasury.

## Rotate a key by replacing it in one update

Rotate when the holder stays but the key changes: a new hardware wallet, a new device, or a new wallet provider. Rebuild the account as above, then put the new key at the old one's weight and keep the threshold, so every group of signers that could approve before still can:

```ts [rotate-signer.ts]
const rotation = await client.accounts.updateConfigSync({
  // on a scheduled rotation, the old key can be one of the approvers
  account,
  nextConfig: { // [!code hl]
    owners: config.owners.map((entry) => // [!code hl]
      isAddressEqual(entry.owner, oldSigner) ? { owner: newSigner, weight: entry.weight } : entry, // [!code hl]
    ), // [!code hl]
    threshold: config.threshold, // [!code hl]
  }, // [!code hl]
})
```

Save `rotation.config` with the account record, as after a removal. Because one update swaps the keys, the account never has both keys active, or neither.

## Remove a lost or compromised signer

When a signer is lost or compromised, the other signers approve the update without it. Tempo has no recovery service or override, so this works only if their weights still reach the threshold. Check that when you create the account, using the rule in [Plan for recovery](/docs/accounts/key-management#plan-for-recovery).

For example, with a passkey at weight 2 plus a backup key and a recovery provider's key at weight 1 each, at threshold 2, the two keys together approve the [rotation](#rotate-a-key-by-replacing-it-in-one-update) that swaps in a new passkey after the customer loses their phone. [Recover a user's account](/docs/accounts/guides/users/recover-an-account) walks through it.

Treat a compromised signer as an attacker and leave it out of the approvers. If its weight reaches the threshold alone, it can remove your other signers first, so give that much weight only to a key you'd trust with the whole account.

## Limits on removing signers

- The approving signers must reach the current threshold, and the remaining weights must reach the new one. viem checks both before sending anything: it throws `Local owners do not meet the threshold.` when the attached keys fall short, and `Invalid account config: threshold exceeds total owner weight.` when the remaining weights do.
- An account keeps at least one signer.
- `multisig configuration commitment mismatch` means the account was rebuilt from an older configuration than the one Tempo stores, for example because another signer update landed first. Load the latest saved configuration and rebuild the account.
- Rebuild with `address: 'infer'` only while the configuration is version 0. After a signer update, the current signers no longer derive the address, so pass the saved `address`, as [Signing thresholds](/docs/accounts/policies/signing-thresholds#collect-approvals) does.

Specifications: [configuration updates](https://tips.sh/1109), [configurable accounts](https://tips.sh/1107).
