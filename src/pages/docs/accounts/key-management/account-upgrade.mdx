# Account upgrade

An account upgrade adds backup signers to a single-key account without changing its address.

A single-key account works like a standard Ethereum account (an EOA): one key controls it, so losing that key loses the account. An account upgrade turns it into a configurable account with several signers and a threshold at the same address, so a lost key no longer means a lost account. The upgrade is permanent.

:::warning
**Account upgrades aren't live yet.** Turning a single-key account into a configurable account at the same address ([TIP-1113](https://tips.sh/1113)) works only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change. Sent on mainnet or testnet, the upgrade transaction succeeds and charges its fee but changes nothing: the original key still approves alone, and transactions from the configurable account are rejected.
:::

## What an upgrade changes

The upgrade gives the account a list of signers, each with a weight, and a threshold: the total weight an approval needs. From then on, signers whose weights reach the threshold approve for the account. The original key approves only if you list it, at its weight. The address, balances, token approvals, nonce, contract storage, and access keys with their limits stay the same.

The original key isn't fully retired: contracts that verify signatures themselves, such as Permit2, may still accept it, and it still controls the address on other EVM chains.

## Choose signers and threshold

List the original key and at least one backup signer, such as a passkey on the user's device or a key your recovery provider holds. With both at weight 1 and threshold 1, either key can pay alone and replace the other if it's lost. To require two approvals per payment, use threshold 2 with three signers at weight 1. Whatever you choose, the signers left after losing any one must still reach the threshold ([Plan for recovery](/docs/accounts/key-management#plan-for-recovery)).

Access keys carry over with their limits, so [revoke](/docs/accounts/access-keys/revocation) any you don't want before you upgrade.

## Send the upgrade

The original key signs one transaction whose only call is `upgradeAccount(threshold, owners)` on Tempo's built-in multisig contract. Call it with `writeContractSync`, and stop unless the client is on the devnet. Set `feeToken` to the stablecoin that pays the fee: without it, Viem sends a standard Ethereum transaction and the upgrade reverts with `PrimitiveRootRequired`. `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

::::code-group

```ts [upgrade.ts]
import { parseAbi } from 'viem'
import { tempoDevnet } from 'viem/chains'
import { Addresses } from 'viem/tempo'
import { client } from './client'

// Mainnet and testnet accept the transaction but don't upgrade the account.
if (client.chain.id !== tempoDevnet.id) throw new Error('Account upgrades run only on the Tempo Accounts devnet.') // [!code hl]

// A test stablecoin on the devnet
const token = '0x20c0000000000000000000000000000000000001'

await client.writeContractSync({ // [!code hl]
  account: original, // [!code hl]
  address: Addresses.nativeMultisig, // [!code hl]
  abi: parseAbi([ // [!code hl]
    'function upgradeAccount(uint8 threshold, (address owner, uint8 weight)[] owners) returns (bytes32)', // [!code hl]
  ]), // [!code hl]
  functionName: 'upgradeAccount', // [!code hl]
  args: [threshold, owners], // [!code hl]
  feeToken: token, // [!code hl]
}) // [!code hl]
```

`original` is the key that controls the account today, such as `Account.fromSecp256k1(privateKey)`. `owners` and `threshold` come from the upgraded account's configuration. Build it with [`Account.fromConfig`](https://viem.sh/tempo/accounts/account.fromConfig) at `original.address`, with `version: 1n` and the salt Tempo derives from the address, `keccak256(concat([toHex('tempo:multisig:upgrade'), original.address]))`, then read `account.config`, which lists the signers sorted by address, as Tempo requires. List `original` as an owner so it can approve, and the backup signer by its address. Its key stays on the user's device or with your recovery provider, and only the address goes in the configuration. [Migrate existing wallets](/docs/accounts/guides/users/migrate-existing-wallets#save-the-configuration) shows saving that configuration.

After the upgrade, the record your app saves is the account's only readable list of signers ([keep the current configuration](/docs/development/configurable-accounts#keep-the-current-configuration)). Whenever your app acts for the account later, rebuild it from that record with `Account.fromConfig` and attach the keys that approve, such as `original`. The other signers stay as addresses. Viem signs with the attached keys until their weights reach the threshold; if they fall short, it throws `Local owners do not meet the threshold.` and sends nothing. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

[Adding](/docs/accounts/key-management/add-signers) or [removing](/docs/accounts/key-management/remove-signers) signers later raises the version: save the `config` that `updateConfigSync` returns and rebuild the account from it, or the next transaction fails with `multisig configuration commitment mismatch`. To upgrade every user's account, follow [Migrate existing wallets](/docs/accounts/guides/users/migrate-existing-wallets).

## Account upgrade limits

- Only the original key can sign the upgrade. Access keys can't, but a [fee payer](/docs/accounts/fees/fee-sponsorship) can sponsor it.
- The upgrade must be the transaction's only call, with no `keyAuthorization` and no EIP-7702 authorization list.
- Accounts with contract code, an EIP-7702 delegation, or existing signers can't upgrade.
- Afterward, a direct signature from the original key fails with `RootKeyRetired` (`primitive root key retired`). Sign with the account rebuilt from the saved configuration instead.
- Upgraded accounts don't use the [recovery factory](/docs/accounts/key-management#recover-funds-sent-on-another-chain) for funds sent to their address on another chain. The original key still controls the address there.
