# Account upgrade

:::warning
**Not live yet.** Account upgrade ([TIP-1113](https://tips.sh/1113)) is in early development and runs only on Tempo devnet. We're seeking feedback; behavior may change.
:::

An account upgrade turns a single-key (EOA) account into a configurable account at the same address, so losing the key no longer loses the account. It's permanent, only the original key can sign it, and it gives up cross-chain recovery.

## What an upgrade changes

A single-key account, like an Ethereum EOA, has no other signer to approve a [signer rotation](/docs/accounts/key-management/remove-signers): if its key is lost, so is the account. The upgrade installs a list of signers and a threshold on the account, and from then on Tempo checks every approval against them.

| Changes | Stays the same |
| --- | --- |
| The account approves with signers whose weights reach a threshold | Address |
| The original key approves only if it's listed as a signer, at its weight | Balances and token approvals |
| Signer updates become possible, starting from configuration version 1 | Nonce and contract storage |
| Cross-chain recovery is unavailable | Access keys and their limits |

Contracts that check signatures themselves, such as Permit2, may still accept the original key, and on other EVM chains the original key still controls the address.

## Choose signers and threshold

List the original key alongside at least one backup signer, such as a passkey or a recovery key. With both at weight 1 and threshold 1, either key can replace the other later, and either can also pay alone. To require both for payments, use threshold 2 and add a third signer so the account can still lose one. [Plan for recovery](/docs/accounts/key-management#plan-for-recovery) gives the rule to check.

Before you upgrade, [revoke the access keys](/docs/accounts/access-keys/revocation) you don't want. The upgrade keeps every access key and its limits.

## Send the upgrade

The original key calls `upgradeAccount(threshold, owners)` on the native multisig precompile, as the transaction's only call. viem 2.57.5 has no upgrade action, so call the precompile with `writeContractSync`:

```ts [upgrade.ts]
import { parseAbi } from 'viem'
import { Account, AccountConfig, Addresses } from 'viem/tempo'

const original = Account.fromSecp256k1(process.env.ACCOUNT_KEY as `0x${string}`)
const { owners, threshold } = AccountConfig.from({
  owners: [
    { owner: original.address, weight: 1 },
    { owner: passkeyAddress, weight: 1 }, // the backup signer
  ],
  threshold: 1,
})

await client.writeContractSync({
  account: original,
  address: Addresses.nativeMultisig,
  abi: parseAbi([
    'function upgradeAccount(uint8 threshold, (address owner, uint8 weight)[] owners) returns (bytes32)',
  ]),
  functionName: 'upgradeAccount',
  args: [threshold, owners],
})
```

`AccountConfig.from` sorts the signers by address, as Tempo requires. After the upgrade, open the account with `Account.fromConfig` and its version-1 configuration, since every approval carries it. From then on, [rotate](/docs/accounts/key-management/remove-signers) and [recover](/docs/accounts/key-management/remove-signers) signers like any configurable account. [Upgrade an existing account](/docs/accounts/key-management/account-upgrade) runs the full flow in a live demo, including saving the configuration.

## Account upgrade limits

- Only the original secp256k1 key or passkey signs the upgrade. Access keys can't. A fee payer can sponsor it.
- The upgrade must be the transaction's only call, with no `keyAuthorization` or authorization list.
- Accounts with contract code, an EIP-7702 delegation, or existing signers can't upgrade.
- The upgrade is permanent. Afterward, the original key approves only as a listed signer: a direct signature fails with `RootKeyRetired`.
- Upgraded accounts can't use [cross-chain recovery](/docs/accounts/key-management#recover-funds-sent-on-another-chain).
