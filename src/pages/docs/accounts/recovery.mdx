# Key rotation

Rotating a key, replacing a lost passkey, and recovering from a compromised key are one operation: a signer update. The account's remaining signers approve a new list of signers and a threshold, and the address, balances, and history stay the same. Tempo has no override, so the approving signers must reach the current threshold, without the key you're replacing when it's lost or compromised.

## Key rotation by situation

The situation decides which signer changes and who approves the update.

| Situation | Change | Approved by | Walkthrough |
| --- | --- | --- | --- |
| Lost phone or passkey | Swap the lost passkey for a new one, and revoke the phone's access keys | The remaining signers, such as a backup key and a recovery key | [Recover from a lost passkey](/docs/accounts/guides/self-custody#recover-from-a-lost-passkey) |
| Scheduled key rotation | Swap a KMS, hardware, or provider key at the same weight | The current signers, including the old key | [Rotate an approver's key](/docs/accounts/guides/company-treasury#rotate-an-approvers-key) |
| Compromised key | Swap or remove it, and revoke the access keys it could reach | The other signers, without it | [Rotate an approver's key](/docs/accounts/guides/company-treasury#rotate-an-approvers-key) |
| Departing approver | Remove their signer, and lower the threshold if needed | The remaining approvers | [Remove a departing approver](/docs/accounts/guides/company-treasury#remove-a-departing-approver) |
| Single-key account with no backup | [Upgrade it](#make-a-single-key-account-recoverable) to a configurable account with a backup signer | The original key | [Upgrade an existing account](/docs/accounts/create#upgrade-an-existing-account) |
| Customer leaves your app | Swap your app's signers for the customer's | Your app's signers | [Hand off to a self-custodial wallet](/docs/accounts/guides/self-custody#hand-off-to-a-self-custodial-wallet) |

## Replace a signer

A replacement swaps one entry in the signer list for a new key at the same weight and keeps the threshold. The approval rules don't change: any combination of signers that could approve before can approve after, with the new key in the old one's place.

```ts [replace-signer.ts]
import { isAddressEqual } from 'viem'
import { Account } from 'viem/tempo'

const account = Account.fromConfig(address) // the account's saved address
const config = await client.accounts.getConfig({ address: account.address })
if (!config) throw new Error('The relay has no configuration for this account.')
const { owners, threshold } = config

const { receipt } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: owners.map((entry) =>
      isAddressEqual(entry.owner, oldSigner) ? { owner: newSigner, weight: entry.weight } : entry,
    ),
    threshold,
  },
  owner: remainingSigner,
})

// A second signer approves the same update when the first can't reach the threshold alone.
await client.sendTransactionSync({ account, hash: receipt.transactionHash, owner: secondSigner })
```

`getConfig` reads the current signers from a relay that runs `Relay.accounts`, so the client's transport must be that relay. It returns `null` when the relay doesn't have the account's configuration. Once the update lands, the old signer can't approve, and approvals collected for the old configuration are void.

Removing a signer is the same update with its entry dropped. The remaining weights must still reach the threshold, or Tempo rejects the update.

## Revoke access keys

Signer updates don't touch access keys. A device key on a lost phone, or a backend key a departing approver set up, keeps paying within its limits until you revoke it, so revoke each key the old holder could use as part of the same recovery:

```ts [revoke.ts]
await client.accessKey.revokeSync({ accessKey: lostDeviceKey, account })
```

Revocation is permanent: a revoked key can't be authorized again, so authorize a new one instead. When you hand an account to a customer, revoke your app's access keys before you swap out your app's signers, since your app can't approve anything afterward. See [Revoke an access key](/docs/accounts/access-keys#revoke-an-access-key).

## Plan for recovery

Recovery works only when the account can lose any one signer and still reach the threshold with the rest. Set this up when you create the account: after a key is lost, only the remaining signers can change the configuration.

For example, give a passkey weight 2, and a backup key and a recovery provider's key weight 1 each, at threshold 2. The passkey replaces a lost key alone, and the two keys together replace a lost passkey.

The rule to check: for every signer, the total weight minus that signer's weight must be at least the threshold. [Recommended signer setups](/docs/accounts/security-policies#recommended-signer-setups) lists configurations that pass, and [Add a backup signer](/docs/accounts/guides/self-custody#add-a-backup-signer) adds one to an existing account.

## Make a single-key account recoverable

A single-key account, like an Ethereum EOA, has no other signer to approve an update: losing its key loses the account. Upgrade it in place to a configurable account that lists the original key and a backup signer, such as a passkey or a recovery key. The address, balances, token approvals, and access keys stay the same.

Only the original key signs the upgrade, and the upgrade must be the transaction's only call. It's permanent. With both keys at weight 1 and threshold 1, either key can replace the other afterward, and either can also pay alone. [Upgrade an existing account](/docs/accounts/create#upgrade-an-existing-account) walks through it with a live demo.

## Recover funds sent on another chain

The address is the same on every EVM chain. On supported chains, the account's initial secp256k1 signers that reach the original threshold can recover funds sent there by mistake, even after you remove them on Tempo. Passkeys and device keys don't count, so accounts created with only passkeys and device keys, and accounts [upgraded in place](/docs/accounts/create#upgrade-an-existing-account), can't recover funds this way.

## Key rotation limits

- The remaining signers must reach the threshold. Tempo can't recover an account whose signers can't.
- `InvalidConfig` means another signer update landed first. Read the signers again and rebuild the update.
- After a signer change, `address: 'infer'` derives a different address. Open the account with `Account.fromConfig(address)`.
- Tempo can't tell whether a signer still holds its key. Have each new signer approve once before you rely on it.
- Recovery signers can also approve payments at their weight. Keep each one below the threshold on its own.

Specification: [configurable accounts](https://tips.sh/1107).
