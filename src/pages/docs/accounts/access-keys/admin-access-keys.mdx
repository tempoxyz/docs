# Admin Access Keys

Before T14, manages an account's other access keys without the signers approving each change.

<AdminAccessKeysT14 />

## Overview

Before [T14](/docs/protocol/upgrades/t14), an admin access key is the only kind of [access key](/docs/accounts/access-keys) that can authorize, change, and revoke keys. A customer's trusted device can add their new phone, or your key-management service can rotate keys.

Unlike a limited key, an admin key has no spending limit, expiry, or scopes. Whoever holds it can spend the whole balance.

From T14, no account can authorize an admin key, and only the account's own key, or its signers on a configurable account, manage access keys. A key stored as admin before T14 becomes a regular access key with no spending limit, expiry, or scopes. It keeps signing payments but manages nothing.

## Permissions

Before T14, an admin key can:

- Authorize any access key, including another admin key.
- Change a limited key's [spending limit](/docs/accounts/access-keys/spending-limits) or [scopes](/docs/accounts/access-keys/scopes).
- [Revoke](/docs/accounts/access-keys/revocation) any access key, including itself.
- Approve a message that a contract checks with [`verifyKeychainAdmin`](/docs/sdk/foundry/signature-verifier#how-signature-verification-works-in-foundry).

An admin key isn't a signer. It can't change the signers or the threshold, or lock the signers out. A key-management call from a limited key reverts with [`UnauthorizedCaller`](/docs/protocol/transactions/AccountKeychain#error-unauthorizedcaller). From T14, so does one from an admin key, and `verifyKeychainAdmin` accepts only the account's own key on an account without signers.

## Use Cases

Give an admin key only to a party you'd trust with the whole balance. On a configurable account, it pays without reaching the [signing threshold](/docs/accounts/policies/signing-thresholds), which removes the protection of requiring several signers. That stays true after T14 and after an [account upgrade](/docs/accounts/account-configuration/account-upgrade), on every network, until the key is revoked or restricted. Nothing migrates these keys automatically, so find the ones your accounts hold and clean them up ([T14 changes](#t14-changes)).

| Holder | Key |
| --- | --- |
| A customer's trusted device, or your key-management service | Admin key until T14, then a [signer](/docs/accounts/account-configuration/configuration-updates#add-a-signer) |
| An [AI agent](/docs/accounts/automations/give-an-agent-a-wallet) | Limited key |
| A [backend that pays out](/docs/accounts/automations/pay-out-from-a-backend) | Limited key |
| A [card program](/docs/accounts/automations/pay-from-an-embedded-wallet) | Limited key |

Protect an admin key like a signer. Keep it in a KMS or HSM, or as a [device key](/docs/accounts/authentication/device-keys) that can't be exported. A leaked admin key compromises the account. Before T14, its holder can authorize a new admin key before you revoke the leaked one.

## Authorize an Admin Access Key

Before T14, enough signers to reach the threshold, or an existing admin key, authorize it like any [access key](/docs/accounts/access-keys#authorize-an-access-key). Pass `admin: true` to Viem's [`accessKey.authorize`](https://viem.sh/tempo/actions/accessKey.authorize). Viem ignores `limits`, `expiry`, and `scopes` on an admin key. Tempo rejects an admin authorization that carries any of them. Check a key with [`accessKey.isAdmin`](https://viem.sh/tempo/actions/accessKey.isAdmin).

From T14, `authorizeAdminKey` reverts with `UnknownFunctionSelector`, and a key authorization with `admin: true` is invalid.

<span id="admin-access-key-limits" />

## Limits

- Before T14, changing an admin key's spending limit or scopes reverts with [`InvalidKeyId`](/docs/protocol/transactions/AccountKeychain#error-invalidkeyid), because it has neither. To bound its holder, revoke it and authorize a new limited key.
- Revoking an admin key leaves the keys it authorized in place, so revoke each one separately.

<span id="t14-changes" />

## T14 Changes

At T14, Tempo doesn't revoke or migrate keys stored as admin. Each one keeps paying from the account with no spending limit, expiry, or scopes. To clean one up, the account's own key, or the signers of a configurable account, either:

- Restrict it with [`updateSpendingLimit`](/docs/accounts/access-keys/spending-limits) and [`setAllowedCalls`](/docs/accounts/access-keys/scopes#change-allowed-calls).
- [Revoke](/docs/accounts/access-keys/revocation) it, then authorize a limited key, or add the device as a [signer](/docs/accounts/account-configuration/configuration-updates#add-a-signer).

The key itself can no longer make these calls. `isAdminKey` returns `false` for it, so contracts that check it stop accepting the key.

Specification: [Account Keychain admin keys](/docs/protocol/transactions/AccountKeychain#admin-key-authorization).
