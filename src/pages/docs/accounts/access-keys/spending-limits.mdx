# Spending limits

A spending limit caps how much of one TIP-20 token an access key can spend, such as 500 OUSD a day.

Spending limits are one of an [access key](/docs/accounts/access-keys)'s three bounds, with [expiry](/docs/accounts/access-keys/expiry) and [scopes](/docs/accounts/access-keys/scopes). Tempo reverts any transaction that would take the key over its limit, which is either one-time or renews each period. A limit caps how much, not where: scopes decide where the money goes.

## Set a spending limit

Pass `limits` when you [authorize the key](/docs/accounts/access-keys#authorize-an-access-key) with viem's [`accessKey.authorize`](https://viem.sh/tempo/actions/accessKey.authorize) or [`accessKey.signAuthorization`](https://viem.sh/tempo/actions/accessKey.signAuthorization). Each entry covers one token, with the amount in base units (most USD stablecoins have 6 decimals). For example, `{ token: stablecoin, limit: parseUnits('500', 6), period: 86_400 }` allows 500 OUSD a day. A key without `limits` can spend any amount.

`period` decides whether the limit renews:

- `0` or omitted: one-time. Once the key spends it, the key can't spend that token again.
- A number of seconds, such as `86_400` for a day: renewing. The limit resets to its full amount when each period ends.

## What counts against the limit

In a transaction the key signs, each of these counts against the limit for its token:

- Transfers the key sends
- Approval increases, so the key can't let a contract pull more than its limit
- Fees the account pays, unless a [fee payer](/docs/accounts/fees/fee-sponsorship) sponsors them
- Tokens that Tempo's built-in contracts (precompiles) pull from the account
- Since T12, tokens burned from the account with `burnAt`

Assets other than TIP-20 tokens, such as NFTs, don't count, and neither does a `transferFrom` that spends an allowance the account already granted. A transaction that would go over the remaining limit reverts entirely with [`SpendingLimitExceeded`](/docs/protocol/transactions/AccountKeychain#error-spendinglimitexceeded).

## Read the remaining limit

Read what a key can still spend with viem's [`accessKey.getRemainingLimit`](https://viem.sh/tempo/actions/accessKey.getRemainingLimit). It returns `remaining` and `periodEnd`.

`remaining` is what the key can spend now, and it reads as the full limit once a period ends. `periodEnd` is when the current period ends, as a Unix timestamp, or `0` for a one-time limit. A missing, revoked, or expired key reads as zero.

Each payment an access key signs emits an `AccessKeySpend` event with the amount spent and the limit left, both in base units, so the indexer shows the spend history behind one key; replace the account and key addresses with yours.

<TidxQuery
  network="mainnet"
  signature="AccessKeySpend(address indexed account, address indexed publicKey, address indexed token, uint256 amount, uint256 remainingLimit)"
  sql={`SELECT token, amount, remainingLimit, block_num, tx_hash
FROM AccessKeySpend
WHERE account = '0x1e0c78105f12079899f7165eb1f74891d4d0f57f'
  AND publicKey = '0xb9f81dd7e629d2ec01e363c7a174c0f4ebe723e3'
ORDER BY block_num DESC
LIMIT 10`}
/>

## Change a spending limit

Enough signers to reach the threshold, or an [admin key](/docs/accounts/access-keys/admin-access-keys), change a key's limit without revoking it. A limited access key can't change limits, not even its own.

Set the new limit with viem's [`accessKey.updateLimit`](https://viem.sh/tempo/actions/accessKey.updateLimit).

The update sets both the limit and what's left of it to the new value, so a key that already spent 400 of its 500 OUSD today can spend 50 more. The period and the current period's end stay the same. On a key with no limits, the update turns limits on. It reverts on a revoked key ([`KeyAlreadyRevoked`](/docs/protocol/transactions/AccountKeychain#error-keyalreadyrevoked)), an expired key ([`KeyExpired`](/docs/protocol/transactions/AccountKeychain#error-keyexpired)), or an admin key ([`InvalidKeyId`](/docs/protocol/transactions/AccountKeychain#error-invalidkeyid)), since admin keys have no limits.

Specification: [Account Keychain spending limits](/docs/protocol/transactions/AccountKeychain#spending-limit-enforcement).
