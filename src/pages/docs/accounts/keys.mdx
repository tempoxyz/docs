# Account model

Tempo EVM has two account types, single-key and configurable. Both delegate to access keys through the Account Keychain. Product view: [How it works](/docs/accounts/how-it-works).

## Single-key and configurable accounts

| | [Single-key account](/docs/development/single-key-accounts) | [Configurable account](/docs/development/configurable-accounts) |
| --- | --- | --- |
| Address derived from | One public key: secp256k1, P-256, or WebAuthn | The version-0 configuration, CREATE2-compatible |
| Approved by | The root key | Owners whose weights reach the threshold |
| Keys can change | No. The key determines the address. | Yes, with `updateConfig`, at the same address |
| Upgrade path | [Upgrade in place](/docs/development/single-key-accounts#upgrade-to-a-configurable-account) to a configurable account | Not applicable |
| Signature type | secp256k1, P-256 (`0x01`), or WebAuthn (`0x02`) | Multisig (`0x05`) |
| Manages access keys | The root key | The owner quorum |
| EIP-7702 delegation | Allowed. A delegated account can't upgrade. | Rejected |

Configurable accounts, the upgrade, and login signatures are Draft TIPs that run on Tempo devnet.

The [Account Keychain](/docs/development/account-keychain) is not a third type. It stores the access keys of both types and checks their limits on every transaction.

<span id="tempo-transaction-signature-types" />

## Tempo transaction signature types

| Signature | Prefix | Used for |
| --- | --- | --- |
| secp256k1 | None (65 bytes) | Root keys, owners, access keys, fee payers |
| P-256 | `0x01` | Root keys, owners, access keys |
| WebAuthn | `0x02` | Passkeys as root keys, owners, or access keys |
| Keychain | `0x04` | An access key signing for its account |
| Multisig | `0x05` | Owner approvals, carrying the configuration |
| ZK | `0x06` | Logins: a sign-in proof plus a bound key's signature |

Encodings: [transaction specification](/docs/protocol/transactions/spec-tempo-transaction#signature-types), [TIP-1114](https://tips.sh/1114) (`0x05`), [TIP-1131](https://tips.sh/1131) (`0x06`).

## Logins as signers

A login is a signer, not an account type. Its ZK signature proves a recent sign-in with an identity provider and carries a signature from the key that sign-in named.

- **As an owner:** a login approves for a configurable account, up to its weight. See [Login signers](/docs/development/configurable-accounts#login-signers).
- **On its own:** a login also has its own address, derived from the key publisher, issuer, and a salted subject and client ID. That address is an ordinary account with no code, and it can send transactions directly.

Set up logins: [OIDC logins](/docs/accounts/authentication/oidc).

## Login, signing, and API credentials

| Credential | Authorizes |
| --- | --- |
| Your app's session | Your app and its records |
| Root key, owner, or login | Account approvals: alone for a root key, up to its weight for an owner |
| Access key | Transactions within its limits |
| Tempo API key | Hosted API requests only. Never signing. |
