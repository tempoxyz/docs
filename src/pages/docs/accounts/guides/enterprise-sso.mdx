# Enterprise SSO login

Give each person an account under the SSO login they already use, with no separate wallet app. Tempo checks each sign-in on chain, and the signing key stays on the person's device.

:::warning
OIDC signers (TIP-1130 to TIP-1133) are drafts that run on Tempo devnet only.
:::

Your identity provider must meet the [OIDC provider requirements](/docs/accounts/authentication/oidc#oidc-provider-requirements). Pair the login with a passkey or a recovery provider at threshold 2, so the identity provider can't approve alone: see [Recommended signer setups](/docs/accounts/security-policies#recommended-signer-setups).

## Sign in with SSO

<GuideDemo guide="identity-provider" />

:::::steps

### Check that your provider's keys are published

Each login names a key publisher, and the publisher's owner can list any key, so use a publisher whose owner you trust. For your own identity provider, [publish its keys](/docs/accounts/authentication/oidc#publish-your-providers-keys) and keep them current.

<span id="connect-to-a-relay" />

### Connect to a salt service

A [salt service](/docs/accounts/authentication/login-services#what-each-service-does) derives each login's address and requests its proof. Point the client at yours, as in [Connect to a salt service](/docs/accounts/authentication/oidc#connect-to-a-salt-service).

### Create a key on the device

```ts [sign-in.ts]
import { WebCryptoP256 } from 'viem/tempo'

const keyPair = await WebCryptoP256.createKeyPair()
```

### Sign the customer in

Pass your existing SSO sign-in function. Viem supplies a `nonce` that binds the login to the device key, so the ID token approves only with a signature from this device.

```ts [sign-in.ts]
const { credential } = await client.oidc.prove({
  getToken: ({ nonce }) => signInWithSso({ nonce }), // your SSO sign-in, returning the ID token
  publicKey: keyPair.publicKey,
})
```

Request the `openid` scope and only the claims you need.

### Open the customer's account

```ts [sign-in.ts]
import { Account } from 'viem/tempo'

const login = Account.fromZk(credential)
const account = Account.fromConfig({ address: 'infer', owners: [login] })
```

The same login reaches the same address on every device. Save `account.address` and `login.address` with the person's record.

### Authorize the device key with the first payment

```ts [sign-in.ts]
import { parseUnits } from 'viem'
import { Expiry } from 'viem/tempo'

const deviceKey = Account.fromWebCryptoP256(keyPair, { access: account })
const alphaUsd = '0x20c0000000000000000000000000000000000001'

await client.token.transferSync({
  account: deviceKey,
  amount: parseUnits('5', 6),
  keyAuthorization: await client.accessKey.signAuthorization({
    accessKey: deviceKey,
    account,
    expiry: Expiry.days(30),
    limits: [{ token: alphaUsd, limit: parseUnits('500', 6), period: 86_400 }],
  }),
  to: recipient,
  token: alphaUsd,
})
```

A [fee payer](/docs/accounts/fees#sponsor-an-accounts-fees) can sponsor the fee if the account has no balance yet.

:::::

<span id="restore-the-session-on-a-returning-visit" />

On a returning visit, rebuild the device key from the saved key pair with `Account.fromWebCryptoP256(keyPair, { access: address })`. When it expires, or on a new device, sign in again.

## Handle an email change

A login signer comes from the provider's user ID, not the email. If your identity provider keeps the user ID when the email changes, nothing changes on Tempo. Otherwise, swap the old login for the new one at the same weight.

<GuideDemo guide="change-email" />

:::::steps

### Sign the customer in with the new email

```ts [change-email.ts]
const { credential } = await client.oidc.prove({
  getToken: ({ nonce }) => signInWithSso({ nonce }), // the person uses the new email
  publicKey: keyPair.publicKey,
})
const newLogin = Account.fromZk(credential)
```

### Replace the old login at the same weight

```ts [change-email.ts]
import { isAddressEqual } from 'viem'

const account = Account.fromConfig(address)
const { owners, threshold } = await client.accounts.getConfig({ address: account.address })
const nextConfig = {
  owners: owners.map((entry) =>
    isAddressEqual(entry.owner, oldLoginAddress) ? { owner: newLogin.address, weight: entry.weight } : entry,
  ),
  threshold,
}
```

### Approve the swap

::::code-group

```ts [Passkey]
await client.accounts.updateConfigSync({ account, nextConfig, owner: passkey })
```

```ts [Old login]
const { credential: oldCredential } = await client.oidc.prove({
  getToken: ({ nonce }) => signInWithSso({ nonce }), // the person uses the old email
  publicKey: keyPair.publicKey,
})
await client.accounts.updateConfigSync({ account, nextConfig, owner: Account.fromZk(oldCredential) })
```

::::

### Open the account by its saved address from now on

After the update, `address: 'infer'` with the new login derives a different, empty account. Use `Account.fromConfig(address)`.

:::::

## SSO login limits

- A login approves for up to 10 minutes after sign-in, 9 by default in viem. After that, approvals fail with `ZkCredentialExpiredError`.
- Your web and mobile apps share one OAuth client ID. A different client ID reaches a different account.
- The identity provider can sign in as anyone it covers. Keep its login below the threshold on its own.

Build it with viem: [Sign in with an identity provider](https://viem-d07zjc3q1-wevm.vercel.app/tempo/guides/oidc/sign-in), [`oidc.prove`](https://viem-d07zjc3q1-wevm.vercel.app/tempo/actions/oidc.prove), and [`Account.fromZk`](https://viem-d07zjc3q1-wevm.vercel.app/tempo/accounts/account.fromZk).
