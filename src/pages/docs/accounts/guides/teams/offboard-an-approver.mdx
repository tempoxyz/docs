# Offboard an approver

Remove a departing approver while the treasury keeps its address, balance, and payment history.

When an approver leaves, remove their signer from the treasury, revoke any access key they could sign with, and add a replacement so one lost key can't lock the treasury.

:::warning
**Configurable accounts aren't live yet.** Accounts with several signers and a threshold ([TIP-1107](https://tips.sh/1107)) work only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change. This guide uses one.
:::

The code continues from [Set up a company treasury](/docs/accounts/guides/teams/company-treasury): a 2-of-3 treasury, where any two of its three signers approve each transaction, and its controller is leaving. The finance and operations teams each hold a key (`finance` and `operations`), and the controller approves with a passkey on their own device. `saved` is the record your app keeps for the treasury: the `address` and `config` you saved when you created it. Finance and operations approve each change below. This example loads both of their keys in one process. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

`client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

Tempo stores only a hash of the treasury's configuration, not the signer list itself. Before each action, rebuild the treasury from `saved.config` and attach the approvers' keys:

```ts [offboard.ts]
import { isAddressEqual } from 'viem'
import { Account } from 'viem/tempo'
import { client } from './client'

/** Rebuilds the treasury from its saved record, with the approvers' keys attached. */
function openTreasury(approvers: readonly Account.RootAccount[]) {
  const { salt, threshold, version } = saved.config
  // Attach the approvers' keys. The other signers stay as addresses.
  const owners = saved.config.owners.map(({ owner, weight }) => ({
    owner: approvers.find((key) => isAddressEqual(key.address, owner)) ?? owner, // [!code hl]
    weight,
  }))
  // Never updated (version 0): derive the address from the first signers.
  if (version === 0n) return Account.fromConfig({ address: 'infer', owners, salt, threshold })
  // After an update, deriving gives a different address, so pass the saved one.
  return Account.fromConfig({ address: saved.address, owners, salt, threshold, version }) // [!code hl]
}
```

viem signs with the attached keys and throws `Local owners do not meet the threshold.` before sending anything if their weights fall short. The demo runs the same steps with keys the page generates.

### Remove their signer

Build the next signer list from the saved one without the departing approver, and keep the threshold. Finance and operations approve it:

```ts [offboard.ts]
const removed = await client.accounts.updateConfigSync({ // [!code hl]
  account: openTreasury([finance, operations]), // [!code hl]
  nextConfig: { // [!code hl]
    owners: saved.config.owners.filter(({ owner }) => !isAddressEqual(owner, controller)), // [!code hl]
    threshold: saved.config.threshold, // [!code hl]
  }, // [!code hl]
}) // [!code hl]
// persist it with the treasury record
saved.config = removed.config // [!code hl]
```

Each signer update raises `config.version` by one and changes the hash Tempo stores, so save the `config` it returns. `openTreasury` reads `saved` on every call, so the next steps build the treasury from the new configuration. An account built from the old configuration fails with `multisig configuration commitment mismatch`, and the controller's passkey can no longer approve anything. If the remaining weights couldn't reach the threshold, viem would throw `Invalid account config: threshold exceeds total owner weight.` and send nothing. Here two signers of weight 1 remain at a threshold of 2.

### Revoke their keys

Removing a signer doesn't revoke [access keys](/docs/accounts/access-keys). Any access key the departing approver could sign with, such as a backend key they managed, keeps paying within its limits until you revoke it:

```ts [offboard.ts]
await client.accessKey.revokeSync({ // [!code hl]
  account: openTreasury([finance, operations]), // [!code hl]
  accessKey: serviceKey, // [!code hl]
}) // [!code hl]
```

`serviceKey` is the address you saved when you authorized the key. Revocation is permanent, so if the service still needs to pay, authorize a new key the departing approver never held. If you didn't save every key's address, [list the keys the treasury has authorized](/docs/accounts/access-keys/revocation#revoke-after-a-signer-change).

### Rebalance the threshold

With two approvers left at a threshold of 2, both must approve every payment, and losing either key locks the treasury. Add a replacement approver to return to 2 of 3:

```ts [offboard.ts]
const replacement = env('NEW_CONTROLLER_PASSKEY_ADDRESS') // the new approver's passkey, on their device

const added = await client.accounts.updateConfigSync({ // [!code hl]
  account: openTreasury([finance, operations]), // [!code hl]
  nextConfig: { // [!code hl]
    owners: [...saved.config.owners, { owner: replacement, weight: 1 }], // [!code hl]
    threshold: saved.config.threshold, // [!code hl]
  }, // [!code hl]
}) // [!code hl]
saved.config = added.config
```

If you already have the replacement's key, swap it in for the departing approver's in step 1's update and skip the 2-of-2 interval. Without a replacement, lowering the threshold to 1 keeps a lost key from locking the treasury but lets either approver pay alone. Have the new approver approve one transaction before you rely on their key.

## Rotate an approver's key instead

If the approver stays and only their key changes, such as a new hardware wallet, [replace the old key with the new one in one update](/docs/accounts/key-management/remove-signers#rotate-a-key-by-replacing-it-in-one-update) at the same weight.

## Offboarding limits

- Approvals collected before a signer update stop counting, because each one covers a single configuration version. Collect them again for any payment still waiting.
- `multisig configuration commitment mismatch` means the account was built from an outdated configuration, usually because another update landed first. Rebuild it from the latest saved configuration.
