# Offboard an approver

Remove a departing approver while the treasury keeps its address, balance, and payment history.

In this guide, a controller leaves a company treasury on the Tempo Accounts devnet where any two of three approvers sign each transaction. The two who remain, finance and operations, replace the controller's signer with a successor's, or remove it, then revoke any access key the controller could sign with.

:::warning
**Configurable accounts aren't live yet.** Accounts with several signers and a threshold ([TIP-1107](https://tips.sh/1107)) work only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change. This guide uses one.
:::

The code continues from [Set up a company treasury](/docs/accounts/guides/teams/company-treasury). The finance and operations teams each hold a key (`finance` and `operations`), and the controller approves with a passkey on their own device. `saved` is the record your app keeps for the treasury: the `address` and `config` you saved when you created it. Finance and operations approve each change below. This example loads both of their keys in one process. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

`client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

Tempo stores only a hash of the treasury's configuration, not the signer list itself. Before each action, rebuild the treasury from `saved.config` and attach the approvers' keys:

::::code-group

```ts [offboard.ts]
import { isAddressEqual } from 'viem'
import { Account } from 'viem/tempo'
import { client } from './client'

/** Rebuilds the treasury from its saved record, with the approvers' keys attached. */
function openTreasury(approvers: readonly Account.RootAccount[]) {
  const { salt, threshold, version } = saved.config
  // Attach the approvers' keys. The other signers stay as addresses.
  const owners = saved.config.owners.map(({ owner, weight }) => ({
    owner: approvers.find((key) => isAddressEqual(key.address, owner)) ?? owner, // [!code hl]
    weight,
  }))
  // Never updated (version 0): derive the address from the first signers.
  if (version === 0n) return Account.fromConfig({ address: 'infer', owners, salt, threshold })
  // After an update, deriving gives a different address, so pass the saved one.
  return Account.fromConfig({ address: saved.address, owners, salt, threshold, version }) // [!code hl]
}
```


### Replace their signer

When a successor is ready, swap the controller's signer for the successor's in one update at the same weight, and keep the threshold. Finance and operations approve it, and the treasury stays 2 of 3 throughout:

```ts [offboard.ts]
const replacement = env('NEW_CONTROLLER_PASSKEY_ADDRESS') // the new approver's passkey, on their device

const replaced = await client.accounts.updateConfigSync({ // [!code hl]
  account: openTreasury([finance, operations]), // [!code hl]
  nextConfig: { // [!code hl]
    owners: saved.config.owners.map((entry) => // [!code hl]
      isAddressEqual(entry.owner, controller) ? { owner: replacement, weight: entry.weight } : entry, // [!code hl]
    ), // [!code hl]
    threshold: saved.config.threshold, // [!code hl]
  }, // [!code hl]
}) // [!code hl]
// persist it with the treasury record
saved.config = replaced.config // [!code hl]
```

Each signer update raises `config.version` by one and changes the hash Tempo stores, so save the `config` it returns. `openTreasury` reads `saved` on every call, so the next steps build the treasury from the new configuration. An account built from the old configuration fails with `multisig configuration commitment mismatch`, and the controller's passkey can no longer approve anything. Have the new approver approve one transaction before you rely on their key.

<span id="remove-their-signer" />

Without a successor yet, drop the controller's entry instead:

```ts [offboard.ts]
const removed = await client.accounts.updateConfigSync({
  account: openTreasury([finance, operations]),
  nextConfig: {
    owners: saved.config.owners.filter(({ owner }) => !isAddressEqual(owner, controller)), // [!code hl]
    threshold: saved.config.threshold,
  },
})
saved.config = removed.config
```

<span id="rebalance-the-threshold" />

Two signers of weight 1 remain at a threshold of 2, so both must approve every payment. Losing either key locks the treasury until you add a replacement with the same update shape, appending `{ owner: replacement, weight: 1 }`. Lowering the threshold to 1 instead keeps a lost key from locking the treasury but lets either approver pay alone. If the remaining weights couldn't reach the threshold, Viem would throw `Invalid account config: threshold exceeds total owner weight.` and send nothing.

### Revoke their keys

Removing a signer doesn't revoke [access keys](/docs/accounts/access-keys). Any access key the departing approver could sign with, such as a backend key they managed, keeps paying within its limits until you revoke it:

```ts [offboard.ts]
await client.accessKey.revokeSync({ // [!code hl]
  account: openTreasury([finance, operations]), // [!code hl]
  accessKey: serviceKey, // [!code hl]
}) // [!code hl]
```

`serviceKey` is the address you saved when you authorized the key. Revocation is permanent, so if the service still needs to pay, authorize a new key the departing approver never held. If you didn't save every key's address, [list the keys the treasury has authorized](/docs/accounts/access-keys/revocation#revoke-after-a-signer-change).

Revocation [leaves two things in place](/docs/accounts/access-keys/revocation#what-revocation-leaves-in-place):

- **Token approvals:** a spender the key approved can still pull tokens up to the allowance, so set each allowance to zero from the treasury.
- **Keys it authorized:** if it was an [admin access key](/docs/accounts/access-keys/admin-access-keys), the keys it authorized stay authorized, so revoke each one.

## Rotate an approver's key instead

If the approver stays and only their key changes, such as a new hardware wallet, [replace the old key with the new one in one update](/docs/accounts/key-management/remove-signers#rotate-a-key-by-replacing-it-in-one-update) at the same weight.

## Offboarding limits

- Approvals collected before a signer update stop counting, because each one covers a single configuration version. Collect them again for any payment still waiting.
- `multisig configuration commitment mismatch` means the account was built from an outdated configuration, usually because another update landed first. Rebuild it from the latest saved configuration.
