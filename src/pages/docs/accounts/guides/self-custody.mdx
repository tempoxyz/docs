# Set up self-custody

Take a customer account from one login to self-custody: add a passkey and a backup signer, require two factors, recover from a lost passkey, then hand the account to a self-custodial wallet, such as Tempo Wallet. The address and balance never change.

The examples use the `client` from [OIDC logins](/docs/accounts/authentication/oidc#connect-to-a-salt-service). The weights follow the [customer accounts setup](/docs/accounts/security-policies#recommended-signer-setups).

## Add a backup signer

The account's current signers approve a new signer in one update.

<GuideDemo guide="add-signers" />

:::::steps

### Create the new signer

::::code-group

```ts [Passkey]
import { Account, WebAuthnP256 } from 'viem/tempo'

const passkey = Account.fromWebAuthnP256(await WebAuthnP256.createCredential({ label: 'My account' }))
const newSigner = passkey.address
```

```ts [Backup login]
const { credential } = await client.oidc.prove({
  getToken: ({ nonce }) => signInWithGoogle({ nonce }), // a second provider
  publicKey: keyPair.publicKey,
})
const newSigner = Account.fromZk(credential).address
```

```ts [Recovery provider]
const newSigner = '0x…' // the address your recovery provider gives you
```

```ts [Hardware or KMS key]
const newSigner = '0x…' // the key's address in your KMS or hardware wallet
```

::::

### Read the current signers

```ts [add-signer.ts]
const { owners, threshold } = await client.accounts.getConfig({ address: account.address })
```

### Approve the update with the current signers

```ts [add-signer.ts]
const { receipt } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [...owners, { owner: newSigner, weight: 1 }],
    threshold, // keep it, or raise it
  },
  owner: login, // a current signer
})
```

### Collect the remaining approvals

```ts [add-signer.ts]
await client.sendTransactionSync({ account, hash: receipt.transactionHash, owner: secondSigner })
```

Skip this step when the first signer reaches the threshold.

### Confirm the account survives losing any one signer

```ts [add-signer.ts]
const config = await client.accounts.getConfig({ address: account.address })
const total = config.owners.reduce((sum, { weight }) => sum + weight, 0)
const recoverable = config.owners.every(({ weight }) => total - weight >= config.threshold)
```

Count at most two logins toward what remains, since a transaction carries at most two login approvals.

## Require multi-factor approval

Move to a passkey (2), an email login (1), and an SMS login (1), with threshold 2. Signer changes and new devices then need the passkey, or both logins. See [Multi-factor approval](/docs/accounts/security-policies#multi-factor-approval) for why the logins need different issuers.

<GuideDemo guide="multi-factor" />

:::::steps

### Sign the customer in with SMS

```ts [multi-factor.ts]
const { credential } = await client.oidc.prove({
  getToken: ({ nonce }) => signInWithSms({ nonce }), // your SMS sign-in
  publicKey: keyPair.publicKey,
})
const sms = Account.fromZk(credential)
```

### Create the passkey

```ts [multi-factor.ts]
import { WebAuthnP256 } from 'viem/tempo'

const passkey = Account.fromWebAuthnP256(await WebAuthnP256.createCredential({ label: 'My account' }))
```

### Switch to the multi-factor configuration

```ts [multi-factor.ts]
await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [
      { owner: passkey.address, weight: 2 },
      { owner: login.address, weight: 1 },
      { owner: sms.address, weight: 1 },
    ],
    threshold: 2,
  },
  owner: login,
})
```

The email login approves alone because the current threshold is 1. After the update, one login alone reaches only 1 of 2.

### Keep paying with the device key

The device key from sign-in keeps its limits: signer changes don't touch access keys.

<span id="authorize-device-keys" />

### Authorize new device keys with the passkey or both logins

::::code-group

```ts [Passkey]
const keyAuthorization = await client.accessKey.signAuthorization({
  accessKey: deviceKey,
  account,
  expiry: Expiry.days(30),
  limits: [{ token: alphaUsd, limit: parseUnits('500', 6), period: 86_400 }],
  owner: passkey,
})
```

```ts [Both logins]
const pending = await client.accessKey.signAuthorization({
  accessKey: deviceKey,
  account,
  expiry: Expiry.days(30),
  limits: [{ token: alphaUsd, limit: parseUnits('500', 6), period: 86_400 }],
  owner: login,
})
const keyAuthorization = await client.accessKey.signAuthorization({ hash: pending.hash, owner: sms })
```

::::

Pass `keyAuthorization` with the new device key's first payment, as at sign-in.

## Recover from a lost passkey

The remaining signers replace a lost one in one update. They must reach the threshold: Tempo can't override an account's signers. Here the account has the multi-factor configuration above, the customer lost the passkey, and both logins replace it.

<GuideDemo guide="recover" />

:::::steps

### Create the replacement passkey on the new device

```ts [recover.ts]
import { Account, WebAuthnP256 } from 'viem/tempo'

const passkey = Account.fromWebAuthnP256(await WebAuthnP256.createCredential({ label: 'My account' }))
```

### Sign in with the remaining signers

```ts [recover.ts]
const email = Account.fromZk(emailCredential)
const sms = Account.fromZk(smsCredential)
const account = Account.fromConfig(address) // the customer's saved account address
```

Get each credential from `client.oidc.prove`.

### Replace the lost signer in one update

```ts [recover.ts]
const { receipt: pending } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [
      { owner: passkey.address, weight: 2 },
      { owner: email.address, weight: 1 },
      { owner: sms.address, weight: 1 },
    ],
    threshold: 2,
  },
  owner: email,
})

await client.sendTransactionSync({ account, hash: pending.transactionHash, owner: sms })
```

The update lands when the second login approves, and the lost passkey can no longer approve.

### Revoke the access keys the lost signer could reach

```ts [recover.ts]
await client.accessKey.revokeSync({ accessKey: lostDeviceKey, account, owner: passkey })
```

Changing signers doesn't revoke access keys, such as the device key on a lost phone.

:::::

A lost login works the same way: the passkey approves its replacement alone.

<span id="recover-funds-sent-on-another-chain" />

The address is the same on every EVM chain. On supported chains, the account's initial secp256k1 signers that reach the original threshold can recover funds sent there by mistake, even after you remove them on Tempo. Passkeys and logins don't count, so accounts created with only passkeys and logins, and accounts [upgraded in place](/docs/accounts/create#upgrade-an-existing-account), can't recover funds this way.

## Hand off to a self-custodial wallet

Swap your app's signers, including any login your auth service issues, for one the customer holds, and they control the same address from their own wallet. Your app keeps no key. A handoff is safer than exporting a private key: an export leaves your app with a copy and its access keys active, and passkeys and logins have no exportable key.

<GuideDemo guide="export" />

:::::steps

### Get the customer's signer address

The customer creates a passkey in a self-custodial wallet, such as [Tempo Wallet](https://wallet.tempo.xyz), and sends you its address. Ask them to confirm it there.

### Revoke your app's access keys

```ts [export.ts]
import { Account } from 'viem/tempo'

const appSigner = Account.fromSecp256k1(process.env.APP_SIGNER_KEY as `0x${string}`)
const account = Account.fromConfig(address) // the customer's account address

for (const accessKey of appAccessKeys) {
  await client.accessKey.revokeSync({ accessKey, account, owner: appSigner })
}
```

Do this first: after the next step, your app can't approve anything.

### Swap the signers in one update

```ts [export.ts]
await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [{ owner: customerSigner, weight: 1 }],
    threshold: 1,
  },
  owner: appSigner,
})
```

To keep backups, use the [customer accounts setup](/docs/accounts/security-policies#recommended-signer-setups), where no login approves alone.

### Send the customer to their wallet

The customer opens the same address in their wallet. Funds don't move, and payments to the address keep arriving.

## Self-custody limits

- Access keys survive signer changes. Revoke each one the old holder could use. A revoked key can't be authorized again.
- `InvalidConfig` means another signer update landed first. Read the signers again and rebuild the update.
- After a signer change, `address: 'infer'` derives a different address. Open the account with `Account.fromConfig(address)`.
- A login approves for up to 10 minutes after sign-in, 9 by default in viem. After that, approvals fail with `ZkCredentialExpiredError`.
- Tempo can't tell whether a signer still holds its key. Have each new signer approve once before you rely on it.

Specification: [configurable accounts](https://tips.sh/1107).
