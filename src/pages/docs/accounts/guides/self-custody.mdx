# Set up self-custody

Take a customer account from one key to self-custody: add a passkey, back it up with a backup key and a recovery key, recover from a lost passkey, then hand the account to a self-custodial wallet, such as Tempo Wallet. The address and balance never change.

The examples use a `client` whose transport is a relay with `Relay.accounts`, as in [Read the current configuration](/docs/development/configurable-accounts#read-the-current-configuration). The weights follow the [customer accounts setup](/docs/accounts/security-policies#recommended-signer-setups).

## Add a backup signer

The account's current signers approve a new signer in one update.

<GuideDemo guide="add-signers" />

:::::steps

### Create the new signer

::::code-group

```ts [Passkey]
import { Account, WebAuthnP256 } from 'viem/tempo'

const passkey = Account.fromWebAuthnP256(await WebAuthnP256.createCredential({ label: 'My account' }))
const newSigner = passkey.address
```

```ts [Device key]
import { Account, WebCryptoP256 } from 'viem/tempo'

const keyPair = await WebCryptoP256.createKeyPair() // non-extractable; store keyPair in IndexedDB
const newSigner = Account.fromWebCryptoP256(keyPair).address
```

```ts [Recovery provider]
const newSigner = '0x…' // the address your recovery provider gives you
```

```ts [Hardware or KMS key]
const newSigner = '0x…' // the key's address in your KMS or hardware wallet
```

::::

### Read the current signers

```ts [add-signer.ts]
const { owners, threshold } = await client.accounts.getConfig({ address: account.address })
```

### Approve the update with the current signers

```ts [add-signer.ts]
const { receipt } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [...owners, { owner: newSigner, weight: 1 }],
    threshold, // keep it, or raise it
  },
  owner: firstSigner, // a current signer
})
```

### Collect the remaining approvals

```ts [add-signer.ts]
await client.sendTransactionSync({ account, hash: receipt.transactionHash, owner: secondSigner })
```

Skip this step when the first signer reaches the threshold.

### Confirm the account survives losing any one signer

```ts [add-signer.ts]
const config = await client.accounts.getConfig({ address: account.address })
const total = config.owners.reduce((sum, { weight }) => sum + weight, 0)
const recoverable = config.owners.every(({ weight }) => total - weight >= config.threshold)
```

## Require multi-factor approval

Move to a passkey (2), a backup key the customer keeps offline (1), and a recovery provider's key (1), with threshold 2. The passkey approves alone. Signer changes and new devices without the passkey need both keys, which different parties hold. See [What a threshold protects](/docs/accounts/security-policies#what-a-threshold-protects).

<GuideDemo guide="multi-factor" />

:::::steps

### Create the backup key

The customer creates a key they keep apart from their phone, such as in a hardware wallet, and gives your app its address:

```ts [multi-factor.ts]
const backupKey = '0x…' // the backup key's address
```

### Get the recovery key's address

A recovery provider holds a key for the customer and gives you its address. It approves only together with the backup key or the passkey.

```ts [multi-factor.ts]
const recoveryKey = '0x…' // the address your recovery provider gives you
```

### Switch to the multi-factor configuration

```ts [multi-factor.ts]
await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [
      { owner: passkey.address, weight: 2 },
      { owner: backupKey, weight: 1 },
      { owner: recoveryKey, weight: 1 },
    ],
    threshold: 2,
  },
  owner: passkey,
})
```

The passkey approves alone because the current threshold is 1. After the update, the backup key or the recovery key alone reaches only 1 of 2.

### Keep paying with the device key

The device key the passkey authorized keeps its limits: signer changes don't touch access keys.

<span id="authorize-device-keys" />

### Authorize new device keys with the passkey

```ts [multi-factor.ts]
const keyAuthorization = await client.accessKey.signAuthorization({
  accessKey: deviceKey,
  account,
  expiry: Expiry.days(30),
  limits: [{ token: alphaUsd, limit: parseUnits('500', 6), period: 86_400 }],
  owner: passkey,
})
```

Pass `keyAuthorization` with the new device key's first payment. Without the passkey, the backup key and the recovery key sign the same authorization together: pass `hash` from the first signature and `owner` for the second.

## Recover from a lost passkey

The remaining signers replace a lost one in one update. They must reach the threshold: Tempo can't override an account's signers. Here the account has the multi-factor configuration above, the customer lost the passkey, and the backup key and the recovery key replace it together.

<GuideDemo guide="recover" />

:::::steps

### Create the replacement passkey on the new device

```ts [recover.ts]
import { Account, WebAuthnP256 } from 'viem/tempo'

const passkey = Account.fromWebAuthnP256(await WebAuthnP256.createCredential({ label: 'My account' }))
```

### Check the remaining signers

```ts [recover.ts]
const account = Account.fromConfig(address) // the customer's saved account address
const { owners, threshold } = await client.accounts.getConfig({ address })
```

The backup key and the recovery key have weight 2 together, enough for threshold 2 without the passkey.

### Replace the lost signer in one update

```ts [recover.ts]
const { receipt: pending } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [
      { owner: passkey.address, weight: 2 },
      { owner: backupKey.address, weight: 1 },
      { owner: recoveryKey.address, weight: 1 },
    ],
    threshold,
  },
  owner: backupKey,
})

await client.sendTransactionSync({ account, hash: pending.transactionHash, owner: recoveryKey })
```

The update lands when the recovery key approves, and the lost passkey can no longer approve.

### Revoke the access keys the lost signer could reach

```ts [recover.ts]
await client.accessKey.revokeSync({ accessKey: lostDeviceKey, account, owner: passkey })
```

Changing signers doesn't revoke access keys, such as the device key on a lost phone.

:::::

A lost backup key or recovery key works the same way: the passkey approves its replacement alone.

<span id="recover-funds-sent-on-another-chain" />

The address is the same on every EVM chain. On supported chains, the account's initial secp256k1 signers that reach the original threshold can recover funds sent there by mistake, even after you remove them on Tempo. Passkeys and device keys don't count, so accounts created with only passkeys and device keys, and accounts [upgraded in place](/docs/accounts/create#upgrade-an-existing-account), can't recover funds this way.

## Hand off to a self-custodial wallet

Swap your app's signers for one the customer holds, and they control the same address from their own wallet. Your app keeps no key. A handoff is safer than exporting a private key: an export leaves your app with a copy and its access keys active, and passkeys have no exportable key.

<GuideDemo guide="export" />

:::::steps

### Get the customer's signer address

The customer creates a passkey in a self-custodial wallet, such as [Tempo Wallet](https://wallet.tempo.xyz), and sends you its address. Ask them to confirm it there.

### Revoke your app's access keys

```ts [export.ts]
import { Account } from 'viem/tempo'

const appSigner = Account.fromSecp256k1(process.env.APP_SIGNER_KEY as `0x${string}`)
const account = Account.fromConfig(address) // the customer's account address

for (const accessKey of appAccessKeys) {
  await client.accessKey.revokeSync({ accessKey, account, owner: appSigner })
}
```

Do this first: after the next step, your app can't approve anything.

### Swap the signers in one update

```ts [export.ts]
await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [{ owner: customerSigner, weight: 1 }],
    threshold: 1,
  },
  owner: appSigner,
})
```

To keep backups, use the [customer accounts setup](/docs/accounts/security-policies#recommended-signer-setups), with a backup key the customer holds.

### Send the customer to their wallet

The customer opens the same address in their wallet. Funds don't move, and payments to the address keep arriving.

## Self-custody limits

- Access keys survive signer changes. Revoke each one the old holder could use. A revoked key can't be authorized again.
- `InvalidConfig` means another signer update landed first. Read the signers again and rebuild the update.
- After a signer change, `address: 'infer'` derives a different address. Open the account with `Account.fromConfig(address)`.
- Tempo can't tell whether a signer still holds its key. Have each new signer approve once before you rely on it.

Specification: [configurable accounts](https://tips.sh/1107).
