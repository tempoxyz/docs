# Add a recovery signer

A recovery signer is a second key that can approve transactions for a user's account, so losing their phone or first key doesn't lock them out. With one signer, a lost key is a lost account: nobody, including Tempo, can recover it. Add a recovery signer, then require two factors so whoever holds it can't take over the account alone. The address and balance stay the same.

:::warning
**Not live yet.** Configurable accounts ([TIP-1107](https://tips.sh/1107)) run only on Tempo devnet, and behavior may change.
:::

This guide starts from one signer at weight 1 and a threshold of 1, the total weight an approval needs. In your app, that first key is the key the account was created with, such as a key your app or wallet provider holds for the user.

The code uses the devnet `client` with `Relay.accounts` from [Signing thresholds](/docs/accounts/policies/signing-thresholds#collect-approvals). The demo runs these steps in this browser: a private key stands in for the user's first key, and a device key for the passkey.

### Create the new signer

Pick a key the user doesn't lose along with the first one, such as a [recovery provider's](/docs/accounts/policies/signing-thresholds#recovery-provider) key or a backup key in a hardware wallet or KMS. The update needs only its address, `newSigner` in the next step.

### Approve the update

Open the account from its saved configuration (with `address: 'infer'` until its first update, then with its saved address), and append `newSigner` to its signers. `currentKey`, the user's first key, approves alone because its weight of 1 reaches the threshold of 1.

```ts [add-signer.ts]
import { Account } from 'viem/tempo'

const account =
  savedConfig.version === 0n
    ? Account.fromConfig({ ...savedConfig, address: 'infer' })
    : Account.fromConfig({ address, ...savedConfig })

const { config } = await client.accounts.updateConfigSync({
  account,
  nextConfig: {
    owners: [...savedConfig.owners, { owner: newSigner, weight: 1 }],
    threshold: savedConfig.threshold,
  },
  owner: currentKey,
})
// Save `config` in place of `savedConfig`: the next update starts from it.
```

### Confirm the account survives losing one signer

Check that the other signers still reach the threshold, whichever one is lost.

```ts [add-signer.ts]
const total = config.owners.reduce((sum, { weight }) => sum + weight, 0)
const recoverable = config.owners.every(({ weight }) => total - weight >= config.threshold)
```

Tempo can't tell whether a signer still holds its key, so have the new signer approve once before you rely on it.

### Require two factors

Either signer can now approve anything alone, including adding a device or removing the other signer, so whoever holds the recovery signer could take over the account. To require two factors, use the [customer accounts setup](/docs/accounts/policies/signing-thresholds#recommended-signer-setups): in one update, add a passkey at weight 2 and raise the threshold to 2.

```ts [multi-factor.ts]
import { Account, WebAuthnP256 } from 'viem/tempo'

const passkey = Account.fromWebAuthnP256(await WebAuthnP256.createCredential({ label: 'My account' }))

const { config: twoFactor } = await client.accounts.updateConfigSync({
  account: Account.fromConfig({ address, ...config }),
  nextConfig: {
    owners: [...config.owners, { owner: passkey.address, weight: 2 }],
    threshold: 2,
  },
  owner: currentKey, // approves alone at the current threshold of 1
})
```

Now a new device or a signer change needs the passkey on the user's device, or the first key and recovery signer together. Give those two keys [different holders](/docs/accounts/policies/signing-thresholds#what-a-threshold-protects-against), because one party holding both can approve alone. Signer changes don't touch access keys, so the user's existing device key keeps paying within its limits.

## Recovery signer limits

- Only current signers count toward the threshold, not the signer being added. When one can't reach it alone, a second signer approves the same transaction, as in [Add signers](/docs/accounts/key-management/add-signers#send-the-signer-update).
- `InvalidConfig` means the update didn't start from the account's current configuration, usually because another update landed first. Load the latest saved configuration and rebuild the update.
- Until the first update, open the account with `address: 'infer'`. After a signer change, `address: 'infer'` derives a different address, so open the account with its saved address.

When the user loses a signer, follow [Recover a user's account](/docs/accounts/guides/users/recover-an-account).
