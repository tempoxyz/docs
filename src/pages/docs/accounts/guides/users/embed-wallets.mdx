# Embed wallets with a provider

Use Privy or Turnkey to run your users' wallets inside your app without letting the provider move their funds alone. Each account has three signers, the keys that approve its transactions: the user's passkey approves alone, and your provider's key approves only together with a separate [recovery provider's](/docs/accounts/policies/signing-thresholds#recovery-provider) key, for example to replace a lost passkey.

:::warning
**Configurable accounts aren't live yet.** Accounts with several signers and a threshold ([TIP-1107](https://tips.sh/1107)) work only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet), not on mainnet or testnet, and may still change. The provider setup below uses one; [connecting a self-custodial wallet](#connect-a-self-custodial-wallet-instead) doesn't.
:::

### Connect Privy or Turnkey

Your provider approves with its key through its Tempo integration, and only when its own signing policies allow.

- [Privy](https://docs.privy.io/wallets/using-wallets/tempo/send-a-transaction): start from the [Privy Tempo example](https://github.com/privy-io/examples/tree/main/examples/privy-next-tempo), which creates wallets and sends payments in a browser app. Keep Privy and your RPC client on the same network.
- [Turnkey](https://docs.turnkey.com/features/networks/tempo): start from the [Turnkey Tempo example](https://github.com/tkhq/sdk/tree/main/examples/chain-integrations/with-tempo). Create Tempo addresses with `ADDRESS_TYPE_ETHEREUM`, write signing policies against Tempo transaction fields in the `tempo.tx` namespace, and add the [Embedded Wallet Kit](https://docs.turnkey.com/sdks/react/getting-started) for wallet UI.

Create the user's wallet with your provider, then use the wallet's address as `providerKeyAddress` in the next step.

<span id="make-the-providers-key-one-signer" />

### Make the provider's key one signer

Give the user's passkey weight 2 and each provider's key weight 1, with a [threshold](/docs/accounts/policies/signing-thresholds#recommended-signer-setups) of 2, the total weight an approval needs. A passkey is a key the user's device keeps and unlocks with Face ID, Touch ID, or Windows Hello. Your app signs only with the passkey, which stays on the user's device; each provider keeps its own key, so the account lists those keys by address. `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)).

```ts [client.ts]
// [!include ~/snippets/accounts-devnet.ts:client]
```

```ts [account.ts]
import { parseUnits } from 'viem'
import { Account, WebAuthnP256 } from 'viem/tempo'
import { client } from './client'

const token = '0x20c0000000000000000000000000000000000001' // AlphaUSD, a test stablecoin

const credential = await WebAuthnP256.createCredential({ label: 'My account' })
const passkey = Account.fromWebAuthnP256(credential)

const account = Account.fromConfig({
  address: 'infer', // derive the address from these first signers
  owners: [
    { owner: passkey, weight: 2 }, // the key on this device, so it approves here
    { owner: providerKeyAddress, weight: 1 }, // the key your provider manages for this user
    { owner: recoveryAddress, weight: 1 }, // the key your recovery provider holds
  ],
  threshold: 2,
})

await client.faucet.fundSync({ account: account.address }) // devnet test stablecoins
// The passkey's weight of 2 reaches the threshold, so it approves this payment alone.
await client.token.transferSync({ account, amount: parseUnits('1', 6), to: recipient, token })
```

Creating the account sends nothing: the address can receive stablecoins right away, and the account's first transaction registers it onchain. Save `account.address`, `account.config` (the signers, weights, threshold, and version), and the passkey's [`credential.id` and `credential.publicKey`](/docs/accounts/authentication/passkeys#passkey-limits) with the user's record. Tempo stores only a hash of the configuration, so when the user returns, your app rebuilds the account from this saved copy, with the passkey attached:

```ts [open-account.ts]
import { isAddressEqual } from 'viem'
import { Account } from 'viem/tempo'

const { address, config, credential } = await loadAccount(userId) // your app's storage
const passkey = Account.fromWebAuthnP256(credential)
const owners = config.owners.map(({ owner, weight }) => ({
  owner: isAddressEqual(owner, passkey.address) ? passkey : owner, // the provider keys stay addresses
  weight,
}))
const account =
  config.version === 0n // never updated: the configuration derives the address
    ? Account.fromConfig({ address: 'infer', owners, salt: config.salt, threshold: config.threshold })
    : Account.fromConfig({ ...config, address, owners })
```

A signer change, such as replacing a lost passkey or handing the account off, raises the configuration's version, and `updateConfigSync` returns the new `config`. Save it over the old copy before the next payment: Tempo checks every transaction against the current configuration, so an account built from the old one fails. After a change, the new signers would derive a different address, which is why `open-account.ts` passes the saved one. Without the passkey, a payment or change needs both providers' keys, which sign on each provider's own systems. To collect approvals from separate devices, see [Signing thresholds](/docs/accounts/policies/signing-thresholds#approvers-on-separate-devices).

:::::

When a user wants full control, [hand off the account](/docs/accounts/guides/users/hand-off): swap the provider's key for a signer the user holds, at the same address.

## Let the provider run login services

To sign users in with an email or social login instead of a passkey, make the login a signer: see [OIDC logins](/docs/accounts/authentication/oidc). Your wallet provider can run the [salt service and prover](/docs/accounts/authentication/oidc#login-services) and still hold no key for your users, so it can't move their funds. If it also issues the logins, it can sign in as those users, so keep each login below the threshold and pair it with the passkey. Logins are experimental and run on a separate devnet.

## Sign users in with Tempo

With Sign in with Tempo, a wallet provider holds each user's Tempo account, and your app holds only a bounded [access key](/docs/accounts/access-keys). The user signs in on Tempo's page with an email code or Google and approves the key's expiry, spending limit, and scopes. Privy holds the account's owner key and signs the key authorization. Tempo checks those bounds on every transaction, so even a leaked key can't spend more than the user approved.

The demo signs you in, shows the key's bounds, funds the account from the faucet, and pays 1 AlphaUSD with the key. It runs on Moderato testnet, whose stablecoins have no value.

<span id="request-a-bounded-access-key" />

Install `@tempoxyz/auth`, then send the user to Tempo's sign-in page with the permissions your app needs. In a browser, the library creates the access key as a non-extractable WebCrypto P-256 key.

```bash [Terminal]
pnpm add @tempoxyz/auth viem
```

```ts [sign-in.ts]
import { Actions, Auth } from '@tempoxyz/auth'
import { tempoModerato } from 'viem/chains'
import { Expiry, Scopes } from 'viem/tempo'

const alphaUsd = '0x20c0000000000000000000000000000000000001'
const auth = Auth.create({ chainId: tempoModerato.id, clientId: '<CLIENT_ID>' })

// The sign-in button: the browser leaves for Tempo's page, where the user approves these bounds.
await Actions.redirect.start(auth, {
  permissions: {
    expiry: Expiry.days(1),
    limits: [{ limit: 5_000_000n, token: alphaUsd }], // 5 AlphaUSD in total, in base units
    scopes: [Scopes.tip20(alphaUsd).transfer()],
  },
})
```

Limits in a sign-in request are one-time totals. To grant a fresh budget, sign the user in again.

<span id="pay-with-the-access-key" />

When the browser returns, `Actions.redirect.complete` returns an `Authorization`: an access token for Tempo APIs, and `account`, a viem account that signs with the access key.

```ts [pay.ts]
import { Actions } from '@tempoxyz/auth'
import { tempoModerato } from 'viem/chains'
import { createClient } from 'viem/tempo'

const authorization = await Actions.redirect.complete(auth)
if (!authorization) throw new Error('Sign in first.')

const client = createClient({ account: authorization.account, chain: tempoModerato, feeToken: alphaUsd })

// The first transaction carries the key authorization, which registers the key on Tempo.
const { receipt } = await client.token.transferSync({ amount: 1_000_000n, to: recipient, token: alphaUsd })
```

Each transaction pays a small network fee in AlphaUSD. To keep the key across page loads, store `authorization.key` in IndexedDB and rebuild the account with `Key.toAccount`. `Actions.signOut` ends the sign-in session; the key stays valid on Tempo until it expires.

## Connect a self-custodial wallet instead

If a user already has a self-custodial wallet, such as Tempo Wallet, connect it with the [Accounts SDK](https://accounts.tempo.xyz/docs). The wallet holds the keys and signs; your app uses the address the user selects. Tempo Wallet sends transactions through its own RPC endpoint, not your devnet client, so the demo and code run on Moderato testnet, whose stablecoins have no value.

```bash [Terminal]
pnpm add --save-exact accounts@0.18.4 viem
```

<span id="connect-tempo-wallet-from-your-application" />

```ts [connect.ts]
import { Provider } from 'accounts'
import { tempoModerato } from 'viem/chains'

const provider = Provider.create({ chains: [tempoModerato], testnet: true })
const [address] = await provider.request({ method: 'eth_requestAccounts' })
if (!address) throw new Error('No account was selected')
```

Track the wallet connection separately from your app's signed-in session. On `accountsChanged`, update the selected address, or clear it when the wallet disconnects; on `chainChanged`, refresh network-dependent state before you enable transactions. To send payments, create wallet and public clients from this provider as in the [browser wallet setup](/docs/guide/payments/send-a-payment/examples#browser-wallet-setup). [Wallet partners](/docs/partners/wallets) lists other wallets you can connect.
