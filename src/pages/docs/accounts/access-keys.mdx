# Access keys

An access key lets a customer's phone, your backend, or an AI agent pay without the account's signers approving each payment.

The account's signers authorize an access key once, and from then on it signs transactions from the account by itself. Tempo checks the key's bounds on every transaction, so even a leaked key can spend only what those bounds allow. Access keys work on mainnet and testnet with a [single-key account](/docs/accounts/how-it-works#address), and with a configurable account only on the Tempo Accounts devnet.

## What an access key is

An access key signs from the account's address and pays from its balance, but holds no funds itself. The account stores only the key's address, type, and bounds, never its private key.

An access key isn't a signer. It never counts toward the [signing threshold](/docs/accounts/policies/signing-thresholds), so it can't change the account's signers, and changing a configurable account's signers leaves every access key in place.

## Bound what a key can do

Each key carries up to three bounds. Every bound is optional, and leaving one out removes that check: a key without scopes can call any contract. Give a backend, agent, or [card program](/docs/accounts/automations/pay-from-an-embedded-wallet) key all three.

## Give each holder its own key

Give each device, service, agent, or team its own key, so you can revoke one without touching the rest. Pick the key type by where its holder signs:

| Holder | Key type |
| --- | --- |
| A customer's browser or phone | A P-256 [device key](/docs/accounts/authentication/device-keys) the device can't export, or a WebAuthn [passkey](/docs/accounts/authentication/passkeys) |
| Your backend or an [AI agent](/docs/accounts/automations/give-an-agent-a-wallet) | A P-256 key it generates, or a secp256k1 key in your [KMS or HSM](/docs/accounts/automations/pay-out-from-a-backend#keep-the-key-in-your-kms) |
| A wallet | A secp256k1 key |
| A [team](/docs/accounts/custodians/company-treasury) | A configurable account, whose own signers and threshold approve as the key. Works only on the Tempo Accounts devnet ([TIP-1111](https://tips.sh/1111)). |

## Authorize an access key

Enough signers to reach the threshold, or an [admin key](/docs/accounts/access-keys/admin-access-keys), sign a key authorization: a message that names the key and its bounds. Submit it in one of two ways:

- With the key's first payment: `signAuthorization` returns a `keyAuthorization` that travels with the first transaction the key signs. The key stays authorized even if that transaction's calls revert.
- On its own: `authorizeSync` sends the authorization in a separate transaction, before the key pays.

This example takes the first path: a new account's signer gives a payout key 10 OUSD for one hour, payable to one recipient. `account.ts` is the configurable account with one signer from [Create an account](/docs/accounts/create#create-an-account-in-code), funded by the [devnet faucet](/docs/accounts/create#fund-an-account-on-devnet). `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)). To run it on testnet with a single-key account, set `account` to that signer and connect `client` to [testnet](/docs/quickstart/connection-details#testnet).

::::code-group

```ts [access-keys.ts]
import { parseUnits } from 'viem'
import { Account, Expiry, P256 } from 'viem/tempo'
import { account } from './account'
import { client } from './client'

export { account }
// A test stablecoin on the devnet
export const stablecoin = '0x20c0000000000000000000000000000000000001'
export const recipient = process.env.TEMPO_RECIPIENT as `0x${string}`

export const accessKey = Account.fromP256(P256.randomPrivateKey(), { access: account }) // [!code hl]
const keyAuthorization = await client.accessKey.signAuthorization({ // [!code hl]
  accessKey, // [!code hl]
  account, // [!code hl]
  expiry: Expiry.hours(1), // [!code hl]
  limits: [{ token: stablecoin, limit: parseUnits('10', 6), period: 0 }], // [!code hl]
  scopes: [{ address: stablecoin, recipients: [recipient], selector: 'transfer(address,uint256)' }], // [!code hl]
}) // [!code hl]

await client.token.transferSync({
  account: accessKey,
  amount: parseUnits('2', 6),
  keyAuthorization, // [!code hl]
  to: recipient,
  token: stablecoin,
})
```

```ts [client.ts]
// [!include ~/snippets/accounts-devnet.ts:client]
```

::::

The other pages in this section import `account`, `accessKey`, `stablecoin`, and `recipient` from this file. To confirm the key landed, read it back with `client.accessKey.getMetadata({ account, accessKey })`.

Tempo stores each limit and scope with the key, so each one adds to the network fee for authorizing it. This example's authorization and first payment cost under a cent together.

To keep the option of canceling a signed authorization before anyone submits it, sign it with a 32-byte `witness`; burning the witness cancels it. See [Witnesses](https://viem.sh/tempo/guides/access-keys/witnesses) and [Authorize access keys](https://viem.sh/tempo/guides/access-keys/authorize) in Viem.

## Revoke and audit keys

[Revoke](/docs/accounts/access-keys/revocation) a key to end it permanently, for example when a device is lost or a service is retired. Revocation doesn't undo payments the key already made or token approvals it granted, so clean those up too.

<span id="see-an-accounts-keys" />

Tempo emits `KeyAuthorized` when an account adds a key and `KeyRevoked` when it revokes one, so the [public indexer](/docs/api/indexer-api) can list every key an account has had; replace the address with your account's.

<TidxQuery
  network="mainnet"
  signature={[
    'KeyAuthorized(address indexed account, address indexed publicKey, uint8 signatureType, uint64 expiry)',
    'KeyRevoked(address indexed account, address indexed publicKey)',
  ]}
  sql={`SELECT 'authorized' AS event, publicKey AS access_key, expiry, block_num, tx_hash
FROM KeyAuthorized
WHERE account = '0x6028375ea6ae3339b16f29b343f8f32f7bb3ee8a'
UNION ALL
SELECT 'revoked' AS event, publicKey AS access_key, NULL AS expiry, block_num, tx_hash
FROM KeyRevoked
WHERE account = '0x6028375ea6ae3339b16f29b343f8f32f7bb3ee8a'
ORDER BY block_num DESC
LIMIT 20`}
/>

## Access key limits

- An access key can't create a contract at the top level of a transaction. See [Scope limits](/docs/accounts/access-keys/scopes#scope-limits).
- All of an account's transactions, whichever key signs them, share one sequence number (nonce) by default, so they land in order. To send payments concurrently, use expiring nonces or separate nonce keys. See [Parallel payments](/docs/guide/payments/send-parallel-transactions).
- Calls that authorize, change, or revoke keys must come from the account's own transaction (`msg.sender == tx.origin`), not through a contract.

The [Account Keychain specification](/docs/protocol/transactions/AccountKeychain) defines these rules in full.
