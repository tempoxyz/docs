# Access keys

An access key lets a customer's phone, your backend, or an AI agent pay from an account without the account's signers approving each payment. Tempo checks the key's spending limit, expiry, and scopes on every transaction, so even a leaked key can spend only what those bounds allow. Access keys work on mainnet and testnet with a [single-key account](/docs/accounts/how-it-works#address), and with a configurable account only on the Tempo Accounts devnet.

## What an access key is

An account's signers are the keys that approve its transactions. They authorize an access key once. From then on, the key signs transactions from the account's address and pays from the account's balance by itself. The key holds no funds, and the account stores only the key's address, type, and bounds, never its private key.

<span id="access-keys-and-signers" />
<span id="choose-the-authority-to-delegate" />

An access key isn't a signer. It never counts toward the [signing threshold](/docs/accounts/policies/signing-thresholds), so it can't change the account's signers. Among access keys, only [admin access keys](/docs/accounts/access-keys/admin-access-keys) can authorize, change, or revoke keys. Changing a configurable account's signers leaves every access key in place.

Every bound is optional, and leaving one out removes that check: a key without `scopes` can call any contract. Give a backend, agent, or [card program](/docs/accounts/guides/automations/fund-a-card-program) key all three. Give an admin key only to a party you'd trust with the whole balance.

## Give each holder its own key

Give each device, service, agent, or team its own key, so you can revoke one without touching the rest. Pick the key type by where its holder signs:

| Holder | Key type |
| --- | --- |
| A customer's browser or phone | A P-256 [device key](/docs/accounts/authentication/device-keys) the device can't export, or a WebAuthn [passkey](/docs/accounts/authentication/passkeys) |
| Your backend or an [AI agent](/docs/accounts/guides/agents/give-an-agent-a-wallet) | A P-256 key it generates, or a secp256k1 key in your [KMS or HSM](/docs/accounts/guides/automations/pay-out-from-a-backend#keep-the-key-in-your-kms) |
| A wallet | A secp256k1 key |
| A [team](/docs/accounts/guides/teams/team-budget) | A configurable account, whose own signers and threshold approve as the key. Works only on the Tempo Accounts devnet ([TIP-1111](https://tips.sh/1111)). |

## Authorize an access key

Enough signers to reach the threshold, or an [admin key](/docs/accounts/access-keys/admin-access-keys), sign a key authorization: a message that names the key and its bounds. Submit it in one of two ways:

- With the key's first payment: `signAuthorization` returns a `keyAuthorization` that travels with the first transaction the key signs. The key stays authorized even if that transaction's calls revert.
- On its own: `authorizeSync` sends the authorization in a separate transaction, before the key pays.

This example takes the first path: a new account's signer gives a payout key 10 AlphaUSD, a test stablecoin, for one hour, payable to one recipient. The account is a configurable account with one signer, as in [Create an account](/docs/accounts/create), so `client.ts` connects to the Tempo Accounts devnet ([set up the devnet key](/docs/accounts/create#connect-to-the-devnet)). To run it on testnet with a single-key account instead, set `account` to `signer` and connect `client` to [testnet](/docs/quickstart/connection-details#testnet).

```ts [client.ts]
// [!include ~/snippets/accounts-devnet.ts:client]
```

```ts [access-keys.ts]
import { parseUnits } from 'viem'
import { generatePrivateKey } from 'viem/accounts'
import { Account, Expiry, P256 } from 'viem/tempo'
import { client } from './client'

export const alphaUsd = '0x20c0000000000000000000000000000000000001'
export const recipient = process.env.TEMPO_RECIPIENT as `0x${string}`

// An account with one signer, as in Create an account, funded by the devnet faucet
const signer = Account.fromSecp256k1(generatePrivateKey())
export const account = Account.fromConfig({ address: 'infer', owners: [signer] })
await client.faucet.fundSync({ account: account.address })

export const accessKey = Account.fromP256(P256.randomPrivateKey(), { access: account })
const keyAuthorization = await client.accessKey.signAuthorization({
  accessKey,
  account,
  expiry: Expiry.hours(1),
  limits: [{ token: alphaUsd, limit: parseUnits('10', 6), period: 0 }],
  scopes: [{ address: alphaUsd, recipients: [recipient], selector: 'transfer(address,uint256)' }],
})

await client.token.transferSync({
  account: accessKey,
  amount: parseUnits('2', 6),
  keyAuthorization, // first payment only
  to: recipient,
  token: alphaUsd,
})
```

The other pages in this section import `account`, `accessKey`, `alphaUsd`, and `recipient` from this file. To confirm the key landed, read it back with `client.accessKey.getMetadata({ account, accessKey })`.

Tempo stores each limit and scope with the key, so each one adds to the network fee for authorizing it. This example's authorization and first payment cost under a cent together. To keep the option of canceling a signed authorization before anyone submits it, sign it with a 32-byte `witness`; burning the witness cancels it. See [Witnesses](https://viem.sh/tempo/guides/access-keys/witnesses) and [Authorize access keys](https://viem.sh/tempo/guides/access-keys/authorize) in viem.

## Access key limits

- An access key can't create a contract at the top level of a transaction. See [Scope limits](/docs/accounts/access-keys/scopes#scope-limits).
- All of an account's transactions, whichever key signs them, share one sequence number (nonce) by default, so they land in order. To send payments concurrently, use expiring nonces or separate nonce keys. See [Parallel payments](/docs/guide/payments/send-parallel-transactions).
- Calls that authorize, change, or revoke keys must come from the account's own transaction (`msg.sender == tx.origin`), not through a contract.

The [Account Keychain specification](/docs/protocol/transactions/AccountKeychain) defines these rules in full.
