# Access keys

An access key pays from an account without the signers, inside a spending limit, an expiry, and scopes that Tempo checks on every transaction. Give each device, backend, or agent its own key with the narrowest bounds its task needs, because Tempo enforces those bounds even if the key leaks.

<span id="access-keys" />

## What an access key is

An access key is a signing key that the account's signers authorize once. After that, it signs transactions from the account's address and pays from the account's balance. The key holds no funds of its own, and the account stores only its address, type, and bounds, never its private key.

Give a backend, agent, or card key all three bounds: a limit for the amount, scopes for the destinations, and an expiry for the time window. Give an admin key only to a party you'd trust with the whole balance.

## Access keys and signers

Signers approve together, by weight. That suits signer changes and large payments, but a phone paying for coffee, a backend running payouts, or an agent buying API calls can't wait for approvals. An access key replaces approval with bounds: it does only what its bounds allow, and Tempo rejects the rest.

The demo authorizes a key on Moderato testnet, pays with it, shows Tempo rejecting an overspend, then revokes it.

<AccessKeyDemo />

An access key never counts toward the [signing threshold](/docs/accounts/policies/signing-thresholds). It can't change signers or add weight, and a limited key can't authorize, change, or revoke keys. Changing signers doesn't revoke it.

## Access key types

| Key type | Typical holder |
| --- | --- |
| P-256 | A device key that the customer's browser or phone can't export, or a key your backend generates |
| WebAuthn | A passkey |
| secp256k1 | A key in your KMS, HSM, or a wallet |
| Configurable account | A team account with its own signers and threshold, which approve as the key. Specified in [TIP-1111](https://tips.sh/1111), a Draft. |

Keep a key where its holder signs. A device key stays on the device, and a backend key stays in your secret manager.

## Authorize an access key

Signers that reach the threshold sign a key authorization, or an [admin key](/docs/accounts/access-keys/admin-access-keys) signs it. There are two ways to submit it:

| Path | Behavior |
| --- | --- |
| With the key's first payment | `signAuthorization` returns `keyAuthorization`, which travels with the first transaction the key signs. The key stays authorized even if that transaction's calls revert. |
| As its own transaction | `authorizeSync` sends the authorization alone, before the key pays. |

In this example, a 2-of-3 treasury gives a payout key 10 AlphaUSD for one hour, payable to one recipient:

```ts [access-keys.ts]
import { parseUnits } from 'viem'
import { tempoModerato } from 'viem/chains'
import { Account, createClient, Expiry, P256 } from 'viem/tempo'

const env = (name: string) => process.env[name] as `0x${string}`
const alphaUsd = '0x20c0000000000000000000000000000000000001'
const recipient = env('TEMPO_RECIPIENT')
const client = createClient({ chain: tempoModerato })

const account = Account.fromConfig({
  address: 'infer',
  owners: [
    Account.fromSecp256k1(env('FINANCE_SIGNER_KEY')),
    Account.fromSecp256k1(env('OPERATIONS_SIGNER_KEY')),
    env('CONTROLLER_PASSKEY_ADDRESS'),
  ],
  threshold: 2,
})

const accessKey = Account.fromP256(P256.randomPrivateKey(), { access: account })
const keyAuthorization = await client.accessKey.signAuthorization({
  accessKey,
  account,
  expiry: Expiry.hours(1),
  limits: [{ token: alphaUsd, limit: parseUnits('10', 6), period: 0 }],
  scopes: [{ address: alphaUsd, recipients: [recipient], selector: 'transfer(address,uint256)' }],
})

await client.token.transferSync({
  account: accessKey,
  amount: parseUnits('2', 6),
  keyAuthorization, // first payment only
  to: recipient,
  token: alphaUsd,
})
```

The other pages in this section continue from this example's `client`, `account`, `accessKey`, and `alphaUsd`. To confirm the key landed, read it back:

```ts [read-key.ts]
const { expiry, isRevoked, keyType, spendPolicy } = await client.accessKey.getMetadata({ account, accessKey })
```

Authorizing a key costs about $0.003, whatever its bounds. To cancel a signed authorization before it lands, bind a witness to it and burn the witness. See [Witnesses](https://viem.sh/tempo/guides/access-keys/witnesses) and [Authorize access keys](https://viem.sh/tempo/guides/access-keys/authorize) in viem.

## Access key limits

Each control's page lists its own limits. These apply to every access key:

- Access keys never count toward the threshold. Among access keys, only admin keys can authorize, change, or revoke keys.
- An access key can't create a contract at the top level of a transaction. See [Scope limits](/docs/accounts/access-keys/scopes#scope-limits).
- An account's payments share one sequential nonce by default, so they land in order. Send concurrent payments with expiring nonces or separate nonce keys. See [Parallel payments](/docs/guide/payments/send-parallel-transactions).
- Key management calls must come from the account's own transaction (`msg.sender == tx.origin`), not through a contract.
- To check that a signature came from an active access key of an account, use `verifyKeychain`. See [Verify approvals](/docs/accounts/policies/signing-thresholds#collect-and-verify-approvals).

Specifications: [Account Keychain](/docs/protocol/transactions/AccountKeychain), [admin access keys](https://tips.sh/1049), [configurable account access keys](https://tips.sh/1111).
