# Signing thresholds

A Tempo account moves funds only when signers whose weights add up to its threshold approve. The threshold decides custody: whoever holds signers that reach it can pay without anyone else, and nobody below it can. Tempo checks the sum on every transaction.

<span id="signer-weights-and-the-threshold" />

## How approvals add up

Each signer has a weight of at least 1. A transaction executes once the signers that approve it reach the threshold in total weight.

Take a customer account with a passkey of weight 2, a backup key of weight 1, and a recovery provider's key of weight 1, with a threshold of 2. The passkey approves alone. The backup and recovery keys approve together. One of them alone reaches 1 of 2 and can't pay.

One approval covers the whole transaction, including every call in a batch. The same threshold covers payments, signer changes, and new [access keys](/docs/accounts/access-keys). Access keys never count toward it: they pay alone, within limits, instead of approving.

<span id="what-a-threshold-protects" />

### What a threshold protects

Each signer can fail: a phone gets lost, a key leaks, an approver leaves. Set weights so the account survives both kinds of failure:

- **Theft:** no single party's signers reach the threshold alone, unless that party is the customer. A compromised signer then can't pay.
- **Loss:** the remaining signers still reach the threshold after you lose any one. Total weight minus the largest weight must be at least the threshold.

Count parties, not signers. Two keys in the same KMS, or a wallet provider's key and a recovery key it also runs, belong to one party: that party can reach their combined weight alone. Keep signers that must be independent with different holders.

## Recommended signer setups

| For | Signers | Threshold | Who can approve |
| --- | --- | --- | --- |
| Getting started | Passkey (1), backup key (1) | 1 | Either one |
| Customer accounts | Passkey (2), backup key (1), recovery provider (1) | 2 | The passkey, or both keys |
| Embedded wallets | Customer's passkey (2), your provider key (1), recovery provider (1) | 2 | The customer, or both providers |
| Company treasury | Three approvers (1 each) | 2 | Any two |

- **Getting started** survives a lost passkey, but either signer can pay alone, so keep both with the customer. Move customers to the customer accounts setup before they hold large balances.
- **Customer accounts** is multi-factor approval. Signer changes, new devices, and payments beyond a device key's limits need the passkey, which only the customer's device holds, or both keys together.
- **Embedded wallets** keeps each provider below the threshold. Neither can pay without the customer or the other provider.

Walkthroughs: [Set up self-custody](/docs/accounts/guides/self-custody) and [Set up a company treasury wallet](/docs/accounts/guides/company-treasury).

## Collect approvals from several approvers

Each approval is a signature over the same transaction hash, so approvers sign separately, on their own devices, in any order. The first approver starts the transaction, and the others approve its hash:

```ts [approve.ts]
const { receipt } = await client.accounts.updateConfigSync({ account, nextConfig, owner: finance }) // starts a signer update
await client.sendTransactionSync({ account, hash: receipt.transactionHash, owner: operations })
```

A relay with `Relay.accounts` holds the approvals and submits once they reach the threshold. Tempo rejects signatures beyond the threshold, so stop collecting once it's met. A signer change voids approvals collected for the old configuration.

<span id="receive-policies" />

## Receive policies

A signing threshold controls what leaves the account. A receive policy controls what arrives: which TIP-20 tokens the address accepts and which senders can pay it. Tempo holds blocked payments for a recovery authority to claim. See [Receive policies](/docs/guide/payments/configure-receive-policies).

## Verify approvals

Your contract or backend can check that an account approved a message, against the account's signers and threshold.

| To check that | Use | Runs |
| --- | --- | --- |
| An account's signers reached its threshold | `verifyMultisig` | In a contract |
| An active access key of an account signed | `verifyKeychain` | In a contract |
| A passkey or key signed | `verify` | In a contract |

<span id="verify-an-account-approval-in-solidity" />

The [signature verifier precompile](/docs/protocol/tips/tip-1020) at `0x5165300000000000000000000000000000000000` checks that signers reaching the account's current threshold approved `hash`:

```solidity [ApprovalCheck.sol]
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface ISignatureVerifier {
    function verifyMultisig(address account, bytes32 hash, bytes calldata signature) external view returns (bool);
}

contract ApprovalCheck {
    ISignatureVerifier constant VERIFIER = ISignatureVerifier(0x5165300000000000000000000000000000000000);

    function isApproved(address account, bytes32 hash, bytes calldata signature) external view returns (bool) {
        return VERIFIER.verifyMultisig(account, hash, signature);
    }
}
```

- It checks the account's signers at call time, so approvals from removed signers fail.
- It works for accounts that haven't sent a transaction yet, against their initial signers.
- It returns `false` when the signers don't match the account, and reverts with `InvalidSignature()` when approvals fall short.
- Include your chain ID, contract address, and the account in `hash`, so an approval can't be replayed elsewhere.
- `verifyKeychain` accepts only access keys that sign with a single key. A configurable account signing as an access key, such as a team budget, reverts with `InvalidFormat()`.

## Signing threshold limits

| Limit | Value |
| --- | --- |
| Signers per account | 1 to 48 |
| Total weight | Up to 255 |
| Approvals per transaction | Up to 8, so the eight largest weights must reach the threshold |

- A signer update voids approvals collected for the old configuration. Approve again.
- Tempo can't tell whether a signer still holds its key. Have each new signer approve once before you rely on it.
