# Embedded wallets

If you're using an embedded wallet, your provider most likely creates a single-key account for each user and holds its key for them.

Privy, Turnkey, and Dynamic each hold one key per user, so each user's wallet is a [single-key account](/docs/accounts/how-it-works#address) that works on Tempo mainnet and testnet as it is. All three also send [Tempo Transactions](/docs/guide/tempo-transaction), so your app can pay fees in any stablecoin, batch payments, sponsor your users' fees, and give out [access keys](/docs/accounts/access-keys).

## Keep your existing provider wallets

If your users already have wallets with Privy or another provider, you don't create new accounts. Each wallet's secp256k1 key gives it the same address on Tempo as on other EVM chains, though balances on other chains don't carry over. Sending and receiving stablecoins works as it is. Fee tokens, batched calls, and access keys need the provider's Tempo integration, which sends Tempo Transactions. Privy's standard EVM `sponsor: true` option isn't available for Tempo Transactions ([Wallet partners](/docs/partners/wallets)), so sponsor fees with your own [fee payer](/docs/accounts/fees/fee-sponsorship).

## What your provider sets up

Each user gets one secp256k1 key, which the provider holds and unlocks when the user logs in. That key controls the whole balance, so whoever the provider lets ask it to sign can move it: the user after they log in, or your backend under the provider's policies. Because the key is secp256k1, the account's own key can't be a passkey or device key.

## What Tempo adds

Any provider that signs Ethereum transactions can hold and send stablecoins on Tempo ([EVM compatibility](/docs/quickstart/evm-compatibility)). It supports Tempo Transaction features only if it sends Tempo Transactions itself, or signs a transaction's raw hash so your app can send it to a Tempo RPC. Privy, Turnkey, and Dynamic do both:

| Provider | Sends Tempo Transactions | Signs raw hashes |
| --- | --- | --- |
| [Privy](https://docs.privy.io/wallets/using-wallets/tempo/send-a-transaction) | Yes, with calls, fee token, nonces, and sponsorship | `secp256k1_sign`, or `raw_sign` on server wallets |
| [Turnkey](https://docs.turnkey.com/features/networks/overview) | Yes, through `sign_transaction`, which its policies can inspect | `sign_raw_payload` with no hash function |
| [Dynamic](https://www.dynamic.xyz/docs) | Yes, through its Tempo SDK extension | `signRawMessage` |

### Give your backend or an agent an access key

Give your backend or agent an access key that the user's wallet signs, never the user's key. The access key carries a spending limit, a list of recipients, and an expiry, and Tempo enforces those bounds on every payment the key signs. Your card program can then pull each purchase from the user's balance on every swipe, and an agent can pay on the user's behalf, without the embedded wallet signing each payment.

The user's wallet signs once, through the provider's raw-hash call or the [Accounts SDK](https://accounts.tempo.xyz/docs). [Authorize access keys from an embedded wallet](/docs/accounts/guides/users/authorize-access-keys-from-an-embedded-wallet) walks through it with Privy or Turnkey.

### Route raw signing through one backend

The provider's policy engine can't read a raw hash, so it can't tell a key authorization from any other request. Route raw signing through one backend service that builds each authorization and checks its key, limits, scopes, and expiry before calling the provider. To keep authorization inside the policy engine instead, send a Tempo Transaction that calls `authorizeKey` on the [Account Keychain](/docs/protocol/transactions/AccountKeychain) through the provider's transaction API.

### Plan recovery that doesn't depend on the provider

Make the provider's key one of three signers, next to the user's passkey and a backup key the user keeps, with any two approving. The passkey and the provider sign each payment together. If your app or the provider is down or breached, the user's passkey and backup still pay, recover, or remove the provider's key, so neither you nor the provider can move funds alone. See [Set up a self-custodial wallet with a provider](/docs/accounts/guides/users/self-custodial-wallets). It uses a configurable account, which works only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet).
