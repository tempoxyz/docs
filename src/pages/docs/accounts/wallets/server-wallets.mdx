# Server wallets

Backends that sign with a KMS key or a Privy or Turnkey server wallet work on Tempo as they are.

A payout service, a card program, or an agent moves money on its own, often with a key in a KMS or HSM. Any key that signs Ethereum transactions can send stablecoins on Tempo, on mainnet and testnet today. On Tempo, that key can also be an access key with a spending limit, a list of recipients, and an expiry. Give your backend one, so a compromised server can pay only within those bounds.

## Give the backend an access key, not the account key

Keep the account's own key with the user, and give your backend an [access key](/docs/accounts/access-keys) with a [spending limit](/docs/accounts/access-keys/spending-limits), a list of [recipients](/docs/accounts/access-keys/scopes), and an [expiry](/docs/accounts/access-keys/expiry). The backend then pays without asking the user each time. [Pay out from a backend](/docs/accounts/guides/automations/pay-out-from-a-backend) walks through it.

## Sign with a KMS key

AWS KMS and Google Cloud KMS keys work as access keys, and the private key never leaves the KMS. Access keys sign [Tempo Transactions](/docs/guide/tempo-transaction), so the key signs a 32-byte digest. Both KMSs sign digests with secp256k1 and P-256 keys, and both curves work as access keys. Wrap the KMS signing call as a viem account, as in [Keep the key in your KMS](/docs/accounts/guides/automations/pay-out-from-a-backend#keep-the-key-in-your-kms).

## Sign with a server wallet

Privy server wallets and Turnkey both sign Tempo Transactions and raw hashes:

| Provider | How it signs on Tempo |
| --- | --- |
| [Privy](https://docs.privy.io/wallets/using-wallets/tempo/send-a-transaction) server wallets | Sends Tempo Transactions through its wallet API, or signs raw hashes with `raw_sign` |
| [Turnkey](https://docs.turnkey.com/features/networks/overview) | Signs Tempo Transactions with `sign_transaction`, which its policies can inspect, or raw hashes with `sign_raw_payload` |

To use one as an access key, wrap its raw-hash signing as a viem account, as in [Authorize access keys from an embedded wallet](/docs/accounts/guides/users/authorize-access-keys-from-an-embedded-wallet#wrap-the-providers-signing-as-an-account).

## Rotate and revoke backend keys

Save each access key's address with the service that holds it. To rotate, authorize a new key, switch the service to it, then [revoke](/docs/accounts/access-keys/revocation) the old one. A key can't be extended past its expiry, so [renew it](/docs/accounts/access-keys/expiry#renew-an-expiring-key) before then.
