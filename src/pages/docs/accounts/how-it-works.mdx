# How it works

A Tempo account is an address with rules about who can move its funds. Signers approve together by weight, access keys pay alone within limits, and Tempo checks both on every transaction. Tempo has no admin key or override, so only the keys the account lists can move its funds.

This page follows one account with three signers: a passkey on the customer's phone, a backup key the customer keeps in a hardware wallet, and a recovery key in your KMS. Any two can approve. A payout server also holds an access key with a daily limit.

## Address

<AccountDiagram
  name="address"
  alt="An address is either a single-key account (EOA) with one key, or a configurable account with weighted signers and a threshold. Both kinds have TIP-20 balances, access keys, and a fee token."
/>

The address is the account's public identifier. It holds the account's TIP-20 balances and sets the account's default [fee token](/docs/accounts/fees). It's one of two kinds:

| Kind | Who approves |
| --- | --- |
| Single-key account | One key, as on other EVM chains. [Upgrade it](/docs/accounts/key-rotation/account-upgrade) to a configurable account at the same address. |
| Configurable account | [Signers](#signers) with weights and a threshold. Its address comes from its first configuration and never changes as signers change. |

The example account is configurable, so the customer keeps the same address when they replace a lost phone or rotate the recovery key. Either kind can have [access keys](#access-keys).

## Signers

<AccountDiagram
  name="signers"
  alt="A signer has a weight and is one of three types: private key, device key, or passkey. The sum of approving signers' weights must reach the threshold."
/>

Signers approve payments and account changes. Each signer has an auth type and a weight, and a transaction executes once signers whose weights reach the threshold approve it. In the example, each signer has weight 1 and the threshold is 2, so the passkey and the backup key can pay together, and the recovery key can stand in for either one.

Each auth type has its own [authentication](/docs/accounts/authentication) guide:

- [Private keys](/docs/accounts/authentication/private-keys)
- [Device keys](/docs/accounts/authentication/device-keys)
- [Passkeys](/docs/accounts/authentication/passkeys)

Only signers can change signers and the threshold. A change voids approvals collected for the old configuration.

## Access keys

<AccountDiagram
  name="access-keys"
  alt="An access key has a key type (passkey, P-256, or secp256k1), spending limits per TIP-20 token that apply once or per period, an expiry, and scopes over contracts, functions, and recipients. An admin access key has no limits and manages other access keys."
/>

Collecting two approvals for every payout is too slow for a server. An access key pays on its own, with no signer approval, and Tempo enforces its bounds instead. Each access key is a passkey, a P-256 key, or a secp256k1 key.

| Bound | What it sets |
| --- | --- |
| Spending limits | How much of each TIP-20 token the key can spend, once or per period |
| Expiry | When the key stops working |
| Scopes | Which contracts, functions, and recipients it can call |

The example payout server's key can spend up to its daily limit, only until it expires, and only on the calls its scopes allow. An admin access key has no bounds and manages the account's other access keys instead. Access keys never count toward the threshold.
