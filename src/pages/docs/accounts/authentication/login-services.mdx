# Login services

OIDC logins, including email, SMS, and Privy, depend on these services. Private keys, device keys, and passkeys don’t.

## How a login approves

<AccountDiagram
  name="login"
  alt="The customer's device holds the key. Its ID token becomes a proof, and Tempo checks the proof and the device's signature. Only the device holds a key."
/>

1. **The customer's device creates a key.** It never leaves the device.
2. **The identity provider issues an ID token that names that key**, so the token approves nothing without a signature from the device.
3. **The salt service and prover turn the token into a zero-knowledge proof.** The token never goes on chain, and the account lists the login by a salted ID that doesn't reveal who the customer is.
4. **Tempo verifies the proof** against the provider's keys in the key publisher, plus the device's signature.

The first payment carries this approval and also authorizes the device key as an access key, so later payments carry only the device's signature. No server holds a key for the customer, so whoever runs the salt service or prover can't move funds. Two parties can still sign in as a customer: the identity provider and the key publisher owner. Pair each login with a passkey the customer holds.

## What each service does

| Service | What it does | Who runs it | What you trust it to do |
| --- | --- | --- | --- |
| Identity provider (issuer) | Signs the customer's ID token. For email codes, SMS codes, and Privy, this is your auth service: it sends the code, or checks the Privy token against Privy's keys, then signs its own RS256 ID token. | The provider, such as Google, Apple, Microsoft, Auth0, or WorkOS. You, for email, SMS, and Privy. | Sign tokens only for customers who signed in |
| Salt service | Checks the ID token, derives the customer's salt from a secret salt key, and requests the proof from the prover. The salt fixes the account address and hides who it belongs to. | Anyone: you, your wallet provider, or another operator, with viem's `Relay.oidc` | Keep the salt key secret and backed up. Losing it locks customers out, and leaking it links addresses to identities. |
| Prover | Proves the ID token in zero knowledge, so the token never goes onchain. | Anyone: you, your wallet provider, or another operator | Keep the tokens it proves private |
| Key publisher | An onchain registry that lists the identity provider's signing keys. Tempo checks each proof against them. | Anyone, with [`keyPublisher.create`](/docs/accounts/authentication/oidc#publish-your-providers-keys). Own your identity provider's publisher yourself. | List only the provider's real keys |
| Fee payer | Pays a new account's first transaction fee, so the account needs no balance. See [Sponsor fees](/docs/guide/payments/sponsor-user-fees). | Anyone: you, your wallet provider, or another operator, with viem's `Relay.feePayer` | Pay fees, and nothing else |

None of these services holds a key for the customer. The ID token names the customer's device key, and Tempo checks the proof on chain, so whoever runs the salt service, prover, or fee payer can't move the customer's funds. See [How a login approves](#how-a-login-approves).

The demos on these pages use a local auth service and salt service on `localhost:5173`.

:::warning
The salt service and prover run against Tempo devnet only, with a development proving key. Proofs there aren't a security boundary.
:::

## Run your own salt service

Host the salt service and fee payer with viem's `Relay`, a small server helper that mounts the `Relay.oidc` and `Relay.feePayer` plugins.

```ts [salt-service.ts]
import { http, type Hex } from 'viem'
import { privateKeyToAccount } from 'viem/accounts'
import { tempoModerato } from 'viem/chains'
import { createClient, Relay, Store, withRelay } from 'viem/tempo'

const env = (name: string) => process.env[name] as Hex
const store = Store.memory()

export const client = createClient({
  chain: tempoModerato,
  transport: withRelay(http(), {
    plugins: [
      Relay.oidc({
        audiences: ['1234567890-abc.apps.googleusercontent.com'], // your OAuth client IDs
        issuers: ['https://accounts.google.com'],
        prover: { apiKey: process.env.PROVER_API_KEY!, url: 'https://prover.example.com' },
        publisherId: env('PUBLISHER_ID'), // part of every address: never change it
        saltKey: env('SALT_KEY'),
      }),
      Relay.feePayer({ account: privateKeyToAccount(env('FEE_PAYER_KEY')) }),
      // Replace Store.memory() with a persistent Store.Atomic shared by every instance.
      Relay.keyAuthorization({ store }),
      Relay.accounts({ store }),
    ],
  }),
})
```

`Relay.keyAuthorization` stores signed access-key authorizations, including a configurable account's once they reach quorum, and attaches each to the key's next transaction. `Relay.accounts` serves account configurations, such as `client.accounts.getConfig`. Both need a persistent `Store.Atomic` shared by every relay instance.

Pass the same plugins to `Relay.create({ client, plugins })` and serve `relay.fetch`. Create the salt key once with `echo "0x$(openssl rand -hex 32)"` and keep it in a secret manager with a backup: it fixes every customer's address.

Keep request bodies out of logs, rate limit `oidc_prove` per client, limit what the fee payer sponsors with its `validate` option, and allow CORS only from your app's origin.

Build it with viem: [Run a salt service](https://viem-d07zjc3q1-wevm.vercel.app/tempo/guides/oidc/salt-service) covers the salt service, fee sponsorship, and browser CORS.

## What each service can and can't do

| Service | Can | Can't |
| --- | --- | --- |
| Identity provider (issuer) | Sign in as any of its users | Approve alone, if its login's weight is below the threshold |
| Key publisher owner | List any key, and so sign in as any customer whose login names its publisher | Approve alone, if that login's weight is below the threshold |
| Salt service | See ID tokens, link logins to account addresses, and delay or refuse service | Sign for a customer, unless it's also the issuer |
| Prover | See the ID tokens it proves, and delay or refuse service | Sign for a customer |
| Fee payer | Pay fees, and delay or refuse service | Approve or move funds |

The salt service, prover, and fee payer can't change or forge an approval, change an access key's limits, or redirect a sign-in to another key: each login commits to the customer's device key.

Pair each login with a passkey the customer holds, and use logins from different issuers, so no single issuer approves alone. See [Policies](/docs/accounts/security-policies).

For other sign-in methods, see [Authentication](/docs/accounts/authentication).
