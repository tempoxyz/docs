# Security

No one, including Tempo, can move an account's funds without the account's keys.

Tempo enforces each account's rules on every transaction. A breach of your app, your backend, or a wallet provider exposes only the keys that party holds, within those keys' bounds. Your security decision is who holds which keys.

<span id="how-tempo-enforces-an-accounts-rules" />

## Onchain enforcement

An account's rules are part of Tempo's protocol rules, so every validator checks them: the signatures the account requires, its [signing threshold](/docs/accounts/policies/signing-thresholds), each [access key's](/docs/accounts/access-keys) spending limits, scopes, and expiry, and its [receive policy](/docs/accounts/policies/receive-policies). A transaction that breaks any of them never lands. No validator or operator, including Tempo, can skip these checks.

Tempo is a blockchain run by a distributed set of validators, not a single sequencer. Each validator checks every block against the protocol's rules before agreeing to it. A block is [final](/docs/protocol/blockspace/consensus) once enough validators agree. A finalized block can't be reverted, so a confirmed transaction can't be changed or undone. These guarantees hold while fewer than a third of validators misbehave.

<span id="who-can-move-the-funds" />

## Fund control

Whoever holds keys that reach an account's threshold can move its whole balance. In every setup, access key holders pay only within their bounds.

<ConfigurableAccountsT14 />

| Setup | Who can move the whole balance |
| --- | --- |
| Embedded wallet in an [app](/docs/accounts/apps) | Whoever the provider lets sign with the account's key, such as the customer after they log in, or your backend under the provider's policies |
| Backend key for an [automation](/docs/accounts/automations) | Your backend, if it holds the account's key. Give it an access key instead, so it pays only within limits. |
| [Custodian](/docs/accounts/custodians) | The custodian, under the policies you set with it |
| Browser or hardware [wallet](/docs/accounts/wallets) | The user, who holds the account's one private key |
| [Configurable account](/docs/accounts/policies/signing-thresholds) | Signers whose weights reach the threshold together. In the [recommended setups](/docs/accounts/policies/signing-thresholds#recommended-signer-setups), no outside party reaches it alone. |

<span id="what-your-app-is-responsible-for" />

## App responsibilities

Tempo checks what a key signs, not whether the right person holds the key. Your app owns four decisions:

- **Where keys live.** Keep a passkey or device key on the customer's device, and backend keys in a KMS or HSM.
- **Which signers your app holds.** Every signer your app or wallet provider holds is weight an attacker gets by breaching you. On a configurable account, keep your combined weight below the threshold, and count parties, not keys ([what a threshold protects against](/docs/accounts/policies/signing-thresholds#what-a-threshold-protects)).
- **Each account's configuration.** Tempo stores only a hash of a configurable account's signers, weights, threshold, and version. Save the configuration with the account record, and replace it after every configuration update. Without it, the signers can't approve ([keep the current configuration](/docs/development/configurable-accounts#keep-the-current-configuration)).
- **What gets signed.** A wallet provider's policy engine can't read a raw hash. It can't tell a key authorization from a payment. Check the key, limits, scopes, and expiry in your own backend before asking the provider to sign ([who can move the funds](/docs/accounts/apps#who-can-move-the-funds)).

<span id="if-a-key-or-service-is-compromised" />

## Compromised keys and services

Revoke the keys the breached party held. On a configurable account, use the remaining signers to replace any signer the attacker reached.

| Compromise | What an attacker can do | What you do |
| --- | --- | --- |
| Lost device | Pay with the device's access key, within its limits, until it expires. A passkey on the device still needs the device's unlock. | [Revoke](/docs/accounts/access-keys/revocation) the device key. On a configurable account, the other signers [replace the passkey](/docs/accounts/apps/recover-an-account). On a single-key account whose only key was on the device, no one can recover the funds. |
| Leaked access key | Spend up to the key's remaining [spending limit](/docs/accounts/access-keys/spending-limits), only to the contracts and recipients in its [scopes](/docs/accounts/access-keys/scopes), until its [expiry](/docs/accounts/access-keys/expiry). A leaked [admin access key](/docs/accounts/access-keys/admin-access-keys) can spend the whole balance and authorize new keys. | Revoke the key. For an admin key, also revoke every key it authorized. Set any token approvals it made to zero ([what revocation leaves in place](/docs/accounts/access-keys/revocation#what-revocation-leaves-in-place)). |
| Breached backend | Use every key the backend holds: access keys within their bounds, and any signer at its weight. If the backend holds a single-key account's key, it can move the whole balance. | Revoke its access keys and authorize new ones. On a configurable account, the other signers [remove the backend's signer](/docs/accounts/account-configuration/configuration-updates#remove-a-lost-or-compromised-signer). For a single-key account, move the funds to a new account. |
| Breached wallet provider | On a single-key embedded wallet, sign anything with the account's key and move the whole balance. On a configurable account where the provider's key is [one signer](/docs/accounts/apps/self-custodial-wallets), approve only at that key's weight, which can't reach the threshold alone. | On a configurable account, the customer's passkey and backup remove the provider's signer. On a single-key account, move the funds to a new account once you control signing again. |
| Your app or wallet provider is down | Nothing new, but customers can't sign through you. | On a configurable account where the customer holds two signers, they [pay or leave without you](/docs/accounts/apps/self-custodial-wallets#if-something-goes-wrong). On a single-key embedded wallet, customers wait until the provider is back. |
| Lost saved configuration | Nothing. The configuration lists signer addresses and weights, not keys. | Restore it from a backup. After a configuration update, each `MultisigConfigUpdated` event carries the new configuration, so you can rebuild a lost copy from the latest one. For an account that has never been updated, your saved copy is the only record, so back it up. |

On a configurable account, a configuration update leaves the account's access keys in place. After replacing a signer, list every key the account has authorized and [revoke the ones its old holder could use](/docs/accounts/access-keys/revocation#revoke-when-signers-change).

## Post-quantum accounts

A [configurable Tempo account](/docs/development/configurable-accounts) can change the keys behind its address, so a switch to quantum-safe signatures doesn't mean moving funds.

A large enough quantum computer could forge the signatures that protect crypto accounts today. That includes the secp256k1 keys in Ethereum wallets and the P-256 keys behind passkeys.

<span id="what-a-new-key-costs-on-most-chains" />

### Key changes on other chains

An account's address ends up in many places: customers save it, exchanges and banks allowlist it, payment providers hold token approvals from it, and your own records use it to identify the account.

On Ethereum, an address is computed from its public key, so a new key is a new address. Moving to a quantum-safe key means creating a new address and moving every balance to it. It means granting every token approval again and asking every counterparty to update what they've saved. Every account on the network has to do the same, before quantum computers can break the old keys.

<span id="how-a-tempo-account-keeps-its-address" />

### Stable addresses on Tempo

A configurable account's address is computed from the account's first configuration, not from any one key ([configurable account address](/docs/development/configurable-accounts#configurable-account-address)). Its signers are a list the account changes through configuration updates. The address stays the same through every change.

A [single-key Tempo account](/docs/development/single-key-accounts#single-key-address-derivation) works like an Ethereum account: its key fixes its address. It can [upgrade in place](/docs/accounts/account-configuration/account-upgrade) to a configurable account at the same address.

<span id="switching-an-account-to-quantum-safe-keys" />

### Migration to quantum-safe keys

1. **Upgrade the account in place.** A single-key account's original key signs one upgrade, and the account becomes a configurable account at the same address. From then on, the original key approves only if you list it as a signer.
2. **Add a quantum-safe signer.** Once Tempo supports a quantum-safe key type, [add a signer](/docs/accounts/account-configuration/configuration-updates#add-a-signer) with that key type.
3. **Remove the old keys in the same update.** The old keys approve one update that adds the new signer and [removes the old ones](/docs/accounts/account-configuration/configuration-updates#remove-a-signer) together. No old key controls the account afterward. The address, balances, and token approvals don't change, and counterparties do nothing.
4. **Replace access keys.** An [access key](/docs/accounts/access-keys) that signs with an old key type is as breakable as the account's old signers. Revoke each one, such as a backend's or an agent's, and authorize a quantum-safe replacement without touching the account's signers.

Tempo accounts already support upgrading, removing signers, and replacing access keys. Only step 2, adding a quantum-safe signer, isn't built yet.

<span id="what-a-quantum-safe-key-type-needs" />

### Protocol requirements

Tempo accounts accept secp256k1, P-256, and passkey (WebAuthn) signatures today. A large enough quantum computer could break all three. Supporting a quantum-safe key type, such as ML-DSA (standardized by NIST in FIPS 204), is a protocol change with three parts:

- **A new signature type.** Accounts list it as a signer, and access keys sign with it.
- **Room for larger signatures.** A secp256k1 signature is 65 bytes, and Tempo accepts passkey signatures of up to 2,049 bytes ([signature types](/docs/protocol/transactions/spec-tempo-transaction)). An ML-DSA-65 signature is 3,309 bytes, and its public key adds 1,952 more. Transaction size limits and fees have to allow for them.
- **A way to stop accepting old signatures.** Removing old signers covers the account's own keys. Access keys and token permits signed with old key types also have to stop working. Otherwise, a forged old-style signature could still spend from the account.

<span id="why-the-switch-has-to-happen-early" />

### Timing

Changing keys only protects an account while its old keys are still safe. Once an attacker can work out a private key from its public key, the attacker and the real owner look the same to Tempo. Accounts need to retire their old keys before those keys can be broken.

A retired key can also still act outside the account's own rules:

- **On other chains.** A secp256k1 key controls the same address on other EVM chains, whatever happens to it on Tempo.
- **In contracts that check signatures themselves.** Contracts such as Permit2 verify signatures on their own, so they may still accept the original key ([what an upgrade changes](/docs/accounts/account-configuration/account-upgrade#what-an-upgrade-changes)).
