# Validator failover

Move your validator to a replacement host while preserving its identity and consensus state. Choose the procedure that matches the state you have available:

| Deployment | Recovery path |
| --- | --- |
| Bare metal with recoverable disks | [Restore the complete disk state](#restore-bare-metal-validator), including execution and consensus data. |
| Cloud with local execution disks | [Transfer the consensus directory](#restore-a-cloud-validator) and use sufficiently recent execution state. |
| Synced standby follower | [Transfer the consensus directory](#restore-a-cloud-validator) and use its existing execution state. |

:::danger[Prevent double-signing]
Only one node may run with a validator signing key at a time. Before starting the replacement, fence the old validator: stop it and prevent automatic restarts.
:::

<span id="preserve-validator-identity-and-networking" />

Reuse the validator's signing key, latest complete consensus directory, and registered ingress and egress addresses. If the addresses change, [update them onchain](/docs/guide/node/validator-rotation#update-ip-addresses) and wait for finalization before starting the replacement. If consensus state is lost, follow [resetting validator data](/docs/guide/node/validator-lifecycle#resetting-your-validators-data).

<span id="restore-bare-metal-disk-state" />

## Restore bare-metal validator

When the disks survive a host failure, restore execution and consensus data together on the replacement host.

:::::steps

### Fence the failed host

Stop the validator and prevent it from restarting. If the host is unreachable, fence it through your infrastructure before bringing up the replacement.

```bash
sudo systemctl stop tempo
```

### Restore the complete data directories

Move or restore the disks containing the full `--datadir` directory, including consensus state. If you use `--consensus.datadir`, restore that directory too.

Copy or mount files only after the source process has stopped. Keep the latest consensus state; if execution data comes from an older backup, apply the [execution recovery window](#execution-recovery-window) requirements below.

### Start the replacement validator

Restore [signing-key access](/docs/guide/node/validator-keys) and registered networking, then start the existing validator service with the same node version and restored data directories.

```bash
sudo systemctl start tempo
```

Verify [consensus participation](/docs/guide/node/validator-monitoring#consensus-states) on the replacement.

:::::

## Restore a cloud validator

Both paths transfer the active validator's complete consensus directory. A fresh replacement restores execution state from a snapshot or backup; a synced standby reuses its existing execution database.

### Prepare cloud consensus storage

Keep execution data on [local NVMe storage](/docs/guide/node/system-requirements) and consensus data on a persistent network-attached volume that you can detach and attach to a replacement host. Use `--consensus.datadir` to select the consensus directory on that volume.

The following example uses mainnet. Use `--chain moderato` for testnet. Provision and mount the volume before starting the service. Keep the other flags from your existing validator configuration, including `--consensus.secret` for an encrypted signing key.

```bash
tempo node \
  --chain mainnet \
  --datadir <EXECUTION_DATADIR> \
  --consensus.datadir <CONSENSUS_DATADIR> \
  --consensus.signing-key <PRIVATE_KEY_PATH> \
  --consensus.listen-address 0.0.0.0:<REGISTERED_INGRESS_PORT>
```

To migrate an existing validator to this layout, stop it, copy its complete consensus directory to the mounted volume, update `--consensus.datadir`, and restart. Configure the service to require the volume mount so it cannot start against an empty local directory when the volume is unavailable. Allow only the active validator to write to this volume.

### Execution recovery window

The consensus volume retains recent finalized blocks that the replacement can replay into its execution database. This matters when local execution disks are lost and the replacement starts from a snapshot or an older execution backup. A synced follower already has recent execution state, so it avoids most or all of this replay.

The default retention window is about ~3 epochs worth of blocks, roughly ~9hrs worth of data (500ms block times). This means the execution disk can be 9 hours behind the previously active validator and startup fine. Any longer would and the failover node would fail to startup. Recently downloaded snapshots will also always fall within this range.

A larger retention window means a larger required consensus disk volume. If your failover procedure always involves using a standby follower node that is in sync, the retention window can be shortened to accomadate a smaller consensus disk via the `--consensus.finalized-blocks-retention` flag. A reasonable default in this circumstance is `16_384`, leaving ~2hrs window to succesfully failover.

Test this handoff before relying on it in production.

### Restore the replacement

:::::steps

#### Fence the old validator

<span id="fence-the-old-instance-and-release-its-volume" />

Fence the old validator and disable any automation that could restart it. Stop the source process before copying its consensus directory. If transferring a network-attached volume, detach it using your cloud provider's procedure once the old host can no longer write or sign. Keep the entire consensus directory intact.

#### Prepare execution state on the replacement

<span id="restore-execution-state-on-the-replacement" />
<span id="prepare-a-follower" />
<span id="promote-the-follower" />

Use the same node version and chain configuration as the old validator.

**For a [synced standby](/docs/guide/node/rpc):** stop the follower cleanly and wait for it to exit. Keep its existing execution `--datadir`; use that path as `<EXECUTION_DATADIR>` below. No snapshot download is needed.

```bash
sudo systemctl stop tempo-follower
```

**For a fresh replacement:** restore a recent execution backup or download a minimal snapshot into a new local data directory. This example uses mainnet; use `--chain moderato` for testnet.

```bash
tempo download --chain mainnet --minimal --datadir <EXECUTION_DATADIR>
```

Download the snapshot before attaching the preserved consensus volume. The download installs its own consensus data under the local data directory; the validator uses the preserved volume instead when started with `--consensus.datadir`.

:::danger[Protect the preserved consensus state]
Do not point `tempo download --consensus.datadir` at the preserved volume. In particular, `tempo download --force` removes existing consensus data at its destination. If replacing a failed download, use a separate local directory and leave the preserved volume untouched.
:::

#### Transfer the validator's consensus directory

<span id="attach-the-preserved-consensus-volume" />

Attach and mount the preserved volume, or copy the stopped validator's complete consensus directory to the replacement. Use `<CONSENSUS_DATADIR>` for this directory. Keep it separate from any consensus directory created by the follower or snapshot; do not merge their files.

A follower's own consensus archive does not contain the active validator's private signing state. Using it can delay signing participation until the node recovers a share. Transfer the active validator's latest complete directory to preserve that state.

#### Start with both data paths

Start the validator with the [storage configuration above](#prepare-cloud-consensus-storage), using the replacement's local `--datadir`, the transferred `--consensus.datadir`, and the old validator's signing key. Remove `--follow` if reusing a follower's service configuration. Keep the retention setting in the service configuration.

If startup fails with an error reporting insufficient execution state, restore fresher execution state, either by [syncing a follower](/docs/guide/node/rpc) or by downloading a fresh snapshot.

Verify [consensus participation](/docs/guide/node/validator-monitoring#consensus-states) on the replacement.

:::::

## After failover

Confirm [validator status](/docs/guide/node/validator-status) and [consensus participation](/docs/guide/node/validator-monitoring#consensus-states) on the replacement.

Treat the replacement as the active validator until you intentionally move the role again. Prevent the old host from restarting in validator mode. You can repurpose it as a follower and future standby by configuring `--follow` without `--consensus.signing-key` or `--consensus.secret`.

Follower mode still requires a consensus archive when the execution database contains finalized blocks. If the consensus directory moved to the replacement, adding `--follow` to the old host's existing execution database is not enough to start it.

If the old host's consensus volume is empty, follow [Running RPC and Standby Nodes](/docs/guide/node/rpc) to set it up as a follower.

Keep the active validator's consensus volume attached exclusively to the active instance.
