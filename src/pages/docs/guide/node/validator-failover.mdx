# Validator failover

Move your validator to a replacement host with the same signing key and validator entry after the active host fails or must be retired. The recommended setup is the same on bare metal and in the cloud: one active validator, plus a replacement that can start from synced or snapshotted state.

## Recommended setup

| Deployment | Run | On failure |
| --- | --- | --- |
| Bare metal | One active validator, plus a second machine that meets the [validator requirements](/docs/guide/node/system-requirements#validator-node) and is ready to take over. Keep it running as a synced [follower](/docs/guide/node/rpc). | [Promote the follower](#promote-the-replacement). |
| Cloud | One active validator instance. A standby follower is optional. | Create a new instance from a [recent snapshot](/docs/guide/node/installation#snapshots), or promote the standby if you run one. |

Keep execution and consensus data on the same host, on local NVMe storage. Network-attached volumes (EBS, GCP Persistent Disk, Azure Managed Disk, NAS, SAN) are not recommended for consensus data and are [not supported](/docs/guide/node/system-requirements) for execution data. Do not plan failover around moving a consensus disk between hosts.

## What to expect during failover

A replacement verifies and follows the chain as soon as it starts, but it does not hold the old host's [signing share](/docs/guide/node/validator-keys#signing-share-recovery). It starts voting and proposing again after it receives a new share in the next DKG ceremony, typically **1–3 hours** after it starts, depending on where the current [epoch](/docs/guide/node/consensus-and-dkg) is. The network keeps finalizing blocks while your validator waits, as long as the rest of the committee has quorum.

This wait applies to every failover, on bare metal and in the cloud. Plan alerting and on-call around detecting a failure and starting the replacement quickly. The share wait is fixed by the network.

## Prepare before you need it

- **Signing key:** back up the validator's signing key and its encryption secret, and make sure the replacement host can retrieve them, for example from your secret manager.
- **Network addresses:** the replacement must use the validator's registered ingress and egress addresses. Use addresses you can move to a new host, such as a reserved, elastic, or floating IP. Otherwise [update them onchain](/docs/guide/node/validator-rotation#update-ip-addresses) during failover.
- **Version:** run the same `tempo` release and chain configuration on the replacement as on the active validator.
- **Monitoring:** alert on the validator's [health and consensus participation](/docs/guide/node/validator-monitoring) so you notice a failure quickly.
- **Optional: keep your own snapshots.** Periodically stop a synced follower and copy its complete data directory, execution and consensus data together, to storage inside your infrastructure. Restoring from it is usually faster than downloading a public snapshot and removes the dependency on Tempo's snapshot service.

## Promote the replacement

:::danger[Prevent double-signing]
Only one node may run with a validator signing key at a time. Before starting the replacement, fence the old validator: stop it and prevent automatic restarts.
:::

:::::steps

#### Fence the old validator

Stop the old validator and disable any automation that could restart it, such as a systemd unit, an orchestrator, or an autoscaling group. If the host is unreachable, cut it off at the network or power level before continuing.

#### Prepare execution state on the replacement

Use the same node version and chain configuration as the old validator.

**Bare metal, synced follower:** stop the follower cleanly and wait for it to exit. Its data directory is reused as the validator's.

```bash
sudo systemctl stop tempo-follower
```

If the follower is not managed by systemd, send `SIGINT` or `SIGTERM` and wait for the process to exit.

**Cloud, new instance:** download a minimal snapshot into an empty local data directory, or restore one of your own snapshots. Snapshots include the consensus certificates the node needs at startup.

```bash
tempo download --chain (mainnet|moderato) --minimal --datadir <DATADIR>
```

Do not start the validator with an empty consensus directory. If startup reports insufficient execution or consensus state, download a fresh snapshot.

#### Check the registered addresses

If the replacement does not use the old validator's ingress and egress addresses, [update them onchain](/docs/guide/node/validator-rotation#update-ip-addresses) and wait for the transaction to finalize before starting the replacement.

#### Start the validator

Start the node with the old validator's signing key and registered ingress port. Keep the other flags from your existing validator configuration, and remove `--follow` if you are reusing a follower's service configuration. The Bash/Zsh command below assumes an encrypted key: replace `<ENCRYPTION_KEY_CMD>` with the command that retrieves its encryption secret. Omit `--consensus.secret` only for an unencrypted key.

```bash
tempo node \
  --chain mainnet \
  --datadir <DATADIR> \
  --consensus.signing-key <PRIVATE_KEY_PATH> \
  --consensus.secret <(<ENCRYPTION_KEY_CMD>) \
  --consensus.listen-address 0.0.0.0:<REGISTERED_INGRESS_PORT>
```

#### Verify

Confirm the node is following the chain, then check [validator status](/docs/guide/node/validator-status) and [consensus participation](/docs/guide/node/validator-monitoring#consensus-states) after the next DKG ceremony. The node should report a signing share and resume voting within one epoch.

:::::

## After failover

Treat the replacement as the active validator until you intentionally move the role again. Never let the old host restart in validator mode.

Restore your failover capacity:

- **Bare metal:** repair or replace the old machine and run it as a follower with `--follow` and without `--consensus.signing-key` or `--consensus.secret`. It becomes the next failover node. If its data directory is lost, bootstrap it again from a snapshot as described in [Running RPC and standby nodes](/docs/guide/node/rpc).
- **Cloud:** delete the failed instance once the replacement participates in consensus.

To replace the validator's signing key instead of moving it, use [validator rotation](/docs/guide/node/validator-rotation).
