# Validator network topology

Run a production validator in an isolated network segment. Allow consensus traffic only between validators, and route execution P2P and transaction ingress through redundant internal follower RPC nodes.

:::info
These internal rpc nodes can also be used internally as a source of chain state. An alternative to `https://rpc.tempo.xyz`
:::

## Recommended Validator Topology

The validator has two types of network relationship:

- **Consensus P2P:** The validators communicates directly with the other Tempo validators
- **Execution P2P:** The validators peers with rpc nodes over TCP and UDP particpiating in transaction gossip.

The Execution P2P layer is open, thus we recommend peering the validator **only** with internally trusted rpc nodes as a layer of indirection. These rpc nodes configured to `--follow <VALIDATOR_JSON_RPC>` such that they locally sync in lockstep with the validator.

At least two of these rpc nodes should run alongside each validator to avoid a single point of failure for execution p2p traffic. The flow of Execution P2P traffic will looks something like this:

None of the validators P2P or RPC ports should be directly accessible to the internet.

## Validator firewall policy

Enforce the topology at the network firewall even when the node's peer configuration restricts discovery or has a fixed fixed peer list.

Firewall for the validator (default ports):

| Traffic | Source or destination | Port | Policy |
| --- | --- | --- | --- |
| Consensus P2P | Other Tempo validators | `8000/TCP` | Allow |
| Execution P2P | Internal RPC hosts | `30303/TCP` and `30303/UDP` | Allow |
| JSON_RPC | Internal RPC hosts | `8545/TCP` | Allow |
| All other inbound traffic | Any source | Any port | Deny |

Restrict the validator's execution peer configuration to the two internal follower RPC nodes. Do not rely on peer discovery alone to provide isolation.

## Validator Execution Peers

Each follower needs a stable and unique execution P2P identity. On each follower, print its `enode://` URL from the discovery secret that the node uses:

```bash
tempo p2p enode <FOLLOWER_DISCOVERY_SECRET>
```

Run the command once for each rpc node within the internal cluster. Each rpc node must have a unique discovery secret it uses to identify itself. Use the private IP of the rpc node that the validator uses to reach it.

Concatenate these `enode://` URLs, passed to the validator command:

```bash
tempo node <EXISTING_ARGUMENTS> \
  --disable-discovery \
  --trusted-only \
  --trusted-peers "enode://<FOLLOWER_A_PUBLIC_KEY>@<FOLLOWER_A_PRIVATE_IP>:30303,enode://<FOLLOWER_B_PUBLIC_KEY>@<FOLLOWER_B_PRIVATE_IP>:30303"
```

Each flags serves a purposes:

| Flag | Effect on the validator |
| --- | --- |
| `--trusted-peers` | Static list of trusted peers the node accepts connections from or tries to connect to |
| `--trusted-only` | Connects to and accepts execution P2P connections from trusted peers only. |
| `--disable-discovery` | Disables DNS, discv4, and discv5 peer discovery. |

Keep the firewall allowlist in place. The enode allowlist authenticates the followers' execution P2P identities, while the firewall restricts which private IPs can reach the validator's p2p port.

## Internal RPC nodes

Place both internal RPC nodes in a separate network segment from the validator. Configure each node to:

- Run in follow mode with `--follow` pointed at the validator's RPC endpoint.
- Participate in the public Tempo execution P2P network.

On startup, RPC nodes are configured to discover a starting set of peers from bootnodes and connect to new ones through p2p discovery. The p2p port for these RPC nodes should **not** sit behind a firewall as peer membership at this layer is open.

## Failure and maintenance considerations

Both follower RPC nodes are on the validator's transaction-ingress path. Monitor their execution peer counts, block heights, resource utilization, transaction-submission health, and private links to the validator.

Run the followers independently so either node can continue accepting and relaying transactions when the other is unavailable. Configure clients or an internal load balancer to remove an unhealthy follower from rotation. Verify that failure of either follower does not interrupt transaction submission through the remaining node.

## Validate the isolation boundary

After deployment or a firewall change, confirm that:

- Other validators can reach the validator's consensus port.
- Validator's execution peer count exactly matches the number of internal rpc nodes..
- Internet hosts cannot reach the validator on any ports.
- The validator cannot establish execution P2P connections to internet peers.
- Each follower is configured with `--follow` against the validator and remains synced.
- Transactions submitted through either follower reach the validator.
- Transaction submission continues after either follower is removed from service.
- Monitoring reaches both hosts only through the private monitoring network.

See [system requirements and ports](/docs/guide/node/system-requirements#ports), [validator monitoring](/docs/guide/node/validator-monitoring), and [node security](/docs/guide/node/security) for the related operational controls.
