# Tempo x402 facilitator

Sell over [x402](https://x402.org) and get paid in stablecoins on Tempo, with no change for buyers.

## Supported payment networks

| Direction | Network | Chain ID | Token | Schemes |
| --- | --- | --- | --- | --- |
| Pay in | Base mainnet | `eip155:8453` | [USDC](https://basescan.org/token/0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913) | `exact` (EIP-3009 or Permit2) |
| Pay out | Tempo mainnet | `eip155:4217` | [OUSD](https://explore.tempo.xyz/address/0x20c0000000000000000000006a37da5c996874be) | — |

- Payouts match the pay-in amount at par: USDC and OUSD both use 6 decimals.
- `GET /v1/x402/supported` lists what the facilitator accepts right now. It's public.
- Permit2 payments need an existing Permit2 allowance or an EIP-2612 permit. Tempo doesn't sponsor gas for an ERC-20 approval.

## How the Tempo x402 facilitator works

Your server calls the facilitator's `verify` and `settle` endpoints like any x402 facilitator. Buyers keep paying with any x402 client.

<MermaidDiagram chart={`sequenceDiagram
    participant Buyer
    participant Seller as Your server
    participant Tempo as Tempo facilitator
    Buyer->>Seller: Request resource
    Seller-->>Buyer: 402 Payment Required
    Buyer->>Seller: Retry with signed USDC
    Seller->>Tempo: Verify and settle
    Note over Tempo: Settle USDC on Base, send OUSD on Tempo
    Tempo-->>Seller: Base and Tempo hashes
    Seller-->>Buyer: Resource
`} />

- **Base settlement.** Every payment goes to one Tempo deposit address on Base, `extra.payTo` in `GET /v1/x402/supported`.
- **Tempo payout.** Tempo then sends the same amount in OUSD to the address in `extra.tempoSettlement`.
- **One payout per payment.** No batching. A retried settle returns the same result and never pays twice.
- **No fee today.** Tempo pays each payout's network fee and holds no balance for you.

## Accept x402 payments on Tempo

:::::steps

### Create an API key

Create a production API key in [Tempo Console](https://tempo.com/console?to=/:org/api-keys) with the `mpp:write` scope.

- Keep it on your server.
- Send it in the `tempo-api-key` header or as `Authorization: Bearer` on verify and settle.
- Sandbox keys get `403 production_api_key_required`. Testnet: coming soon.

```bash [Terminal]
export TEMPO_API_KEY="tempo:sk:..."
```

### Point your x402 middleware at Tempo

Set the facilitator URL to `https://api.tempo.xyz/v1/x402` with your API key, pay to Tempo's deposit address, and name your Tempo payout address in `extra.tempoSettlement`:

```bash [Terminal]
export TEMPO_PAYOUT_ADDRESS="0x..." # any Tempo address you control
```

```ts [Next.js]
import { HTTPFacilitatorClient, x402ResourceServer } from '@x402/core/server'
import { ExactEvmScheme } from '@x402/evm/exact/server'
import { withX402 } from '@x402/next'
import { NextResponse } from 'next/server'

const network = 'eip155:8453' // Base mainnet
const headers = { 'tempo-api-key': process.env.TEMPO_API_KEY! }

const facilitator = new HTTPFacilitatorClient({
  createAuthHeaders: async () => ({ settle: headers, verify: headers }),
  url: 'https://api.tempo.xyz/v1/x402',
})

const server = new x402ResourceServer(facilitator).register(network, new ExactEvmScheme())

// Tempo's deposit address on Base, read from GET /supported when the middleware starts
const payTo = () => server.getSupportedKind(2, network, 'exact')?.extra?.payTo as string

export const GET = withX402(
  async () => NextResponse.json({ forecast: 'sunny' }),
  {
    accepts: {
      extra: { tempoSettlement: process.env.TEMPO_PAYOUT_ADDRESS! },
      network,
      payTo,
      price: '$0.01',
      scheme: 'exact',
    },
  },
  server,
)
```

- The middleware answers unpaid requests with `402 Payment Required` and settles paid requests through Tempo.
- The x402 SDK reads `payTo` from `GET /v1/x402/supported` when the middleware starts. Verify refuses any other `payTo`.
- Payouts go to whatever `tempoSettlement` names. It must be a valid Tempo address, and it's screened.
- Price routes at any amount above 0, up to the per-payment maximum Tempo sets.

### Check the payout

Settle waits for the Base receipt, then returns a standard x402 settle response:

- `transaction` is the Base settlement hash.
- `extensions.tempoSettlement` is the Tempo payout. It's usually still `pending`: Tempo pays out once Base marks the settlement's block safe from reorgs, which takes minutes.

```json
{
  "success": true,
  "transaction": "0x<BASE_HASH>",
  "network": "eip155:8453",
  "payer": "0x<PAYER>",
  "extensions": {
    "tempoSettlement": {
      "transaction": null,
      "status": "pending",
      "network": "eip155:4217",
      "amount": "10000",
      "token": "0x20c0000000000000000000006a37da5c996874be",
      "to": "<TEMPO_PAYOUT_ADDRESS>",
      "payoutId": "x402pay_..."
    }
  }
}
```

Poll the payout by `payoutId` until `status` is `confirmed`:

```bash [Terminal]
curl https://api.tempo.xyz/v1/x402/payouts/<PAYOUT_ID> \
  --header "tempo-api-key: $TEMPO_API_KEY"
```

- `status` goes `pending`, `submitted` (broadcast on Tempo), then `confirmed`. `transaction` is the Tempo hash once set, and it never changes.
- `GET /v1/x402/settlements/<BASE_HASH>` returns the same payout by its Base hash.
- If settle answers `settlement_pending`, retry it with the same payload. It never pays twice.

## Tempo x402 facilitator API

All endpoints live under `https://api.tempo.xyz/v1/x402`. `GET /supported` is public; the others require an API key with the `mpp:write` scope.

| Endpoint | Description |
| --- | --- |
| `GET /supported` | Lists the schemes served. Each kind's `extra` carries the deposit address in `payTo`. |
| `POST /verify` | Checks an x402 payment without settling it. Takes the standard x402 facilitator body. |
| `POST /settle` | Settles the payment on Base and sends the Tempo payout. Returns both hashes. |
| `GET /payouts/{id}` | Returns a payout by `payoutId`. `status` is `pending`, `submitted`, `confirmed`, or `failed`. |
| `GET /settlements/{transaction}` | Returns the same payout, looked up by its Base settlement hash. |

- **Limits.** No minimum: any amount above 0. Tempo sets the maximum per payment.
- **Rate limits.** Settle is rate-limited per API key. Over the limit, it answers `429` with `Retry-After`.

## x402 payment refusals

Verify and settle answer HTTP `200` for payment-level refusals, with `isValid: false` or `success: false` and a reason:

| Reason | Meaning |
| --- | --- |
| `payto_not_deposit_address` | `payTo` isn't the deposit address from `GET /supported`. |
| `missing_tempo_settlement` | `extra.tempoSettlement` is missing, isn't a valid Tempo address, or is the zero or deposit address. |
| `payout_address_unresolved` | `tempoSettlement` is a virtual address with no registered master. |
| `amount_below_minimum` | The amount is zero. |
| `amount_above_maximum` | The amount is above the maximum per payment that Tempo sets. |
| `insufficient_tempo_liquidity` | Tempo can't fund the payout right now. Nothing is charged on Base; retry later. |
| `screen_rejected` | The payer or payout address failed address screening. |
| `screening_unavailable` | Screening couldn't run. Nothing is charged; retry later. |
| `invalid_payload` | The payment doesn't carry exactly one authorization for its scheme. |
| `unsupported_scheme`, `unsupported_network`, `unsupported_asset` | The payment isn't `exact` USDC on Base, as `GET /supported` lists. |
| `payment_conflict` | The same payment was already sent with different terms or by another organization. |
| `settlement_pending` | Rare: Base doesn't hold the settlement yet. Retry settle with the same payload; it never pays twice. |

Refusals that come from the x402 signature or Base state use the x402 SDK's reasons. An upstream failure answers `unexpected_verify_error` or `unexpected_settle_error`.

## Tempo x402 facilitator FAQ

### Do buyers change anything?

No. Buyers sign the same USDC payment on Base mainnet as for any x402 facilitator. Any x402 client, such as `@x402/fetch`, or an `mppx` client pays.

- `@x402/fetch` refuses payments above $1 by default. Raise its limit to pay pricier routes.
- If a paid request comes back with `settlement_pending`, resend the same signed payment. Don't sign a new one.

### Can a platform settle for many sellers?

Yes. Set each seller's Tempo address in `tempoSettlement` on their routes. Each payout goes to the address its payment names.

### When should I use MPP instead?

Use [MPP](/docs/guide/machine-payments/server) when buyers can pay on Tempo directly. It adds [payment sessions](/docs/guide/machine-payments/pay-as-you-go), which bill per use without a transaction per request. Use the facilitator to keep x402 buyers paying on Base.
