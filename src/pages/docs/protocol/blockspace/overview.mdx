# Blockspace overview: understanding payment lanes

## Abstract

This specification defines the structure of valid blocks in the Tempo blockchain.

## Motivation

Tempo blocks extend the Ethereum block format in multiple ways: there are new header fields to account for payment lanes and shared gas accounting, and a protocol system call updates the committee at each epoch boundary. This specification contains all the modifications to the block format.

## Specification

### Header fields
Tempo extends an Ethereum header with gas-accounting fields, a millisecond timestamp component, and consensus context.
```rust title="Header struct"
pub struct Header {
    pub general_gas_limit: u64,
    pub shared_gas_limit: u64,
    pub timestamp_millis_part: u64,
    pub inner: alloy_consensus::Header,
    pub consensus_context: Option<TempoConsensusContext>,
}

pub struct TempoConsensusContext {
    pub epoch: u64,
    pub view: u64,
    pub parent_view: u64,
    pub proposer: PublicKey, // Valid 32-byte Ed25519 public key
}
```
- `inner` is the canonical Ethereum header (parent_hash, state_root, gas_limit, etc.).
- `general_gas_limit` and `shared_gas_limit` partition the canonical `gas_limit` for payment and non-payment capacity (see [payment lane specification](/docs/protocol/blockspace/payment-lane-specification)).
- `timestamp_millis_part` stores the sub‑second component; the full timestamp is `inner.timestamp * 1000 + timestamp_millis_part` .

Current non-genesis headers MUST contain `consensus_context`. It records the consensus epoch, view, parent view, and proposer public key. Validators MUST reject a proposal whose context doesn't exactly match the consensus round's epoch, view, parent view, and leader. RLP decoding MUST reject an invalid Ed25519 proposer key. The header RLP field order is `[general_gas_limit, shared_gas_limit, timestamp_millis_part, inner, consensus_context]`, with context encoded as `[epoch, view, parent_view, proposer]`. The context participates in the header hash. JSON-RPC exposes it as `consensusContext`, with `parentView` in camel case.

### Block body
The block body in Tempo retains the canonical Ethereum block body structure. It MUST NOT contain system transactions. Its transactions are subject to `general_gas_limit` on non-payment transactions.

### Block system calls

Before transactions in every non-genesis block, the VM MUST call the EIP-2935 history contract at `0x0000F90827F1C53a10cb7A02335B175320002935` from `0xfffffffffffffffffffffffffffffffffffffffe`, passing the parent block hash as 32 raw bytes. It MUST commit the returned state. EVM invocation and database errors invalidate the block; a returned revert or halt does not. Missing history code produces no update.

The VM MUST NOT schedule the EIP-4788 beacon-root call, EIP-7002 withdrawal request call, EIP-7251 consolidation request call, or EIP-8282 builder request calls. It MUST NOT parse EIP-6110 deposit logs into execution requests. The execution-request list MUST be empty.

### Epoch-boundary committee update

The VM MUST run a committee update system call after all transactions in the last block of each epoch, at height `h` where `(h + 1) % epoch_length == 0`. It decodes the DKG outcome from the block's `extra_data` and calls `setCommitteeMembers(epoch, publicKeys)` on the current committee precompile at `0xC077E00000000000000000000000000000000000` from the zero address. This call isn't part of the transaction list. The block is invalid if `extra_data` doesn't decode as a DKG outcome or the call fails.
