# T13 Network Upgrade

T13 ships the prover for [Tempo Zones](/docs/zones). Tempo can now check that a Zone executed its private transactions correctly before it accepts the Zone's settlement. T13 also adds the Tempo changes the prover depends on, and lets transactions pay fees in OUSD when the fee payer has no pathUSD.

:::info[T13 status]
T13 is scheduled for **October 29, 2026 at 15:00 UTC on Moderato testnet** and **November 3, 2026 at 15:00 UTC on mainnet**, as set by the [merged scheduling PR](https://github.com/tempoxyz/tempo/pull/8480). The required node release is not yet published. Check [Node Operator Updates](/docs/guide/node/network-upgrades#t13) before upgrading.
:::

## Zone prover

A Zone sequencer executes transactions privately and settles batches on Tempo. Before T13, Tempo accepted a batch when enough sequencers signed it; it trusted them to have executed it correctly. With T13, a prover replays each batch and Tempo verifies the result before settlement. This prevents a sequencer from settling invented balances or unauthorized transfers.

<OndineDiagram
  name="prover"
  alt="Inside the Zone, the sequencer sends a batch and state witness to the Nitro prover, which replays it and returns a signed attestation. The sequencer submits the batch, attestation, and quorum signatures to the ZonePortal on Tempo, which calls the native verifier and, if valid, records the new state and queues withdrawals. A dashed T13 fallback path submits with quorum signatures only (NoProof)."
  caption="Private transactions and the state witness stay in the Zone. Tempo sees only the batch commitments, the attestation, and signatures."
/>

1. **Prepare.** The sequencer groups Zone blocks into a batch and gathers a state witness: the starting state and the Tempo state the batch read.
2. **Prove.** The prover replays the batch inside an AWS Nitro Enclave running approved code. If execution checks out, the enclave signs an attestation bound to the Zone, the batch, and its resulting commitments.
3. **Settle.** The sequencer submits the batch, attestation, and quorum signatures to the Zone's portal on Tempo. The portal checks the signatures and continuity, and the native verifier checks the attestation. Only then does the portal record the new state and queue withdrawals.

This is a TEE-based prover, not a zero-knowledge proof: security rests on the approved enclave code and AWS Nitro's attestation. The prover checks execution, including balances and authorized transfers. It does not guarantee uptime, transaction inclusion, or completed withdrawals, and Zone operators still see plaintext data.

### Temporary NoProof fallback

T13 ships the prover with training wheels. A sequencer can still settle a batch in `NoProof` mode (`verifierConfig = 0x02`, empty proof), which keeps the quorum and continuity checks but skips Nitro verification. This keeps Zones settling if proving fails during rollout. Because `NoProof` is allowed even when proving works, execution of any batch settled this way still relies on the sequencer quorum.

Nitro proofs also require approved enclave measurements, and the [release measurement registry](https://github.com/tempoxyz/tempo/blob/main/crates/precompiles/src/zone_verifier/pcrs.json) is currently empty. Until measurements are approved, Nitro proofs are rejected and Zones settle through `NoProof`.

<OndineDiagram
  name="prover-rollout"

A later upgrade removes `NoProof`; after that, a missing or invalid proof stops settlement. Forced exits are not part of T13.

### Prover upgrades

A new prover build changes its enclave measurements (PCRs), the fingerprints of the approved code. A Tempo hardfork approves new measurements, and at activation the verifier and sequencers switch to the matching prover. Each attestation binds its own Zone and batch, so Zones can share a prover version without their proofs being interchangeable.

See [Zone proving and settlement](/docs/protocol/zones/proving) for the verifier interface and execution checks.

## Tempo changes for the prover

The prover runs on Zones, but Tempo has to verify its output and give it a replayable history. T13 ships three Tempo changes for this:

| TIP | Change | Why the prover needs it |
|-----|--------|-------------------------|
| [TIP-1098](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1098.md) | Nitro-backed Zone batch verification | Adds the native verifier at `0x5a56000000000000000000000000000000000000`. It checks the AWS certificate chain, attestation signature, approved enclave measurements, and batch digest. |
| [TIP-1096](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1096.md) | Multi-block Tempo imports for Zones | Bounds the work in a batch so the prover can replay it, and lets Zones catch up after downtime without historical Tempo state proofs. |
| [TIP-1119](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1119.md) | Explicit block system calls | Pins the automatic system calls in Tempo and Zone blocks, so the prover replays exactly what Zone nodes executed. |

The [T13 meta-TIP PR (TIP-1146)](https://github.com/tempoxyz/tempo/pull/8289) collects these TIPs, [TIP-1115](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1115.md), and additional fixes; it is still under review.

### Multi-block Tempo imports for Zones

One Zone block can now import a range of consecutive Tempo headers. A header-only block advances the Zone's Tempo checkpoint, and a full block then processes pending deposits and token enablements against the latest imported state. To keep that work bounded, each Zone portal limits pending items:

| Limit | Value | Effect |
|-------|-------|--------|
| Unprocessed deposits | 230 | Withdrawal bounce-backs are rejected at this limit. |
| Reserve for withdrawal bounce-backs | 20 | Ordinary deposits are rejected once 210 deposits are unprocessed. |
| Unprocessed token enablements | 8 | `enableToken` reverts while eight enablements are pending. |

A withdrawal batch is rejected if its size exceeds the remaining deposit capacity, because every withdrawal could bounce back. See [Zone execution](/docs/protocol/zones/execution).

### Explicit block system calls

Tempo blocks now run only two automatic system calls: the EIP-2935 parent-hash history update before transactions, and the committee update after the last block of each epoch. Blocks no longer schedule the EIP-4788 beacon-root call or the EIP-7002, EIP-7251, and builder request calls, and the execution-request list is always empty. Zone execution selects the same EIP-2935 call. Transactions and receipts are unchanged.

### Zone deposit and refund fixes

- Zone deposits, withdrawal bounce-backs, and refund claims check TIP-403 `Recipient` authorization instead of `MintRecipient`.
- `ZoneInbox.claimRefund(token)` reverts with `NoRefund` when the caller has no pending refund for that token.

## Ordered fallback fee tokens

Today, when a transaction has no `feeToken`, no stored preference, and no inferred token, Tempo charges the fee in pathUSD. If the fee payer holds no pathUSD, the transaction fails. As OUSD becomes the recommended stablecoin on Tempo, many accounts hold OUSD but no pathUSD, and integrations that assumed pathUSD for gas started failing.

[TIP-1115](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1115.md) replaces that last step with an ordered list: pathUSD, then [OUSD](/docs/guide/ousd) (`0x20c0000000000000000000006a37da5c996874be`).

<OndineDiagram
  name="fee-token-fallback"
  alt="If the transaction sets feeToken, has a stored preference, or an inferred token, it pays in that token as before. Otherwise it pays in pathUSD if pathUSD covers the max fee, else in OUSD if OUSD covers it, else it is rejected for insufficient funds."
/>

- One token must cover the whole maximum fee, `ceil(gasLimit * maxFeePerGas / 10^12)` in base units. Balances are not combined.
- Only an insufficient balance moves on to OUSD. Pause, policy, access-key, and Fee AMM liquidity failures on the selected token do not.
- An explicit `feeToken`, a `setUserToken` preference, and inference from TIP-20 transfers and DEX swaps keep their precedence. The fallback never overrides them.
- The validator default fee token stays pathUSD.

### Affected partners

You are affected if your integration assumes users pay gas in pathUSD:

- **You set `feeToken` to pathUSD.** The fallback does not apply to explicit choices, so users without pathUSD still fail after T13. Set `feeToken` to OUSD (or the token the user holds), or omit it and let the fallback choose.
- **You check pathUSD before sending.** Wallets and frontends that block a transaction or show "insufficient gas" when pathUSD is zero should check pathUSD, then OUSD, against the maximum fee.
- **You display or reconcile fees in pathUSD.** Read `feeToken` from the receipt instead of assuming pathUSD.
- **You sponsor fees.** The fallback checks the fee payer's balances, so a sponsor holding only OUSD works after T13.

Until T13 activates on your network, the fallback does not exist: set `feeToken` to OUSD explicitly, or keep pathUSD in the fee payer's account.

## Integration impact

- **Fee payers:** a transaction without `feeToken` or a stored preference, and with too little pathUSD, now pays in OUSD when the fee payer holds enough. To pin a token, set `feeToken` or call `setUserToken`. A pathUSD transfer before inclusion can change which token a pending transaction pays with.
- **Wallets and fee displays:** read the receipt's `feeToken`. When estimating before signing, check pathUSD first, then OUSD, against the maximum fee.
- **Zone operators:** T13 is a coordinated Tempo and Zone upgrade. Run compatible sequencer and prover builds with a T13-compatible Tempo node before activation, and monitor `NoProof` fallback. Clear any deposit or token-enablement backlog above the new limits under T12. `ITempoState.finalizeTempo(bytes)` becomes `finalizeTempo(bytes[])`, and `IZoneInbox.advanceTempoHeaders(bytes[])` is new.
- **Zone applications:** handle deposit rejections when a Zone's deposit queue is full, and expect `enableToken` to revert while eight enablements are pending. Treat `NoRefund` from `claimRefund` as "nothing to claim".
- **Node operators and indexers:** install the T13 release before your network activates. Stop expecting beacon-root or execution-request system calls in Tempo blocks after activation.
