# T13 Network Upgrade

T13 introduces the prover for [Tempo Zones](/docs/zones): it replays private Zone execution inside an AWS Nitro Enclave and produces an attestation that Tempo can verify before accepting settlement. The upgrade adds the protocol changes needed for that flow, improves Zone recovery after downtime, and lets accounts pay fees in OUSD through an ordered fallback.

:::info[T13 status]
T13 is scheduled for **October 29, 2026 at 15:00 UTC on Moderato testnet** and **November 3, 2026 at 15:00 UTC on mainnet**, as set by the [merged scheduling PR](https://github.com/tempoxyz/tempo/pull/8480). The required node release is not yet published. Check [Node Operator Updates](/docs/guide/node/network-upgrades#t13) before upgrading.
:::

**Integration note:** If your transactions omit `feeToken` and the fee payer has no fee-token preference, T13 can charge fees in OUSD instead of rejecting the transaction for an insufficient pathUSD balance. [See integration guidance](#integration-impact).

## T13 overview

The prover checks the execution behind a batch's commitments. The portal also checks sequencer authorization and continuity before recording those commitments and queuing withdrawals. T13 retains a temporary proofless fallback during rollout; it does not yet require a Nitro proof for every settlement.

| TIP | Change | Role in T13 |
|-----|--------|-------------|
| [TIP-1098](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1098.md) | Nitro-backed Zone batch verification | Authenticates the prover's approved enclave code and binds its attestation to the submitted batch. |
| [TIP-1096](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1096.md) | Multi-block Tempo imports for Zones | Lets the prover replay bounded batches and lets Zones recover from downtime without fetching historical Tempo state proofs. |
| [TIP-1119](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1119.md) | Explicit block system calls | Makes automatic system processing explicit in Tempo and Zone execution. |
| [TIP-1115](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1115.md) | Ordered fallback fee tokens | Tries pathUSD, then OUSD, when no fee token has been selected. |

The [T13 meta-TIP PR (TIP-1146)](https://github.com/tempoxyz/tempo/pull/8289) collects these TIPs and additional protocol changes; the meta-TIP is still under review.

## T13 features

<span id="nitro-backed-zone-batch-verification" />

### Zone prover and settlement

A Zone sequencer orders and executes private transactions. The prover independently replays a batch using the stateless proof function (SPF), with witnessed Zone and Tempo state. It checks state transitions, processed deposits, token enablements, and withdrawal commitments before producing a result. This lets Tempo authenticate the execution behind a settlement without replaying the private transactions on the public chain.

The normal Nitro settlement path has three parts:

1. **Replay inside the enclave.** The sequencer supplies the batch and state witness to the prover. The SPF checks and re-executes the batch against trusted network configuration. An execution failure produces no successful attestation.
2. **Attest the result.** After successful replay, the enclave commits to the batch result in an AWS Nitro attestation document. The attestation binds the Zone, parent chain, anchor, block transition, Zone height, deposit and token-enablement progress, withdrawal commitment, and verifier configuration.
3. **Verify on Tempo.** The sequencer submits the attestation with a quorum-signed batch to the Zone portal. The portal checks authorization and continuity, then calls the native verifier at `0x5a56000000000000000000000000000000000000`. The verifier checks the AWS certificate chain, attestation signature, approved enclave measurements, and batch digest. On acceptance, the portal records the new commitments and queues withdrawals.

This is a **TEE-based prover**, whose security relies on AWS Nitro and approved enclave code. It does not generate a zero-knowledge proof. Sequencer signatures authorize a batch; the Nitro attestation authenticates its execution result.

#### Prover rollout and trust assumptions

During rollout, a sequencer can also submit a batch with the `NoProof` mode (`verifierConfig = 0x02`) and an empty proof. This fallback preserves quorum, continuity, canonical-portal, and settlement checks but skips Nitro validation. It allows settlement to continue when proving is unavailable or verification fails. A later upgrade removes it.

Nitro mode (`0x01`) requires approved enclave measurements. The current [release measurement registry](https://github.com/tempoxyz/tempo/blob/main/crates/precompiles/src/zone_verifier/pcrs.json) is empty, so Nitro proofs are rejected until those measurements are approved. Shipping the prover does not by itself make every Zone settlement proof-enforced. T13 also does not introduce forced exits; withdrawals still depend on the operator processing and submitting batches.

Read [TIP-1098](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1098.md) and [Zone proving and settlement](/docs/protocol/zones/proving) for the verifier interface and execution checks.

### Multi-block Tempo imports for Zones

T13 lets one Zone block import a range of consecutive Tempo headers. A header-only block advances the Zone's Tempo checkpoint without other execution, so a Zone can recover from a long outage without historical state proofs. A full block then processes every pending deposit and token enablement against the latest imported Tempo state.

To keep recovery bounded, each Zone portal limits pending work:

| Limit | Value | Effect |
|-------|-------|--------|
| Unprocessed deposits | 230 | Withdrawal bounce-backs are rejected at this limit. |
| Reserve for withdrawal bounce-backs | 20 | Ordinary deposits are rejected once 210 deposits are unprocessed. |
| Unprocessed token enablements | 8 | `enableToken` reverts while eight enablements are pending. |

A withdrawal batch is rejected before processing if its size exceeds the remaining deposit capacity, because every withdrawal could bounce back.

Read the [specification](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1096.md) and [Zone execution](/docs/protocol/zones/execution).

### Ordered fallback fee tokens

Before T13, a transaction that reaches the last step of [fee-token selection](/docs/protocol/fees/spec-fee#fee-token-preferences) pays in pathUSD and fails if the fee payer cannot cover the fee in pathUSD.

T13 replaces that last step with an ordered list: pathUSD, then [OUSD](/docs/guide/ousd). The protocol picks the first token whose balance covers the transaction's maximum fee, `ceil(gasLimit * maxFeePerGas / 10^12)` in base units. One token must cover the whole fee; balances are not combined. A transaction with a zero maximum fee uses pathUSD.

Explicit `feeToken` values, account preferences set with `setUserToken`, and inference from TIP-20 transfers and DEX swaps keep their precedence. Only an insufficient balance moves the search to the next token. Once a token is selected, pause, policy, access-key, and Fee AMM liquidity checks apply as before, and a failure there does not try the next token. The validator default fee token remains pathUSD.

Read the [specification](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1115.md).

### Explicit block system calls

At T13, Tempo blocks run two automatic system calls: the EIP-2935 parent-hash history update before transactions, and the committee update after the last block of each epoch. Blocks no longer schedule the EIP-4788 beacon-root call, EIP-7002 and EIP-7251 request calls, or builder request calls, and the execution-request list is always empty.

Zone execution also explicitly selects the EIP-2935 history call and excludes Ethereum beacon-root and execution-request processing, so SPF replay and Zone nodes use the same system-call rules. See the [Zone executor implementation](https://github.com/tempoxyz/tempo/pull/8472).

This keeps block validity independent of code deployed at Ethereum system-contract addresses. Transactions and receipts are unchanged.

Read the [specification](https://github.com/tempoxyz/tempo/blob/main/tips/tip-1119.md).

### Zone deposit and refund fixes

T13 also changes how Zones credit bridged funds:

- Zone deposits, withdrawal bounce-backs, and refund claims check TIP-403 `Recipient` authorization instead of `MintRecipient`. Receive policies and refund behavior are unchanged.
- `ZoneInbox.claimRefund(token)` reverts with `NoRefund` when the caller has no pending refund for that token.

## Integration impact

- **Fee payers:** a transaction that omits `feeToken`, has no stored preference, and has too little pathUSD now pays in OUSD when the fee payer holds enough OUSD. To keep a specific token, set `feeToken` on the transaction or call `setUserToken`. A transfer into pathUSD before inclusion can change the token a pending transaction pays with.
- **Wallets and fee displays:** read the fee token from the receipt's `feeToken` field instead of assuming pathUSD for transactions without a preference. If you estimate the fee token before signing, check pathUSD first, then OUSD, against the maximum fee.
- **Zone operators:** T13 is a coordinated Tempo and Zone upgrade. Run compatible sequencer and prover builds with a T13-compatible Tempo node before activation. Monitor fallback to `NoProof` and verify the approved enclave measurements before relying on Nitro enforcement. Process any deposit or token-enablement backlog above the new limits under T12 first. `ITempoState.finalizeTempo(bytes)` becomes `finalizeTempo(bytes[])`, and `IZoneInbox.advanceTempoHeaders(bytes[])` is new.
- **Zone applications:** handle deposit rejections when a Zone's deposit queue is full, and expect `enableToken` to revert while eight enablements are pending. Treat `NoRefund` from `claimRefund` as "nothing to claim".
- **Node operators and indexers:** install the T13 release once it is published, before your network activates. Tooling that expects beacon-root or execution-request system calls in Tempo blocks should stop expecting them after activation.
