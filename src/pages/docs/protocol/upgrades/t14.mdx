# T14 Network Upgrade

T14 upgrades the Account Keychain so accounts on Tempo support multiple signers, with approval thresholds, key rotation, and recovery built into the protocol. It also ends admin access keys' key management and tightens validator, consensus, and Zone Portal rules.

:::tip[T14 status]
T14 is scheduled to activate on testnet on November 24, 2026 and on mainnet on December 8, 2026, both at 15:00 UTC. Its scope may still change before activation. Until T14 activates, the account changes run only on the [Tempo Accounts devnet](/docs/accounts/create#connect-to-the-devnet).
:::

**Integration note:** T14 stops new admin access keys and removes existing ones' power to manage other keys. Existing admin keys can still spend without limit until you revoke them. If you use an admin key to manage a user's other keys, plan the change before T14. [See integration impact](#integration-impact).

## T14 overview

- **Multiple signers per account:** several signers approve together once their weights reach a threshold, such as any two of three finance leads, with no multisig contract to deploy.
- **Keys change, the address doesn't:** signers replace a lost key or add a backup at the same address, without moving funds.
- **Existing accounts upgrade in place:** a single-key account gains signers and a threshold and keeps its address and balances.
- **Team approval for access keys:** a team's account can act as another account's access key, approving with its own signers.
- **Zone support:** these accounts work on Zones with the same signers and threshold.
- **Admin access keys removed:** Tempo rejects new admin access keys.
- **Validator and consensus rules:** blocks must pay the proposer's registered fee recipient, endpoint formats are stricter, and consensus defaults to deferred verification.
- **Paused Zone Portals:** a paused Zone Portal also rejects refund claims. Batch settlement continues.
- **Cheaper batches:** a batch call pays cold access only for a target no earlier call reached.

<span id="features" />

## T14 features

<span id="changes-to-accounts" />

### Multiple signers for accounts

T14 extends the Account Keychain so one address can be controlled by up to 48 signers. Each signer has a weight, and a transaction runs once the weights of the approving signers reach the account's threshold. With three signers at weight 1 and a threshold of 2, any two can approve a payment.

- **Mixed signing methods:** signers can be passkeys, P-256 keys, or standard Ethereum keys, so a user's passkey and a provider's key can approve together.
- **Rotation and recovery at the same address:** the current signers replace the signer list and threshold in one transaction. The address and balances stay the same, so anyone paying the account needs no update.
- **In-place upgrades:** an existing single-key account adds signers at the same address, and its original key is retired.
- **Team approval for access keys:** an account with multiple signers can be another account's [access key](/docs/accounts/access-keys) and approves with its own signers.

Read the specifications for [multiple signers](https://tips.sh/1107), [in-place upgrades](https://tips.sh/1113), and [access keys](https://tips.sh/1111), and the [Tempo EVM reference](/docs/development/configurable-accounts).

### Multiple signers on Zones

Zones read each account's signer configuration from Tempo, so an account uses the same signers and threshold on a Zone as on Tempo. A signer change applies on a Zone once it imports that Tempo block. Configuration updates and upgrades revert on a Zone with `UnsupportedOnZone()`.

Read the [specification](https://tips.sh/1154).

### Admin access key removal

From T14, Tempo rejects new admin access keys, and only an account's own key or its signers authorize, change, or revoke access keys. An admin key authorized before T14 keeps spending as an access key without limits until you revoke it. To let a second device manage keys, [add it as a signer](/docs/accounts/account-configuration/configuration-updates#add-a-signer).

Read the [specification](https://tips.sh/1137).

### Validator and consensus changes

- **Fee recipient:** Tempo rejects a block whose beneficiary isn't the proposer's fee recipient in `ValidatorConfigV2`, or whose proposer has no entry. A registered zero address burns the fees.
- **Endpoint format:** `addValidator`, `rotateValidator`, and `setIpAddresses` revert with `InvalidIp` when an ingress or egress address is longer than 255 bytes. They also revert for the IPv4-mapped IPv6 form, such as `::ffff:192.0.2.1`. Tempo doesn't recheck endpoints registered before T14.
- **Consensus verification:** `--consensus.verification-mode` defaults to `hardfork`, which switches to deferred verification at the first epoch boundary after T14. An explicit `immediate` or `deferred` setting still overrides it.

Read the [specification](https://tips.sh/1152).

### Paused Zone Portals

From T14, a paused Zone Portal also rejects refund claims. Batch settlement continues.

Read the [specification](https://tips.sh/1152).

### Batch call gas

From T14, each call after the first in a Tempo transaction pays the 2,600-gas cold access cost only when no earlier call targeted it and validation hasn't already loaded it, such as the sender, a fee payer, or the access key. Other calls pay 100 gas. Before T14, every call after the first paid 2,600 gas.

Read the [specification](https://tips.sh/1152).

## Integration impact

- **Existing accounts:** single-key accounts and limited access keys keep working unchanged. Adding signers to an account is optional.
- **Admin access keys:** if you use an admin key to manage a user's other keys, [add that device as a signer](/docs/accounts/account-configuration/configuration-updates#add-a-signer) instead and revoke admin keys you no longer need before T14 ([details](#admin-access-key-removal)).
- **Account upgrades:** the upgrade call only exists once T14 activates on a network. Sent earlier, the transaction still pays its fee but leaves the account unchanged, so send upgrades only after activation.
- **Signature parsing:** accounts with multiple signers sign with the [`0x05` multisig signature](/docs/development/configurable-accounts#multisig-signature-format). Viem builds and reads it. If you parse or verify Tempo transaction signatures yourself, handle this type. It isn't valid as a fee payer signature, in subblock transactions, or in authorization lists.
- **New configurable accounts:** a derived address for a new configurable account exists only on Tempo and its Zones. Funds sent to it on another chain are lost. Warn users not to share it for other chains.
- **Contracts that check signatures from configurable accounts:** single-key accounts are unchanged. A configurable account answers ERC-1271 `isValidSignature`. Contracts can also call `verifyConfigurableAccount` on the [signature verifier precompile](/docs/development/configurable-accounts#verify-owner-approvals-in-a-contract). Configurable accounts follow [extra signature rules](#upgrade-impact).
- **Validators:** check your fee recipient and endpoint formats against the [validator and consensus changes](#validator-and-consensus-changes).

## Upgrading from a single-key account

An [account upgrade](/docs/accounts/account-configuration/account-upgrade) turns a single-key account into a configurable account at the same address. It's optional and permanent. Accounts that don't upgrade work exactly as before.

### What changes

- **Signing:** signers whose weights reach the threshold approve for the account. The original key approves only if listed, at its weight.
- **Original key:** Tempo rejects its direct signatures with `RootKeyRetired`. It still controls the address on other EVM chains, and on a Zone until that Zone imports the upgrade.
- **What carries over:** the address, balances, allowances including Permit2, and access keys. Admin keys granted before T14 keep spending without limits until revoked.
- **Who can upgrade:** accounts without code, an EIP-7702 delegation, or existing signers.

Integrations that touch configurable accounts need these changes:

| Integration | What to do |
|---|---|
| Wallets | Send the upgrade after T14 activates. A fee payer can sponsor it. Before the user confirms, show the signers, threshold, and every access key that carries over. Warn that the original key still controls the address on other EVM chains. |
| Error handling | Treat `RootKeyRetired` as "this key was upgraded", not an invalid signature. Rebuild the account from its [saved configuration](/docs/development/configurable-accounts#keep-the-current-configuration). |
| Fee sponsors | Configurable accounts can be sponsored but can't sponsor others. Keep a single-key fee payer. |
| TIP-20 `permit` | Configurable accounts can't sign it. Permits signed before the upgrade also fail, so relayers should drop queued ones. Batch an `approve` instead. |
| Signature verifiers | Permit2 and OpenZeppelin `SignatureChecker` v5.1+ need no change. Code that tries `ecrecover` first still accepts the original key. That includes `SignatureChecker` before v5.1, SIWE and TIP-1053 sign-in, signed orders, and ERC-2612 permits on non-TIP-20 tokens. Check for code or call `getConfigCommitment` first. |
| Payment channels and MPP sessions | Deposits made before the upgrade still settle but can't be topped up, so close channels first if they need more funds. A configurable account can't sign its own vouchers under T14. Set a separate single-key `authorizedSigner` until [TIP-1166](https://tips.sh/1166) in [T15](/docs/protocol/upgrades/t15). |
| Zones | Revoke access keys on each Zone separately. |

For more details on upgrading your account, see the [account upgrade checklist](/docs/accounts/account-configuration/account-upgrade).

Read the [specification](https://tips.sh/1113).
