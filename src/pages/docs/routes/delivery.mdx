# Track delivery

A successful source-chain transaction starts a route; it does not establish that the destination received funds. Keep the Routes object ID with your payment record and follow its status through delivery or refund.

## Read the transfer or deposit

For a transfer your application authorizes, use `GET /v1/routes/transfers/{id}`. Register the submitted source transaction hashes as described in [Make a transfer](/docs/routes/transfers).

For a deposit-address flow, list deposits with `GET /v1/routes/deposits`, filtering by `depositAddress`, then read each deposit with `GET /v1/routes/deposits/{id}`. The address being `active` says it can receive deposits; it does not describe a particular deposit's progress.

```bash
curl "https://api.tempo.xyz/v1/routes/transfers/${ROUTE_TRANSFER_ID}" \
  --header "tempo-api-key: ${TEMPO_API_KEY}"
```

Run this from your backend or terminal after setting the API key and transfer ID. See [API authentication](/docs/api/authentication).

## Keep delivery and refund states distinct

| State | Application behavior |
| --- | --- |
| `processing` | Keep the payment pending. |
| `completed` | Reconcile destination delivery, including the delivered amount and transaction references. |
| `action-required` | Inspect `statusReason` and the endpoint's instructions before continuing. |
| `refunding` | Keep the refund pending. |
| `refunded` | Reconcile the refund amount and transaction references. |

Use the full [transfer](/docs/api/routes/transfers) or [deposit](/docs/api/routes/deposit-addresses) reference for the lifecycle and response fields. Do not automatically send the payment again when it is pending or being refunded.

## Retry a create request safely

Reuse the same `idempotency-key` for the same create request. Changing the input while keeping the key conflicts. If a response is lost, follow the endpoint's retry behavior before creating a replacement; a missing response does not prove that creation failed.

## Use funds after delivery

After the destination account receives stablecoins, it can [send a payment](/docs/guide/payments/send-a-payment), [deposit into Earn](/docs/earn/integrate), or [deposit into a Zone](/docs/zones/deposit). Each is a separate operation. Direct Routes transfers into a vault or Zone are not implemented; their endpoints return HTTP `501`.
