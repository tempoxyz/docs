# Set up API access

Create a key, request Routes access, and keep the key on your backend. Later guides assume this setup.

## Routes API key scopes

| Scope | Allows | How a key gets it |
| --- | --- | --- |
| `routes:read` | Quotes, and transfer and deposit status reads | On by default. |
| `routes:write` | Creating transfers and deposit addresses, and registering source transactions | Tempo adds it when it [approves access](#request-routes-access). |
| `data:read` | Reading the [route directory](/docs/routes/networks) with your key, which applies your organization's access policy | On by default. |

Use a production key. Sandbox keys can't create live routes.

The route directory also accepts requests without a key at the [public rate limit](/docs/api/rate-limits). The Routes API key authenticates your application; it doesn't sign blockchain transactions.

## Request Routes access

Any organization member can request access. Tempo reviews the request and adds `routes:write` to the keys you choose.

:::::steps

### Create a production key

[Create an API key](/docs/api/console/api-keys#create-an-api-key) in the project that calls Routes. Creating keys needs the admin or owner role. The key starts with `routes:read` and `data:read`.

### Open the request form

In [Tempo Console](https://console.tempo.xyz/?to=/:org/routes), open **Routes**, choose the project, and select **Request access**. Exit sandbox first.

### Send the request

Choose the keys and routes you need, estimate monthly volume, and say whether you need [1:1 delivery](/docs/routes/quotes#offer-11-delivery). Leave routes empty if you're unsure. Select **Send request**.

### Check the status

The **Routes access** card shows the status:

| Status | Card shows | Next |
| --- | --- | --- |
| Pending | **Request sent** | Wait, or select **Cancel request**. |
| Declined | Tempo's reason | Address it and request again. |
| Approved | **Ready**, or no card | Start building. |

:::::

Approval sets the routes your keys can use and any 1:1 terms. To add routes later, select **Request a route** under **Routes** › **Available routes**. The [access request endpoints](/docs/api/routes-access-requests) use Console sign-in, not API keys.

## Resolve Routes access errors

These `403` codes mean the key or organization lacks access:

| Code | Cause | Fix |
| --- | --- | --- |
| `api_key_forbidden` | Missing scope, or a sandbox key. | Use a production key with the scope named in the message. |
| `routes_not_allowed` | The route isn't in your policy. | Select **Request a route** in Console. |
| `routes_subsidy_not_enabled` | No approved 1:1 terms. | Request 1:1 delivery, or omit `subsidize`. |
| `routes_subsidy_not_allowed` | The route can't be subsidized. | Omit `subsidize`. |
| `billing_required`, `billing_past_due` | 1:1 delivery your organization pays for needs active billing. | [Add a payment method](/docs/api/console/usage-and-billing#add-a-payment-method). |
| `routes_suspended` | New routes are paused for your organization. | [Contact Tempo](https://tempo.xyz/contact). |

## Configure the client

Set `TEMPO_API_KEY` in your environment. TypeScript uses Node.js with built-in `fetch`; Python uses `requests` (`python -m pip install requests`); cURL examples require `curl` and `jq`.

::::code-group

```ts [TypeScript (fetch)]
const api = 'https://api.tempo.xyz/v1'
const headers = {
  'tempo-api-key': process.env.TEMPO_API_KEY!,
  'Content-Type': 'application/json',
}
```

```python [Python (requests)]
import os
import requests

api = "https://api.tempo.xyz/v1"
headers = {
    "tempo-api-key": os.environ["TEMPO_API_KEY"],
    "Content-Type": "application/json",
}
```

```bash [cURL (API)]
# Set TEMPO_API_KEY in your terminal's environment before running requests.
curl --fail-with-body 'https://api.tempo.xyz/v1/routes' \
  --header "tempo-api-key: $TEMPO_API_KEY"
```

::::

Each request builder in the flow guides generates cURL and TypeScript for its endpoint with these headers.

## Set idempotency keys

Create requests require an `idempotency-key` header. Assign one key per operation, such as one payment or one customer's deposit address, and store it with that record before sending the request:

::::code-group

```ts [TypeScript (fetch)]
const requestKey = crypto.randomUUID() // Persist with your payment record.
```

```python [Python (requests)]
import uuid

requestKey = str(uuid.uuid4())  # Persist with your payment record.
```

```bash [cURL (API)]
# Choose and retain one key per operation, including across retries.
ROUTE_REQUEST_KEY="my-payment-001"
```

::::

Reuse the key when you retry the same request with unchanged inputs. Matching requests replay the successful response for 24 hours; a request with changed inputs conflicts. Use a new key for a new operation.
