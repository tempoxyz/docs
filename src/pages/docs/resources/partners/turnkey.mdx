# Turnkey on Tempo

[Turnkey](https://www.turnkey.com/) provides wallet keys and policy-controlled signing for Tempo mainnet and Moderato testnet. Its native Tempo parser exposes transaction fields and individual batch calls so an application can apply signing rules before producing a signature.

## What Turnkey supports on Tempo

The [Tempo network guide](https://docs.turnkey.com/features/networks/tempo) documents Ethereum-style address derivation, legacy Ethereum transactions, and native Tempo transactions. Native transaction policies use the `tempo.tx` namespace rather than the legacy Ethereum policy fields.

| Control | Documented policy inputs |
| --- | --- |
| Network and fee settings | Chain ID, fee token, gas limit, and maximum fee per gas. |
| Permitted calls | Call destination, function selector, and encoded input. |
| Atomic batches | The `tempo.tx.calls` list and quantifiers such as `all`, `any`, and `count`. |
| Inclusion window | Transaction validity fields. |
| Signing authority | Wallet or private-key identity and required approvers. |

Turnkey's [Tempo policy examples](https://docs.turnkey.com/features/policies/examples/tempo) show these controls. Replace example networks, contracts, token addresses, and policy thresholds with the values your application has validated.

## Prepare Turnkey wallet signing

:::::steps

### Create the organization and authentication path

Follow the [Company Wallets quickstart](https://docs.turnkey.com/solutions/company-wallets/quickstart) for a server integration. It requires an account, organization, and API keypair. Select the provider's appropriate wallet and authentication model if users initiate payments from an embedded wallet.

### Derive the account and choose the network

Turnkey documents Tempo address derivation with `ADDRESS_TYPE_ETHEREUM`. Configure the signing client and RPC transport for the same Tempo network. Use [connection details](/docs/quickstart/connection-details) and [account setups](/docs/accounts/use-cases) to choose the surrounding integration.

### Construct a native Tempo transaction

Start from Turnkey's published [`with-tempo` example](https://github.com/tkhq/sdk/tree/main/examples/chain-integrations/with-tempo). It covers single and batched transactions, broadcasting, and a fee-sponsorship reference flow. Use [Tempo Transactions](/docs/guide/tempo-transaction) for the protocol fields and [fee-token configuration](/docs/guide/payments/pay-fees-in-any-stablecoin) for payment funding.

### Apply and test signing policies

Define allowed wallets, contracts, functions, networks, fee tokens, and approvers. For a batch that must contain only approved calls, evaluate every call; a rule on the first call does not restrict later calls.

Exercise a permitted payment and rejected variations before enabling the flow. Include an unexpected destination, disallowed function, wrong network, and a batch containing an additional unapproved call.

### Verify the resulting payment

Retain the business instruction and transaction identifier. Follow [receiving payments](/docs/guide/payments/accept-a-payment) to confirm the expected token, recipient, amount, and delivered transfer after execution. Signing approval is not delivery evidence.

:::::

## Inspect contract arguments deliberately

Turnkey exposes call destinations, input, and function selectors, but its Tempo policy examples note that Smart Contract Interfaces do not provide ABI parsing for this path. Use its documented calldata-inspection approach when a rule must inspect an encoded recipient or amount.

Do not treat an allowed token contract or function selector as an allowed recipient. Those checks constrain different fields. Review encoding and every relevant call against the provider's [policy language and examples](https://docs.turnkey.com/features/policies/examples/tempo).

## Separate Turnkey policies from Tempo access keys

Turnkey policies govern signing performed through Turnkey. A [Tempo access key](/docs/accounts/access-keys) authorized for a separate backend has its own onchain bounds. That backend can sign within its delegated authority without asking Turnkey to approve every payment.

Define the key's token limits, permitted calls, recipients where supported, and expiry separately. Use [Pay from a user's embedded wallet](/docs/accounts/automations/pay-from-an-embedded-wallet) for the documented Turnkey authorization path, and preserve both provider approval records and key lifecycle records.

For [Tempo-native fee sponsorship](/docs/guide/payments/sponsor-user-fees), configure a funded fee payer and its policy. Turnkey also documents [managed sponsorship](https://docs.turnkey.com/features/transaction-management) for mainnet and Moderato through its transaction-management service. That path requires an Enterprise plan, Gas Sponsorship enabled in the dashboard, and `sponsor: true`. Configure the organization's spend limits and track the returned transaction status.

Choose the signing and submission path before configuring its policies. The native `tempo.tx` rules described above govern native Tempo transaction signing; use the provider's documented policy fields for its managed transaction service.

## Turnkey integration questions

### Does Turnkey support mainnet and testnet?

Yes. Turnkey lists Tempo mainnet and Moderato testnet. Match the network in the transaction, client, funding, and policy.

### Can a policy inspect every call in a batch?

Yes. The native transaction parser exposes the call list. Use the appropriate quantifier when every call must satisfy a condition, rather than checking one list entry.

### Can a signing request require an approver?

Yes. Turnkey's Tempo examples include approver-specific signing conditions. Configure the applicable organization and policy instead of assuming an approver is required by default.

### Do provider policies constrain a separately delegated access key?

The access key has separate Tempo-enforced bounds. Configure and revoke those permissions onchain; changing a Turnkey policy alone does not revoke the key.
