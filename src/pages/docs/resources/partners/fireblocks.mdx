# Fireblocks on Tempo

[Fireblocks](https://www.fireblocks.com/products/wallets) provides vault accounts, asset wallets, transfer APIs, and transaction approval policies. Its [supported-assets directory](https://www.fireblocks.com/supported-assets) lists Tempo and Tempo Moderato Test. Start with the exact asset and workflow available in your workspace.

## Check the supported asset before integrating

Fireblocks distinguishes [globally and locally supported assets](https://developers.fireblocks.com/docs/list-supported-assets-1). Global assets are available by default when creating new asset wallets. Local assets appear only in workspaces that added or requested them; a receiving counterparty must also support the asset.

A network listing does not establish that every Tempo token or Fireblocks product is enabled. Record the workspace asset ID, network, token contract, and intended transfer direction. Use the provider's asset API to inspect workspace availability and the [Tempo stablecoin registry](/docs/partners/stablecoins) to confirm the onchain asset.

## Use vault accounts and transaction policies

| Component | Role in the payment integration |
| --- | --- |
| Vault account | Organizes the wallets used by a business, treasury, or customer-funds model. |
| Asset wallet | Holds a supported asset within a vault account and provides its receiving details. |
| API user | Authenticates API requests with a workspace role and permissions. |
| Transaction policy | Governs which initiators, sources, destinations, and conditions are allowed. |
| Transaction record | Tracks the provider operation and its status separately from the business instruction. |

The [vault-wallet documentation](https://developers.fireblocks.com/reference/create-vault-wallet) explains the account and address structure. The [policy guide](https://developers.fireblocks.com/docs/set-transaction-authorization-policy) covers workspace transaction controls and policy management.

## Prepare a Fireblocks payment flow

:::::steps

### Configure workspace API access

Follow the [Fireblocks quickstart](https://developers.fireblocks.com/docs/quickstart) for the chosen workspace and environment. API requests use an API key and a secret key that signs those requests. Assign the role required by the integration and configure its signing and approval path.

API authentication and onchain payment authorization are different responsibilities. Do not treat possession of a read API credential as permission to move a vault's funds.

### Create the supported vault wallet

Choose the vault account and the exact Tempo asset ID exposed by your workspace. Verify the generated receiving details and network before funding. The general quickstart uses a different test asset; do not copy that identifier into a Tempo payment.

### Apply transaction policies

Define who can initiate payments, the source vault, allowed destinations, and required approvals. Review rule ordering and exercise both allowed and blocked requests. Preserve business approvals alongside the provider operation.

### Submit and track a payment

Use Fireblocks' documented transaction API for the enabled asset. Save the returned Fireblocks transaction ID with the invoice, payout, or treasury instruction. Follow its status and retain any onchain transaction references rather than treating creation as completed delivery.

### Reconcile the recipient outcome

For direct onchain delivery, verify the expected token, recipient, amount, and successful delivered transfer using [receiving payments](/docs/guide/payments/accept-a-payment). If a separate provider performs conversion or a bank payout, retain that provider's completion evidence too. Use [payment reconciliation](/docs/resources/guides/payment-reconciliation) to connect these records to finance.

:::::

## Confirm native Tempo features separately

A supported token transfer does not establish support for every native transaction feature. Check the exact Fireblocks product and transaction path before using fee-token overrides, atomic batches, fee sponsorship, or access-key authorizations. The [custodian integration model](/docs/accounts/custodians) explains these distinctions.

Tempo network fees are paid in eligible stablecoins. Configure and fund the applicable fee mechanism under the [fee-token rules](/docs/guide/payments/pay-fees-in-any-stablecoin). A general gas-management product listing is not evidence that the same flow applies to Tempo.

For customer funds, record account ownership, signing authority, customer ledger attribution, and recovery responsibilities before opening deposits. A vault account structure alone does not determine the contractual custody model. See [treasury operations](/docs/resources/guides/corporate-treasury) for the operating records to preserve.

## Fireblocks integration questions

### Where can I verify Tempo support?

Check the public supported-assets directory, then query the assets available in your workspace. Confirm the network, token contract, asset ID, and intended operation together.

### Is every supported asset enabled in every workspace?

No. Local assets need workspace-specific addition or approval. Confirm the recipient's support as well before transferring them through a Fireblocks Network destination.

### Can Fireblocks restrict payment destinations?

Yes. Its workspace policies can govern transaction initiators, sources, destinations, and other conditions. Configure and test the actual policy; the presence of a policy engine does not establish that your payment restrictions are active.

### Does a Fireblocks transaction ID prove the recipient was paid?

No. It identifies the provider operation. Track its outcome and verify the relevant delivered transfer or additional payout evidence before fulfilling the business obligation.
