# Account Keychain

The Account Keychain holds each account's access keys and checks every transaction they sign against the limits you set.

Access keys are extra keys that sign for an account, and they are live on mainnet and testnet. An access key works within its spending limits, expiry, and scopes. The Account Keychain is a precompile, a contract built into Tempo, at `0xAAAAAAAA00000000000000000000000000000000`. To build with access keys, start with the [Access keys](/docs/accounts/access-keys) guide.

Both [account types](/docs/accounts/keys) use access keys. A [single-key account](/docs/development/single-key-accounts) is controlled by one root key, the key its address derives from. A [configurable account](/docs/development/configurable-accounts) is controlled by owner keys, whose weights must reach a threshold to approve. Configurable accounts run on [testnet](/docs/accounts/create#connect-to-testnet) now. [T14](/docs/protocol/upgrades/t14) brings them to mainnet on December 8, 2026.

## Access key types

Each access key has a signature type, the `signatureType` value you pass when you authorize it. The Account Keychain identifies each of an account's keys by its key ID, an address.

| Key type | `signatureType` | Key ID |
| --- | --- | --- |
| secp256k1 | `0` | The key's address |
| P-256 | `1` | The key's address |
| WebAuthn | `2` | The address derived from the passkey's public key |
| Configurable account | `3` | The account's address. Its owners sign for it. Testnet until T14 reaches mainnet ([TIP-1111](https://tips.sh/1111)). |

## Access key restrictions

| Restriction | Rule |
| --- | --- |
| Spending limits | One per [TIP-20 token](/docs/protocol/tip20/overview), Tempo's stablecoin standard, in base units. Each limit's `period` of `0` sets a one-time limit; a positive `period` resets it every `period` seconds. |
| What limits count | Direct TIP-20 transfers, approval increases, fees the account pays, and and tokens that protocol precompiles pull, such as a Stablecoin DEX swap's input. A `transferFrom` that spends an allowance the account already granted doesn't count, and neither do non-TIP-20 assets. |
| Expiry | A Unix timestamp. The key stops working at that second. Omit it for no expiry; a direct [`authorizeKey`](#authorize-an-access-key) call passes `type(uint64).max` instead. |
| Scopes | Any call, or an allowlist of `(target, selector, recipients)`: the contracts, functions, and payees the key can use. An empty allowlist denies every call; a target with no selector rules allows any function. Only the calls the key signs directly are checked, not calls those contracts make in turn. |
| Contract creation | A key can't deploy a contract directly, but it can call a permitted factory that does. |
| Key management | Access keys can't authorize, change, or revoke keys, including themselves. |

Tempo rejects an expired key with [`KeyExpired`](/docs/protocol/transactions/AccountKeychain#error-keyexpired), a transaction over a limit with [`SpendingLimitExceeded`](/docs/protocol/transactions/AccountKeychain#error-spendinglimitexceeded), and a call outside the scopes with [`CallNotAllowed`](/docs/protocol/transactions/AccountKeychain#error-callnotallowed).

## Access keys on each account type

| | [Single-key account](/docs/development/single-key-accounts) | [Configurable account](/docs/development/configurable-accounts) |
| --- | --- | --- |
| Authorizes, changes, and revokes keys | The root key | Owners whose weights reach the threshold, with a `0x05` [multisig signature](/docs/development/configurable-accounts#multisig-signature-format) |
| Acts as another account's access key | As type `0`, `1`, or `2`, matching its root key | As type `3`, signed by its owners |

Any account can also be another account's access key, as the second row shows. Access keys never count toward a threshold.

## Authorize an access key

An account authorizes a key in one of two ways: a `key_authorization` field on a [Tempo Transaction](/docs/protocol/transactions/spec-tempo-transaction), or a direct call to the precompile.

| Path | Behavior |
| --- | --- |
| `key_authorization` on a transaction | The account signs the authorization, and the new key can sign the transaction that carries it. The key stays authorized even if the calls revert. |
| `authorizeKey` call | The account calls the precompile. The authorization rolls back if the transaction reverts. |

Viem's `client.accessKey.signAuthorization` and `authorize` both use the `key_authorization` path. An optional `witness`, an application-defined `bytes32`, binds the authorization to an offchain challenge, such as a sign-in nonce. To cancel an authorization that hasn't landed yet, the account burns its witness with `client.accessKey.burnWitness`. Tempo then rejects any authorization signed with that witness.

## `0x04` keychain signature

An access key signs a transaction with a `0x04` keychain signature. Viem builds this signature for any access-key account, such as `Account.fromP256(privateKey, { access: account })`. To build it yourself:

```text
signature    = 0x04 || account || access_key_signature
inner_digest = keccak256(0x04 || tx_signature_hash || account)
```

The access key signs `inner_digest`; a configurable account acting as an access key signs it with its owners, as a `0x05` multisig signature. `tx_signature_hash` is the transaction's signing hash ([keychain signature format](/docs/protocol/transactions/spec-tempo-transaction#keychain-variable-length)). Tempo checks that the key is authorized for `account`, unexpired, unrevoked, and of the stored type, then enforces its limits and scopes. Since the T1C network upgrade, Tempo rejects the legacy `0x03` keychain format.

## Revoke an access key

`revokeKey(keyId)` is permanent: that key ID can never be authorized again for the account. Configuration updates (owner changes) and [account upgrades](/docs/development/single-key-accounts#upgrade-to-a-configurable-account) leave every other key in place, so revoke each key separately.

## Account Keychain functions

| Function | Purpose | Viem action |
| --- | --- | --- |
| `authorizeKey` | Authorize an access key | `client.accessKey.authorize` |
| `revokeKey` | Revoke a key | `client.accessKey.revoke` |
| `updateSpendingLimit` | Set one token's limit; resets the remaining amount to the new limit and keeps the period | `client.accessKey.updateLimit` |
| `setAllowedCalls`, `removeAllowedCalls` | Replace or remove a target's scope | `writeContract` |
| `getKey` | Read a key's type, expiry, and status | `client.accessKey.getMetadata` |
| `getRemainingLimitWithPeriod` | Read the remaining limit and period end | `client.accessKey.getRemainingLimit` |
| `getAllowedCalls` | Read a key's scopes | `readContract` |
| `getTransactionKey` | Read the key signing the current transaction; `address(0)` means the root key | None; call it from a contract |

For `writeContract` and `readContract`, pass `Abis.accountKeychain` and `Addresses.accountKeychain` from `viem/tempo`. Functions that change keys must be called directly by the account's transaction (`msg.sender == tx.origin`). The [specification](/docs/protocol/transactions/AccountKeychain) lists every function, event, and error.
